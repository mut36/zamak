# 결정 기록

**왜 지금 이렇게 되어 있는가.** 코드를 읽으면 아는 "무엇"이 아니라, 코드에 안 남는
"왜"와 "무엇을 버렸는가"를 적는다. 뒤집힌 결정은 지우지 않고 취소선으로 남긴다 —
같은 논의를 다시 하지 않기 위해서다.

튜닝 수치(B/K)의 상세 유도는 [`tuning/chunk-size-model.md`](tuning/chunk-size-model.md),
API 한도 원본은 [`tuning/gemini-limits.md`](tuning/gemini-limits.md), 결정으로 안 이어진
것까지 포함한 실험 원본 기록은 [`tuning/experiment-log.md`](tuning/experiment-log.md).

## 1. 과금·접근 모델

### 1-1. BYOK(사용자 API 키)는 완전히 삭제됐다 — 2026-07-21

세 번 뒤집힌 끝의 최종 상태다.

| 시점 | 상태 |
|---|---|
| ~2026-07-18 | 하이브리드 — 키를 넣으면 그 키로, 없으면 서버 키로 |
| 2026-07-18 | ~~BYOK 필수~~ — 결제가 없으니 전원이 자기 키를 내라 |
| 2026-07-21 | ~~BYOK 선택~~ — 서버 키를 기본값으로, 키는 옵션 |
| **2026-07-21** | **BYOK 삭제** — 사용자가 API 키를 보는 화면 자체가 없다 |

**이유**: 어차피 로그인 + 서버 키 + 크레딧으로 가기로 확정된 이상, BYOK는 언젠가
지울 코드였다. 그리고 결정적으로 — **무료 Gemini 키는 Google Search grounding을
아예 지원하지 않는다.** grounding은 `/api/enrich`가 작품의 감독·톤·인물 말투를
가져오는 수단이고, 이건 우리 제품의 방어선 2개 중 하나다. BYOK 사용자는 구조적으로
이 기능을 못 쓴다 — 즉 BYOK 티어는 "느린 무료"가 아니라 "핵심 기능이 빠진 무료"였다.

**삭제된 것**: 키 입력 UI, `geminiKey` state·sessionStorage, `x-gemini-key` 헤더
(클라·서버 양쪽), `apiKeyError.ts`, `ApiKeyField.tsx`, invalid-key UX 전체.

**남긴 것**: provider 레이어의 `apiKey` 파라미터. 계정별 키가 생길 경우의 seam이고
아무 비용이 없다.

> 교훈: 기획이 죽인 기능을 "옵션"으로 반쯤 남기지 말 것. 한 번 그렇게 했다가
> 아무도 채울 이유가 없는 입력란만 화면에 남았다.

### 1-2. 익명 미리보기는 폐기됐다 — 2026-07-21

앞 50줄을 서버 키로 무료 번역해 보여주고 그 아래에 페이월을 두는 방식. 구현·검증까지
마쳤으나 **당일 폐기**했다.

**이유**: 막을 수 없는 어뷰징 벡터. 같은 파일을 51~100줄, 101~150줄로 잘라 "다른 파일"인
척 반복 요청하면 IP당 일일 제한 안에서도 전체를 공짜로 뽑아간다. 레이트리밋은 요청 횟수만
세지 파일 내용을 보지 않는다. 파일 해시 추적으로 막으려 하면 복잡도가 계속 붙는데,
**더 단순한 해법은 "익명이 서버 키를 쓰는 엔드포인트를 아예 없애는 것"**이었다.

대체안이 아래 1-3이다. 코드는 전량 제거됐다.

### 1-3. 로그인 게이트 + 선불 크레딧 — 2026-07-21 구현 완료

```
방문 → 로그인 벽 → Google 로그인 → 가입 즉시 크레딧 1개 → 전체 번역 1회 무료
     → 이후 크레딧 구매 (결제 미구현, "준비 중"에서 멈춤)
```

- **어뷰징 표면이 사라진다.** 익명이 서버 키를 쓰는 경로가 없고, 계정은 구글이
  사실상 신원 확인을 대신해준다.
- **완결된 결과물이 미완성 미리보기보다 강한 미끼.** "손에 쥐어본 사람만 두 번째에
  결제한다"는 논지는 유지하되, 50줄 샘플 대신 진짜 완성품을 준다.
- 다계정으로 무료 1편을 반복 수령하는 건 이론상 가능하지만 일반적인 SaaS 프리미엄
  어뷰징 수준이라 우선순위가 낮다. 익명 API 자금 유출과는 리스크 등급이 다르다.

### 1-4. 크레딧은 요청이 아니라 **파일** 단위로 차감한다

**이것이 이 시스템에서 가장 중요한 설계 결정이다.**

영화 한 편은 청크 여러 개로 쪼개져 `/api/translate`를 N번 호출한다. 요청마다 차감하면
한 편에 크레딧이 7~12개 날아간다. 그래서:

1. `/api/translation/begin`이 **크레딧 1개 차감 + job 생성을 하나의 SQL 함수
   (`begin_translation_job`)에서** 수행한다 — 단일 statement의 행 잠금 덕에 탭 두 개가
   마지막 크레딧을 동시에 쓸 수 없다.
2. 이후 모든 청크 요청은 `jobId`를 함께 보내고, 서버가 소유권·유효기간을 검증한다.

이게 없으면 `/api/translate`는 "로그인만 하면 무제한"이 된다. 크레딧이 begin에서
차감되므로, **그 지불을 증명하는 자리가 청크 엔드포인트**다.

*실측 검증(2026-07-21)*: 461블록 → 청크 3개 → Gemini 3회 호출 → `translation_jobs` 행
1개, 잔액 1 → 0. 설계대로 동작한다.

### 1-5. 보조 라우트는 로그인만 요구하고 크레딧은 안 깎는다

`/api/analyze`, `/api/enrich`, `/api/summarize`는 값싼 flash-lite 호출이다. 사용자가
결과를 보고 버릴 수도 있는 메타데이터에 과금하는 건 부당하고, 금액도 무의미하다.
다만 **서버 키를 쓰므로 로그인은 반드시 요구한다.**

### 1-6. 설정 누락 시 fail-closed

Supabase 설정이 없으면 모델 라우트는 **500으로 닫힌다.** 열어두고 넘어가면 설정 실수가
곧 "인증 없는 서버 키 개방"이 되는데, 그건 이 게이트가 막으려는 바로 그 상태다.

### 1-7. 미해결 — 번역 실패 시 크레딧 환불 없음

크레딧은 begin에서 차감되므로 이후 번역이 실패해도 돌려주지 않는다. 부분 실패는 실패한
청크가 원문을 유지해 **재생 가능한 완전한 SRT**가 나오므로 결과물은 손에 남는다는
판단으로 수용했다. 실패율이 오르면 재검토 대상.

### 1-8. 랜딩은 벽 앞의 정적 콘텐츠, 단일 스크롤, `/` 유지 — 2026-07-21

로그인 벽은 내릴 수 없으므로(모델 라우트 전부 서버 키) 랜딩의 유일한 일은 "로그인
버튼을 누를 이유"를 만드는 것이다. 전부 정적 콘텐츠라 API 비용 0.

- **구조**: `app/page.tsx`의 `!user` 분기에서 `LandingPage` 렌더. `/`·`/app` 분리는
  검토 후 보류 — 결제가 붙어도 필요한 건 `/terms`·`/refund` 같은 문서 페이지지
  라우트 분리가 아니고, 분리 비용(OAuth 콜백 수정)은 지금 낼 이유가 없다.
  `LandingPage`는 독립 컴포넌트라 분리가 필요해지면 import 한 줄만 옮기면 된다.
- **메뉴바 없음**: 이동할 페이지가 없는데 메뉴를 두면 빈 약속. 대신 푸터를 미리
  두어 결제 날 법적 고지·가격 링크가 들어갈 자리를 확보했다.
- **가격 미노출** (대표 위임 후 결정): 잠정 가격은 원가 실측 후 조정될 수 있어
  숫자를 박지 않는다. 대신 "사람에게 맡기면 편당 15만 원" 앵커 + 무료 1편만 노출.
- **브랜드 톤 = 도구, 타깃 = 국내 우선·해외는 나중** (대표 확인). 카피는 한국어
  한 벌, `COPY.landing` 네임스페이스.
- **샘플은 자체 제작 예문** (형사물 선배/신입 대화 3블록) — 저작권 0. 방어선 2개
  (타임코드 동일, 관계 기반 존댓말/반말)가 눈으로 비교되도록 설계.
- 인터랙티브 데모(가짜 위저드 시뮬레이션)는 각하 — 구현 비용 대비, "실제가
  아님"이 드러나는 순간의 신뢰 역효과가 더 크다.

### 1-9. 결제는 토스페이먼츠 결제창 + 서버 승인 — 2026-07-22

국내 단일 시장이므로 토스페이먼츠. 해외를 열면 PayPal/Paddle을 **추가**하게 되므로,
Toss 호출은 `app/lib/server/toss.ts` 한 곳에만 두고 라우트는 "주문 → 승인 → 지급"
흐름만 안다. PG 추가는 이 파일 옆에 형제 모듈을 놓는 일이 된다.

- **금액은 브라우저가 정하지 않는다.** 클라이언트는 팩 id만 보내고,
  `/api/payments/prepare`가 `app/config/packs.ts`에서 가격을 찾아 **결제창을 열기 전에**
  `orders` 행에 적는다. 정산 함수는 Toss가 알려준 결제 금액이 그 행과 다르면 거절한다.
  이게 없으면 클라이언트가 30편을 100원에 사갈 수 있다.
- **승인은 successUrl(서버 라우트)에서 한다.** 결제창은 `paymentKey`만 만들고 돈은
  아직 안 움직인다. 승인을 클라이언트 페이지에서 하면 **우리 JS가 도는지에 결제가
  의존**하게 되므로, Toss가 리다이렉트하는 목적지를 `/api/payments/confirm`으로 직접
  잡았다. 돈을 움직이는 GET은 이례적이지만 외부 사이트발 최상위 리다이렉트라 다른
  모양이 없고, 대신 전 경로를 멱등으로 만들었다(주문이 `paid`면 재승인 없이 통과,
  `Idempotency-Key`는 주문번호, `ALREADY_PROCESSED_PAYMENT`는 결제 조회로 회수).
- **가상계좌·계좌이체는 안 판다.** 입금이 몇 시간 뒤 웹훅으로 오는데 웹훅 수신부가
  없다. 지금 열면 "결제됐는데 크레딧이 없다"가 구조적으로 생긴다. 카드/간편결제만.
- **정산도 크레딧 차감과 같은 규칙** — `credits` 테이블에 쓰는 경로는 여전히
  security definer 함수뿐이고(`settle_order`), 행 잠금으로 탭 두 개가 같은 주문을
  두 번 지급할 수 없다. 클라이언트는 `orders`를 읽을 수만 있다.
- **세션은 쿠키로 따라온다.** 승인 라우트는 `requireUser()`를 그대로 쓴다 —
  Toss 리다이렉트는 최상위 GET이라 SameSite=Lax 쿠키가 실린다. 서비스 롤 키를
  새로 들이지 않기 위한 선택이고, 대가는 웹훅을 붙일 때 그 키가 필요해진다는 것.
- **환불 버튼은 안 만든다.** 미사용분 전액 환불이 정책이지만(`/legal`), 거래량이
  붙기 전까지는 토스 대시보드에서 수동 처리가 더 싸다. 자동화는 CS가 쌓이면.

### 1-10. 베타 가입 크레딧 1편 → 3편 (한시적) — 2026-07-27

~30명에게 링크로 베타를 돌리는데, 토스 가맹점 심사가 아직이라 결제로 크레딧을
채울 방법이 없다(§1-9 끝의 "대표가 직접 해야 하는 것" 참고). 결제창을 흉내 낸
테스트 모드(테스트 카드 등)도 검토했지만, 애초에 **공짜로 주는 거라 결제창이
낄 이유가 없다**는 게 결론 — 그래서 가입 크레딧 자체를 올리는 쪽으로 단순화했다.

- `supabase/migrations/0003_beta_signup_credit.sql`이 `grant_signup_credit()`
  트리거의 지급량을 1 → 3으로 바꾼다. **신규 가입자에게만** 적용되고, 이미 1편을
  받은 계정(마이그레이션 이전 가입자)은 소급되지 않는다 — 필요하면
  `supabase/comp-credit.sql`의 "+3 지급" 스니펫으로 개별 보충.
- `app/i18n/simpleCopy.ts`의 "1편 무료" 카피 3곳(`ctaHint`, `closing.title/body`,
  `credits.emptyBody`)도 3편으로 맞췄다. `tooLargeBody`·`coverage`의 "1편"은
  무관(크레딧 1개=자막 몇 줄인지를 말하는 것)이라 손대지 않았다.
- **한시적이다.** 정식 오픈(결제 활성화) 시 되돌린다 — 되돌리기 SQL의 위치는
  아래 §1-10-1을 볼 것(0003 하단의 옛 블록이 **아니다**). 베타 기간에 이미 지급된
  크레딧은 회수하지 않는다(그럴 필요가 생기면 그때 별도 스니펫 작성).

### 1-10-1. 되돌리기를 0010으로 다시 씀 — 라이트1+프로0 — 2026-07-31

§1-10이 "0003 하단의 되돌리기 블록을 실행하라"고 적어뒀는데, **그 블록은 지금
실행하면 신규 가입자에게 크레딧 0편을 준다.** 그 사이 `0004_credit_tiers.sql`이
잔액을 `lite_balance`/`pro_balance`로 쪼개고 `balance`를 DEPRECATED로 내렸는데,
0003의 블록은 옛 단일 `balance=1`만 채우기 때문이다 — `begin_translation_job`은
새 두 컬럼만 차감하므로 두 잔액이 0인 계정이 만들어지고 첫 번역에서 바로
insufficient_credits를 맞는다. **마이그레이션에 딸린 롤백 주석은 뒤 마이그레이션이
스키마를 바꾸면 같이 썩는다**는 사례로 남긴다.

- 올바른 되돌리기는 `supabase/migrations/0010_signup_credit_revert.sql`. 0003의
  옛 블록에는 실행 금지 경고를 달았다.
- **복귀 지급량은 라이트 1 + 프로 0.** 프로를 빼는 이유: 결제가 열리는 순간
  프로는 전환의 미끼가 아니라 **판매 대상**이 된다. 프로 1편의 실측 원가가
  약 2,500원(`docs/tuning/cost-per-block.md`, 크레딧 상한 2,000블록 기준)이라
  미끼로 쓰기에 비싸기도 하다.
- **아직 실행하지 않았다** — 토스 가맹점 심사가 안 끝나 결제창이 없는데 지금
  되돌리면 신규 가입자가 1편을 쓰고 나서 충전할 경로가 없다(대기자 등록 화면만
  뜬다). 파일만 커밋해두고 실행은 결제 오픈 시점으로 미룬다.
- §1-10이 말한 "카피 3곳"은 **이미 해소됐다** — 베타 리디자인(852dea9)에서
  `ctaHint`·`closing.title/body`·`credits.emptyBody` 키가 전부 사라졌다.

### 1-12. 랜딩 메시지: "속도"보다 "구조적 타임코드 안정성" — 2026-07-28

랜딩의 핵심 메시지를 "30초 번역"에서 **"번역해도, 뒤 자막이 밀리지 않도록."**으로 교체했다.

### 1-16. 푸터는 전 페이지 하나로 통일 — 2026-07-31

랜딩(§1-15)과 앱 셸이 각자 푸터를 갖고 있었고, `/mypage`·`/legal/*`에는 아예
없었다. 전자상거래법 제10조의 판매자 표시는 어느 페이지로 바로 들어오든 닿아야
하는데, 페이지마다 다른 푸터를 두면 **어느 하나가 반드시 빠진다.** 그래서
`app/components/SiteFooter.tsx` 하나를 다섯 화면 전부에 넣었다. 변형(variant)을
두지 않은 것이 이 결정의 핵심이다 — 변형을 허용하는 순간 같은 누락이 돌아온다.

- **값은 `COPY.seller` 한 곳.** `/legal`의 사업자 정보 표와 푸터가 같은 객체를
  읽는다. 두 곳에 적으면 한쪽만 고쳐져 갈라지고, 갈라진 쪽이 표시의무 위반이 된다.
  `/legal`에 표가 중복 노출되는 건 감수했다 — 목차 앵커가 그 표를 가리키고,
  같은 소스라 드리프트가 없다.
- **서버 컴포넌트**라 정적인 `/legal/*`에 들어가도 클라이언트 번들이 늘지 않는다.
  대신 로그인 여부를 모르므로 마이페이지 링크는 항상 보이고, 비로그인 방문자는
  `/mypage`가 홈으로 돌려보낸다.
- **랜딩 앵커(`/#compare` 등)는 넣지 않았다.** 로그인하면 `/`가 앱 셸로 바뀌어
  앵커가 죽는다. 전역 푸터는 로그인 상태와 무관하게 유효한 링크만 담는다.
- 워드마크는 `app/components/Wordmark.tsx`로 빼서 랜딩 nav와 공유한다.
- §1-15가 만든 `.lp-footer`는 `.site-footer`로 대체됐다. `.lp-wordmark`는 남는다.
- 버전 `0.24.0`.

### 1-17. 프로는 팩이 아니라 종량제로 간다 — 베타 범위 밖 (2026-07-31)

§2-16의 장편 실측으로 Pro 원가가 확정되면서 팩 가격을 재계산했고, **팩 모델
자체가 Pro에 안 맞는다**는 결론이 나왔다. 대표 판단: **프로는 실사용 크레딧을
계산하는 새 결제 모델로 간다. 크레딧 정책을 새로 설계해야 하므로 베타 오픈
범위 밖으로 미룬다.**

#### 왜 팩이 안 맞는가

크레딧은 "1편 = 파일 1개"인데(§1-4), Pro는 **편차가 크레딧 단위를 무의미하게
만든다**. 같은 1편인데 원가가 4.6배 벌어진다:

| 파일 | Pro 원가(글로사리 포함) |
|---|---|
| TV 1편 (461블록) | 627원 |
| 전형적 장편 (1,100블록) | 1,595원 |
| 크레딧 상한 (2,000블록) | **2,900원** |

flash는 이 편차가 절대액으로 작아서(135~780원) 팩 하나로 뭉갤 수 있었지만,
Pro는 상한 파일 한 편이 TV 한 편의 4.6배다. 팩으로 팔면 **큰 파일만 넣는 게
언제나 이득**이라, 유저가 합리적으로 행동할수록 우리가 손해 보는 구조가 된다.

#### 재계산 결과 (근거는 `docs/tuning/cost-per-block.md`)

편당 손익분기 = 원가 ÷ (1 − 카드수수료) × (1 + VAT). 일반과세 10% + 토스 3.3%
기준이며, 과세유형·수수료율을 바꿔도 ±7% 안이라 결론은 안 흔들린다.

- **Pro 손익분기 3,299원/편** (상한 파일 + 글로사리)
- **Lite 손익분기 888원/편** (같은 조건)

#### ⚠️ 같이 드러난 것 — 현행 라이트 팩 2개가 최악 시나리오 적자다

| 팩 | 편당 | 실수취 | 최악마진 | 전형마진 |
|---|---|---|---|---|
| starter (3편 2,900원) | 967원 | 850원 | 8% | 50% |
| standard (10편 7,900원) | 790원 | 694원 | **−12%** | 38% |
| bulk (30편 18,900원) | 630원 | 554원 | **−41%** | 23% |

`app/config/packs.ts`(feature/payments)의 주석은 *"상한 파일이 약 500원이니 모든
팩이 편당 그 위에 있다"*고 적어뒀는데, **그 500원이 VAT·카드수수료·글로사리를
전부 뺀 값이었다.** 셋을 넣으면 780원이고 bulk는 편당 554원만 남는다.

전형적 파일(1,100블록)에서는 23~50%가 남으므로 평균적으로는 흑자다. 문제는
**손해 보는 사용 패턴을 유저가 학습할 수 있다**는 것 — 큰 파일에 쓸수록 이득이다.
Pro 종량제를 설계할 때 라이트 팩도 같이 재가격한다(`docs/TODO.md`).

**교훈: 원가 비교는 판매가가 아니라 실수취액과 해야 한다.** 세금과 PG 수수료를
빼기 전 숫자로 마진을 계산하면 12%p가 조용히 사라진다.

### 1-11. 법적 고지 — 저작권보다 규제 준수가 먼저였다 — 2026-07-27

자막 번역 서비스의 리스크를 저작권으로만 보고 약관을 강화하려다, 실제 순위가
뒤집혀 있다는 걸 확인하고 방향을 바꿨다.

**저작권 리스크는 구조적으로 낮다.** 국내에서 자막으로 실제 처벌된 사례는 자막을
*공개 배포한* 커뮤니티·웹하드다 — 침해되는 권리가 공중송신권이라 배포가
구성요건이다. ZAMAK은 파일을 저장하지도 배포하지도 않는다(§2-1의 무저장 구조가
여기서 프라이버시 미담이 아니라 **핵심 방어 논리**가 된다). 게다가 저작권법
제30조(사적이용 복제)에 제36조 제1항이 번역까지 허용하므로, 소장 영상을 개인적으로
보려고 번역하는 다수 이용자는 법이 직접 허용하는 행위를 하는 것이다.

→ 그래서 약관의 무게를 "권리 없으면 쓰지 마라"가 아니라 **"배포·공유·판매 금지"**에
실었다. 전자는 정상 이용자 대부분을 겁줘서 전환율만 깎고 방어력은 같다.

**대신 이미 위반 중이던 두 가지가 있었다.**

1. **개인정보처리방침 부재** — 개인정보보호법 제30조는 개인정보를 수집하는 모든
   서비스에 처리방침 공개를 의무화한다. Google 로그인으로 이메일을 받는 순간
   대상이다. 저작권과 달리 "걸릴 확률"이 아니라 점검하면 바로 나오는 과태료
   사안이라 `/legal/privacy`를 신설했다. 처리자가 전원 미국 법인이라
   제28조의8 국외이전 고지도 같이 넣었다.
2. **`SELLER_INFO` TODO** — §1-9와 위 "미결" 3번에 이미 적혀 있던 것. 통신판매업
   미신고 자체가 벌칙 대상이라 결제 오픈의 하드 블로커다. 처리방침의
   개인정보 보호책임자(`OFFICER`)도 같은 이유로 TODO다.

**초안에서 뺀 것들.** ① "모든 손해 전액 배상 / 회사는 일체 책임 없음" 식 강도는
약관규제법 제7조로 무효가 될 수 있어(개인 대상 B2C) **고의·과실 범위**로 한정했다.
② "시스템 오류·데이터 유실 면책"은 §1-7 후속으로 이미 약속한 *번역권 복구*와
정면으로 충돌해서, 면책 범위를 결과물의 정확성·가용성으로 좁혔다. ③ 권리침해
신고 시 "해당 콘텐츠 접근 차단" 조항은 **호스팅하는 게 없어 이행 불가능**이라
계정 이용제한으로만 적었다 — 지키지 못할 약속을 약관에 쓰면 오히려 불리하다.
(③은 §5-4에서 결과물 30일 보관이 붙으며 전제가 바뀌었다 — 이제 보관 기간 안의
특정 결과물은 실제로 찾아 지울 수 있어, 약관을 그에 맞게 다시 썼다.)

**노출은 모달이 아니라 상시 고지.** 첫 업로드에 동의 모달을 세우면 "30초면
번역돼요"라는 제품 약속(§1-8)을 스스로 깬다. 대신 ① 업로드 드롭존 아래(리스크가
실제로 발생하는 지점), ② 가입 CTA 바로 아래 signup-wrap 문구, ③ 푸터 링크 —
세 곳에 상시 노출했다. signup-wrap은 단순 푸터 링크(browsewrap)보다 효력이
안정적이면서 모달의 마찰이 없다. **→ §5-7 참고 — 이 결정은 결과물 보관이
시작되며 뒤집혔다. 상시 고지 세 지점은 그대로 두되, 첫 번역 앞에 동의 모달이
추가로 선다.**

### 1-18. 랜딩의 수치는 코드에서 온다 — 핸드오프 예시값 정리 (2026-07-31)

§1-15가 디자인 핸드오프를 그대로 옮기면서, **랜딩에 박힌 숫자 대부분이 예시값**인
채로 배포돼 있었다. 표시광고 리스크가 실재하므로 전수 대조하고 실제값으로 바꿨다
(`TODO.md`의 "랜딩 문구의 수치 검증"에 항목별 근거).

**틀린 것이 세 종류였다.**

1. **계산이 틀린 것** — 비교 섹션의 CPS 태그(17.3 / 9.6 / 6.2). 같은 화면에 적힌
   노출 시간(2.63초)과 대사로 `computeCps` 방식대로 다시 재면 **17.1 / 10.3 /
   6.5**다. CPS 섹션의 측정값 3개(6.2 / 13.0 / 4.3)도 마찬가지로 틀렸고, 그중
   "예능 13.0"은 **같은 카드가 내건 상한 14를 실제로는 15.0으로 넘고 있었다.**
2. **없는 기능을 판 것** — 영상 종류별 CPS 프로필(영화 12 / 예능 14 / 다큐 10,
   한 줄 18·20·16자)은 코드에 존재하지 않는다. 실제로는 도착어 단위 단일 밴드
   (`languages.ts`의 `reading` + `lineMaxChars: 25`)뿐이다. 마찬가지로 "숫자 표기
   규칙"은 프롬프트에도 후처리에도 없고, "올린 포맷 그대로 다운로드"는 원본 형식
   writer가 VTT 하나뿐이라(`subtitles/document.ts`의 `WRITERS`) ASS·SMI에 대해
   거짓이었다.
3. **강점을 잘못 말한 것** — "타임코드는 원본 그대로 유지". `adjustSubtitleTiming`은
   읽기 속도가 상한을 넘는 블록의 타임코드를 이웃 갭 안에서 실제로 넓힌다. 우리
   강점은 타임코드가 안 변하는 것이 아니라 **AI가 타임코드를 만지지 않는 것**
   (§2-1)이고, 그래서 싱크가 안 밀린다. 문구를 그쪽으로 고쳤다.

**CPS 섹션은 축을 바꿨다.** 세그먼트 컨트롤을 지우는 대신 "영상 종류별 기준값"에서
**"대사 길이별 예시 + 단일 기준"**으로 바꿨다 — 인터랙션은 살고, 보여주는 수치는
전부 코드에서 온다. 영상 종류별 프로필은 **기능 자체를 나중에 구현하기로** 했다
(`TODO.md`의 "영상 종류별 CPS 프로필"). 즉 이 커밋은 문구를 코드에 맞췄고, 나중에
코드가 원래 문구를 따라잡는 순서다.

**속도는 "12초 + 조건"으로 정리했다.** "최고 속도 10초"는 어떤 런도 찍은 적 없는
숫자였고(실측 최소가 461블록 12.0초), 진행링은 또 flash 30초를 쓰고 있어 랜딩·UI·
로그 셋이 전부 달랐다. 대표 결정은 **실측치를 그대로 쓰되 파일 크기를 명시**하는
것 — "드라마 한 편 12초"다. 같은 로그의 장편(1,874블록)은 17.8초라, **조건 없는
12초는 장편에 대해 거짓이 된다.** 그래서 세 곳을 함께 맞췄다:

| 자리 | 값 | 근거 |
|---|---|---|
| 랜딩 제목 + 히어로 | 드라마 한 편 12초 | 461블록 실측 12.0초 |
| 랜딩 각주 | "라이트 모델 · 461블록 기준, 장편은 더" | 1,874블록 17.8초 |
| 진행링 `TRANSLATION_ESTIMATE_MS` | flash 30초 → **20초** | 실측 최악값 17.8초를 덮는 값 |

링이 짧은 쪽(12초)이 아니라 긴 쪽을 덮는 이유는 링의 성질 때문이다 — 링은 99%로
수렴하다 결과가 도착해야 100%가 되므로, **추정이 길면 일찍 차고 짧으면 기어간다.**
파는 숫자는 짧은 쪽, 기다리게 하는 숫자는 긴 쪽이 맞다. 타임라인의 중간 시각
(0:01/0:03)은 실측한 적이 없어 단계 번호 01–04로 바꿨다.

#### 2026-08-03 개정 — 12초 → **15초**, 그리고 "장편은 더"라는 설명은 틀렸다

베타 오픈 전 점검에서 두 가지가 드러났다.

**첫째, 위 결정이 히어로에 반영되지 않았다.** 7/31에 12초로 정했는데
`COPY.landing.hero.sub`와 `settings.liteDesc`는 **10초**로 남아 있었다 — 같은
페이지의 속도 섹션(12초)과 자기모순이었고, 10초는 위 문단이 이미 "어떤 런도 찍은
적 없는 숫자"라고 적어 둔 값이다. 표시광고법 리스크를 문서로 알면서 화면엔 그대로
둔 상태였다.

**둘째, 12초 자체가 재현되지 않았다.** 같은 파일·같은 설정으로 8/3에 다시 돌리니
**13.4초**였다(`experiment-log.md` 2026-08-03). 12.0초는 최선값이었지 대표값이
아니었다. 그래서 실측 세 건(13.4 · 14.8 · 17.8)을 놓고 **15초**로 올렸다.

**그리고 각주의 "장편은 자막 길이에 따라 더 걸립니다"는 인과가 틀렸다.** 같은 날
1,124블록 파일을 재보니 14.8초 — 블록이 **2.4배**인데 시간은 **10%**만 늘었다.
벽시계는 자막 길이가 아니라 **웨이브 수**로 결정된다:

| 블록 | 청크 | 웨이브 | 총시간 |
|---|---|---|---|
| 461 | 5 | 1 | 13.4초 |
| 1,124 | 11 | 1 | 14.8초 |
| 1,874 | 19 | **2** | 17.8초 |

`SERVER_CONCURRENCY=16` · `SERVER_CHUNK_SIZE=100`이라 **1,600블록까지는 전 청크가
한 웨이브에 나가고, 총시간은 곧 최장 청크 하나의 시간**이다(위 두 런 모두
`총시간 == 최장청크`로 찍혔다). 청크는 어떤 파일에서든 ~100블록이므로 그 시간이
거의 안 변한다. 1,874블록이 느린 건 19청크 > 16이라 두 번째 웨이브가 생겨서다.
크레딧 상한 2,000블록 = 20청크 = 2웨이브가 최악이고 그게 ~18초다.

이는 `PRO_CHUNK_SIZE` 주석(§2-16)이 Pro에서 이미 적어 둔 것과 같은 구조적 논증이다
— **파일이 길어지면 청크 *수*만 늘고 청크 *크기*는 안 늘어난다.** flash에도 같은
성질이 적용된다는 걸 이번에 실측으로 확인했다.

각주는 그래서 "장편은 더"가 아니라 **"1,600블록을 넘으면 조금 더"**로 고쳤다.
진행링 `TRANSLATION_ESTIMATE_MS` flash 20초는 그대로 둔다 — 여전히 최악값
17.8초를 덮고, 위 문단의 "파는 숫자는 짧은 쪽, 기다리게 하는 숫자는 긴 쪽" 원칙도
15초 < 20초로 유지된다.

**교훈은 "수치 옆에 출처를 적는다"다.** `COPY.landing.cps`에 어느 상수에서 온
값인지 주석을 달았다. 랜딩 수치가 코드에서 오지 않으면 코드가 움직일 때 아무도
모른다 — 이번에 틀린 값들이 정확히 그 경로로 생겼다.

### 1-19. 영상 종류별 읽기 속도 프로필 — 랜딩이 팔던 기능을 코드가 따라잡았다 (2026-07-31)

§1-18에서 "영상 종류별 CPS·한 줄 자수"가 **코드에 없는 기능**이라 랜딩을
실제값으로 낮췄다. 대표 결정은 반대 방향이었다: **문구를 낮추지
말고 기능을 만든다.** 그래서 랜딩 CPS 섹션은 원래 모양·원래 숫자로 되돌아갔고,
이번엔 그 숫자가 진짜다.

**축을 하나 더 만들지 않았다.** 읽기 속도는 이미 도착어에 달려 있었으므로
(`TargetLang.reading`), 프로필은 그 옆에 새 개념을 세우는 대신 **같은 표를
2차원으로** 넓혔다 — `TargetLang.shapes: Record<프로필, {target, hardMax}>`.
언어를 추가하든 프로필을 추가하든 고치는 파일은 여전히 `languages.ts` 하나다.

**선택 화면도 새로 만들지 않았다.** 업로드 화면에 이미 "콘텐츠 유형"
2지선다(영화·드라마 / 유튜브·일반)가 있었고, 그걸 랜딩과 같은 3지선다로 넓혀
`ContentType`을 그대로 프로필 키로 썼다(`movie`/`variety`/`doc`). **한 번의 선택이
두 가지를 정한다** — 정보 수집 분기(영화만 TMDB enrich)와 자막 모양. 별도
선택기를 설정 화면에 두는 안은 컨트롤만 늘고 사용자에겐 같은 질문을 두 번 하는
꼴이라 버렸다.

**랜딩이 파는 "권장 읽기 속도"는 목표치(target)다** (대표 결정) — `target`은
`adjustSubtitleTiming`이 위반 블록을 끌어내리는 착지점, `hardMax`는 그 위만
손대는 천장이다. 최종 값(2026-07-31 대표 결정):

| 프로필 | target | hardMax |
|---|---|---|
| 영화 · 드라마 | 10 | 12 |
| 예능 · 유튜브 | 8 | 11 |
| 강연 · 토크쇼 | 12 | 15 |

**영화 = 프로필 도입 전의 한국어 밴드 그대로다.** 기본 프로필이기도 해서, 프로필을
안 고른 경로(구 클라이언트, 폴백)는 예전과 완전히 같이 동작한다 — 기능을 추가하면서
기존 동작을 하나도 안 건드린 셈이라, 이 축이 회귀를 만들 여지가 없다.

**순서가 직관과 반대인 것이 핵심이다.** 예능이 가장 **느긋하고**(8) 강연이 가장
**촘촘하다**(12). 발화 속도가 아니라 **남는 주의력**으로 정했기 때문이다 — 예능
화면엔 이미 자체 자막·그래픽이 깔려 번역 자막에 쓸 주의력이 가장 적고, 강연은
화면이 비어 있어 자막에 집중되는 대신 말이 끊이지 않아 한 줄을 넓히면 다음 말을
밀어낸다. 초안(영화 12 / 예능 14 / 다큐 10)은 발화 속도를 따라간 배치였고,
뒤집었다.

**다큐멘터리는 영화 프로필에 얹었다.** 읽는 방식이 영화에 가깝고, 카드를 4장으로
늘리면 업로드 첫 화면이 분류 퀴즈가 된다. 세 번째 슬롯은 실제로 다른 대우가
필요한 강연·토크쇼가 가져갔다.

**한 줄 자수는 프로필 축에서 뺐다** (대표 결정, 같은 날). 처음엔 프로필마다
18/20/16자를 줬다가 25자 하나로 되돌렸다. 이유는 성질이 다르기 때문이다 —
읽기 속도는 **완성된 줄이 화면에 머무는 시간**을 바꾸지만, 줄 예산은 **번역문
자체**를 바꾼다(분할·압축이 늘어난다). "예능이라 문장이 다르게 번역된다"는 건
프로필이 약속한 범위가 아니고, 검증도 훨씬 비싸다(타이밍은 계산으로 확인되지만
번역 품질은 사람이 봐야 한다). 그래서 프로필이 바꾸는 것은 **오직 노출 시간**이다.

**그 결과 프로필은 서버로 갈 이유가 없어졌다.** 프롬프트가 프로필에 의존하지
않으므로 요청 바디의 `contentProfile`, 라우트·`translateSubtitle`·composer의
파라미터를 전부 걷어냈다. 프로필은 클라이언트의 타이밍 패스
(`getReadingSpeed(도착어, 프로필)` → `adjustSubtitleTiming`)에서만 쓰인다.
안 쓰이는 배선을 "나중에 쓸지도 모르니" 남겨두면 그게 다음 사람이 읽어야 할
거짓 단서가 된다.

**랜딩 카드에서도 "한 줄 최대" 줄을 뺐다.** 남은 스펙은 권장 읽기 속도와 2줄
상한뿐이고, 프로필별 "ZAMAK이 하는 일" 문구도 압축·요약이 아니라 **노출 시간**을
말하도록 고쳤다 — 압축을 프로필이 다르게 한다는 근거가 이제 없다.

**랜딩과 코드를 테스트로 묶었다.** `app/i18n/simpleCopy.test.ts`가 랜딩 카드의
`value`를 `shapes` 표와 대조하고, 카드에 적힌 예시 대사·타임코드로 CPS를 직접
계산해 표시값(`CPS 6.1 ✓`)과 맞는지 확인한다. 같은 파일이 **랜딩이 프로필별 줄
예산을 다시 팔기 시작하면** 실패하도록도 막아 뒀다(위 결정의 회귀 방지). §1-18의 사고는 "문구가 코드에서 오지 않아서" 생겼으므로, 다시 갈라지면
빌드가 깨지게 만드는 것이 재발 방지책이다.

- `resolveSubtitleShape`는 모르는 프로필·빈 프로필을 **거절하지 않고** 기본
  프로필로 폴백한다. 자막을 아예 못 만드는 것보다 영화처럼 만드는 게 낫다.
- env `NEXT_PUBLIC_CPS_*`는 그대로 **전역** 오버라이드다(모든 도착어 × 모든
  프로필). 프로필 하나만 바꾸려면 표를 고칠 것.
- 버전 `0.26.8`.

### 1-20. 히어로 데모의 높이는 '가장 긴 대사'가 정한다 — 모바일 레이아웃 시프트 (2026-08-04)

베타 배포 첫날 들어온 리포트: **"글자가 바뀌면서 페이지 전체가 실시간으로
위아래로 움직여 읽을 수가 없다."** 모바일에서만 났다.

원인은 애니메이션이 아니라 **높이**였다. 히어로 데모 카드는 대사 4개를 3.8초마다
순환하는데, 대사마다 줄 수가 다르다. 데스크톱에서는 `min-h-[150px]`과 넓은 폭이
차이를 흡수했지만, 375px에서는 본문 폭이 232px(패딩 40px×2)까지 줄어 2줄짜리
대사가 3줄로 접힌다. 실측:

| 대사 | 카드 높이(375px) |
|---|---|
| 0 (src 2줄 / ko 3줄) | **299px** |
| 1 (src 1줄 / ko 1줄) | **210px** |
| 2 (src 3줄 / ko 2줄) | 288px |
| 3 (src 1줄 / ko 1줄) | 210px |

**3.8초마다 최대 89px.** 히어로 아래 6개 섹션 전체가 그만큼 밀렸다. 게다가 전환
직전 500ms 동안 ko를 대기 커서로 **교체**했기 때문에 그 사이 한 번 더 주저앉았다
(299 → 232px).

**고친 방법 — 자리를 비우지 않는다.** 대사 4개를 전부 렌더해 CSS 그리드 한 칸
(`grid-area: 1/1`)에 겹쳐 쌓고, 쉬는 대사는 `display:none`이 아니라
`visibility:hidden`으로 숨긴다. 숨어도 자리는 차지하므로 **칸 높이 = 가장 긴 대사의
높이**로 늘 고정된다. 대기 커서도 ko를 치우고 들어서는 대신 `.lp-hero-ko-slot`
안에 겹친다 — 치우면 활성 대사가 가장 긴 대사일 때 카드가 500ms 내려앉는다.

- **숫자를 안 박은 게 요점이다.** `min-height: 299px`로도 오늘은 고쳐지지만,
  대사를 하나 더 넣거나 폰트를 키우면 그날로 다시 틀린다. 스택은 내용이 바뀌면
  높이도 같이 맞는다.
- **등장 애니메이션이 `key` 리마운트에서 클래스로 바뀌었다.** 겹쳐 쌓은 노드는
  순환해도 살아 있어서 리마운트가 안 일어난다. 대신 `.is-waiting`이 빠지는 순간
  `animation`이 `none → zsubin`으로 바뀌며 다시 돈다. 대기가 끝나는 시점에
  맞춰야 하므로 `.is-on`이 아니라 `:not(.is-waiting)`이 조건이다.
- `prefers-reduced-motion`의 `animation: none`은 여전히 이긴다 — 그 블록은
  `@layer components` **밖**이라 레이어 안의 어떤 특이도보다 우선한다.
- 검증은 눈이 아니라 측정으로 했다. 4개 대사 × 대기/비대기 8가지 상태에서 카드
  높이와 `#compare`의 문서 좌표를 재서, 모바일 **299px 고정 · 시프트 0px**,
  데스크톱 266px 고정을 확인했다(고치기 전 89px).
- 버전 `1.0.1`.

### 1-21. 모바일 줄바꿈 — 산문의 `\n`은 풀고, 자막의 `\n`은 지킨다 (2026-08-04)

같은 리포트의 두 번째 항목: **"문장 줄이 깨진다."** 375px 실측으로 **14곳**이
의도한 줄 수를 넘겼다. 대표적으로 히어로 h1이 `전문 자막가의 규칙을 / 배운 /
AI 자막 번역` — '배운' 한 어절이 혼자 한 줄을 차지했다.

원인은 두 겹이었다.

1. **랜딩에 미디어 쿼리가 하나도 없었다.** `clamp()`만으로 버텼는데, 하한이
   데스크톱 감각으로 잡혀 있었다(`.lp-h1`은 `clamp(38px, 5.4vw, 58px)` — 375px
   에서 하한 38px에 붙은 채 폭만 모자랐다).
2. **카피에 데스크톱 폭 기준의 `\n`이 박혀 있었다.** 그 줄이 좁은 화면에서 다시
   접히면서 고아 줄이 생겼다.

**핵심 판단 — `\n`을 두 종류로 나눴다.** 그냥 전부 `whitespace-normal`로 바꾸면
안 된다. 랜딩에 있는 `\n`의 절반은 **자막 그 자체**이기 때문이다:

| | `\n`의 정체 | 처리 |
|---|---|---|
| 산문 (헤딩·본문·설명) | 데스크톱 폭에 맞춘 **조판 지시** | 640px 아래에서 공백으로 풀고 `text-wrap: balance`에 맡긴다 |
| 자막 예시 (`.lp-hero-*`, `.lp-line`) | 우리가 파는 **결과물의 줄 나눔** | 그대로 둔다. 대신 글자·패딩을 줄여 그 줄 수가 유지되게 한다 |

두 번째 줄이 요점이다. 자막에서 줄 수는 장식이 아니라 내용이고("2줄 상한",
§1-19), 예시가 3줄로 접히면 랜딩이 파는 문구가 그 자리에서 거짓이 된다. 그래서
자막 쪽은 줄바꿈을 건드리는 대신 **폭을 양보했다** — 히어로 카드 좌우 패딩
40px → 20px, ko 24px → 18px.

- 코드에서 둘을 가르는 표식은 클래스 순서다. 산문은
  `break-keep whitespace-pre-line`, 자막은 `whitespace-pre-line break-keep`으로
  이미 갈려 있었다(우연이지만 일관됐다). 그대로 경계로 썼다.
- **미디어 쿼리 조건은 `max-width: 640px`이 아니라 Tailwind `sm:`의 정확한
  여집합(`not all and (min-width: 40rem)`)이다.** `max-width: 640px`은 640px에서
  `sm:`과 **둘 다 참**이라 "모바일 글자 크기 + 데스크톱 줄바꿈"이 1px 폭으로
  생긴다. `39.99rem`으로 피하면 이번엔 그 사이가 어디에도 안 걸리는 틈이 된다.
  639px/640px 두 폭에서 실측해 확인했다.
- **미디어 쿼리는 `@layer components` 안에 뒀다.** 밖에 두면 Tailwind 유틸리티까지
  이겨서, 폭에 따라 JSX에 적힌 유틸리티가 조용히 무시된다. 반대로 히어로 카드
  패딩과 nav 링크 숨김은 유틸리티가 레이어를 이기므로 JSX에 있어야 한다 —
  **어느 쪽이 이기는지가 코드 위치를 정한다.**
- `word-break: keep-all` + `text-wrap: balance`는 JSX마다 붙이지 않고 네 헤딩
  클래스에 한 번 뒀다. 새 헤딩이 생겨도 따라온다.
- 남은 예외 둘은 의도한 것이다. `.lp-h2-dark`의 `15초.`는 `<br>`로 만든 강조
  줄이고, 영문 **원본** 자막(`.lp-hero-src`)이 좁은 화면에서 한 줄 더 접히는 건
  실제 자막 재생과 같은 동작이라 그대로 둔다(우리 결과물은 ko 쪽이다).
- 측정: 자막 줄 수 초과 **4곳 → 0곳**, 고아 줄 **10곳 → 0곳**(위 의도된 1곳
  제외), 가로 오버플로 없음. 히어로 카드는 245px로 줄었고 시프트는 여전히 0px.
- 버전 `1.0.2`.

#### 뒤집힘 — 산문의 `\n`도 지킨다, 대신 글자를 줄인다 (2026-08-04)

위 표의 **첫 줄이 뒤집혔다.** 640px 아래에서 `\n`을 푸는 방식은 두 가지를
놓쳤다:

1. **폰에서는 손으로 잡은 문장 리듬이 통째로 사라진다.** 조판 지시를 "데스크톱
   전용 장식"으로 본 게 전제였는데, 실제로는 카피를 쓸 때 의도한 호흡이다.
2. **640px~데스크톱 사이는 여전히 깨진다.** 그 구간에서는 `\n`이 살아 있는 채로
   그 줄이 또 접힌다. 스위치가 2단이라 그 사이를 덮지 못한다. 브레이크포인트를
   더 넣어도 문제가 자리만 옮긴다 — 폭은 연속이고 스위치는 이산이다.

**지금 방식: 줄바꿈을 풀지 않고 글자 크기를 줄인다.** 한글 글자폭이 대략 1em
이라, 한 줄을 통째로 넣는 데 필요한 크기는 `가용 폭 ÷ 그 줄의 폭(em)`이다.

- `app/utils/fitText.ts`의 `fitVars()`가 카피에서 **가장 긴 줄의 폭**을 재서
  (한글·CJK 1em, 라틴·공백·부호 0.5em) `--fit`으로 넘긴다.
- `globals.css`의 `.lp-fit`이 나눗셈을 한다:
  `clamp(--fit-min, 100cqw * --fit-scale / --fit, --fit-max)`.
  `100cqw`는 가장 가까운 `.lp-fit-ctx`(그 텍스트가 실제로 쓸 수 있는 폭)다 —
  컨테이너가 없으면 뷰포트로 떨어지므로 안 붙여도 망가지진 않는다.
- **하한(`--fit-min`)에 닿으면 거기서 멈추고 브라우저 줄바꿈에 넘긴다.** 못 읽는
  크기까지 갈 이유는 없다. 그때도 `keep-all` + `balance`가 강제 줄바꿈 구간마다
  따로 걸린다.
- 하한 고르는 법이 이 방식의 유일한 함정이다. **접힐 게 확실한 요소는 하한을
  원래 크기 가까이 올린다** — 접히는데 작아지기까지 하면 순손해다. 한 줄이
  30em을 넘는 산문(히어로 부제·섹션 도입부·벤토 본문)이 그 경우라 하한을
  13.5~16px로 올렸고, 줄이 짧아 끝까지 버틸 수 있는 값(CPS 카드의 '하는 일')만
  12.5px로 낮게 뒀다.
- 모바일 미디어 쿼리의 헤딩 크기 지정에는 `:not(.lp-fit)`을 붙였다. 안 붙이면
  `.lp-fit`의 계산이 모바일에서만 조용히 무효가 된다.
- **데모 스테퍼 설명(`.lp-demo-step-desc`)만 이 장치를 안 쓴다.** 열 폭이 290px
  남짓이라 34em짜리 줄이 들어가는 크기가 아예 없다 — 하한까지 작아지고도 결국
  접히므로, 그냥 흘린다. 이게 "폭이 근본적으로 모자란" 경우의 처리다.
- 측정(375 / 640 / 820 / 1280px, 가로 오버플로 0):

  | | 375px | 640px | 820px | 1280px |
  |---|---|---|---|---|
  | h1 (2줄) | 24.0px ✓ | 34.8px ✓ | 44.5px ✓ | 58px ✓ |
  | features h2 (2줄) | 25.2px ✓ | 40px ✓ | 40px ✓ | 40px ✓ |
  | final h2 (2줄) | 21.0px ✓ | 35.9px ✓ | 44px ✓ | 44px ✓ |
  | 속도 본문 (3줄) | 13.0px ✓ | 16px ✓ | 13.2px ✓ | 15.5px ✓ |
  | CPS '하는 일' (2줄) | 13.4px ✓ | ✓ | ✓ | ✓ |
  | 히어로 부제 (2줄) | 16px **3줄** | ✓ | ✓ | ✓ |
  | CPS 도입부 (3줄) | 15.5px **5줄** | ✓ | ✓ | ✓ |

  375px에서 접히는 셋은 한 줄이 30em을 넘는 것들이다 — 읽을 수 있는 크기로
  그 줄을 넣을 방법이 없어 하한에서 넘겼다. **의도된 폴백이지 미달이 아니다.**
- 자막 예시 쪽(표의 둘째 줄)은 그대로다. 거기 `\n`은 여전히 내용이다.
- 버전 `1.3.0`.

### 1-22. 업로드 input에서 `accept`를 뗐다 — 폰에서 자막을 못 고르던 원인 (2026-08-04)

리포트 네 번째: **"폰에서는 srt 파일 첨부가 안 된다."** 드롭존을 눌러 파일 앱이
열리긴 하는데 **모든 파일이 회색**이라 아무것도 고를 수 없었다.

범인은 `<input type='file' accept='.srt,.vtt,.smi,.sami,.ass,.ssa'>`였다. iOS는
`accept`의 확장자를 그대로 쓰지 않고 **UTI로 변환해서** 건다. `.srt`·`.smi`·
`.ass`는 시스템에 등록된 UTI가 없어서 어느 파일도 조건을 만족하지 못한다 —
필터가 아니라 **차단**이 된다. 데스크톱에서만 테스트하면 절대 안 보인다.

**`accept`를 없애는 쪽을 골랐다.** MIME을 섞어 넣는 우회(`text/plain` 등)도
있지만, iOS에서 `.srt`가 어떤 타입으로 잡히는지는 파일 출처마다 다르다 —
확실히 고쳐지는 게 아니라 **덜 자주 깨지는** 상태가 될 뿐이다.

- **거르는 일은 원래 `accept`의 몫이 아니었다.** `inspectUpload`가 확장자 →
  파싱 → 타이밍 → 크기 순으로 이미 거절하고(§거절 4경로는 `useWizard.test.ts`가
  고정), 이유는 드롭존 옆에 뜬다. `accept`는 피커를 회색으로 칠해 주는 편의였을
  뿐이고, 그 편의의 대가가 "모바일에서 제품을 못 쓴다"였다.
- 잃는 것: 데스크톱 피커에서 무관한 파일이 이제 선택 가능해 보인다. 고르면
  같은 자리에 같은 문구로 거절된다.
- **회귀 테스트를 붙였다** — `useWizard.test.ts`가 `UploadStep.tsx` 소스를 읽어
  file input에 `accept=`가 없는지 본다. "지원 포맷을 미리 걸러 주자"는 직관이
  워낙 자연스러워서 언젠가 반드시 다시 붙는데, 그때 데스크톱에서는 아무 증상도
  안 보이기 때문이다. 테스트가 실제로 깨지는지는 `accept`를 도로 넣어 확인했다.
- 배포 후 관찰 지점: 이미 붙어 있는 `upload_rejected` 이벤트(`reason`,
  `format`). `invalidFile` 비율이 튀면 피커가 너무 열린 것이다.
- 버전 `1.0.3`.

### 1-23. "이용방법" 섹션 — 파이프라인이 아니라 사용자가 누르는 4단계 (2026-08-04)

베타 배포 첫날 리포트 다섯 번째: **"이용방법 안내가 필요하다."** 랜딩엔 이미
"속도" 섹션에 4단계가 있었지만(`L.speed.steps`), 그건 "15초 동안 시스템이
자동으로 하는 일"을 파는 문구였다 — 방문자가 실제로 무엇을 입력하고 무엇을
고르는지는 안 나와 있었다.

`#how` 섹션을 새로 넣었다. 4단계는 실제 화면 흐름을 그대로 옮긴 것이다:

1. 업로드(`UploadStep`) — 파일 + 콘텐츠 유형(영화·드라마 / 예능·유튜브 /
   강연·토크쇼)
2. 작품 확인(`WorkPickStep`) — 영화·드라마는 TMDB 자동 인식 후보를 확인,
   그 외는 유형·톤을 직접 입력
3. 품질 선택(`TranslateSettingsStep`) — 라이트/프로 중 골라 시작
4. 다운로드(`DoneStep`) — 원본 형식(SRT·VTT는 그대로, ASS·SMI는 SRT)이
   우선이고 SRT는 항상 대안으로 뜬다

- **"속도" 섹션은 그대로 뒀다.** 같은 파이프라인이지만 파는 각도가 다르다 —
  속도는 "시스템이 자동으로 한다"(신뢰), 이용방법은 "당신이 누르는 건 이게
  전부다"(진입장벽 해소). 겹치는 정보가 아니라 관점이 다른 정보라 중복 삭제
  대상이 아니다.
- 카드 레이아웃은 `.lp-step`(속도 섹션, 다크 배경 전용 색상)을 재사용하지
  않고 `.lp-how-*`를 새로 뒀다 — `#how`는 밝은 배경이고, `.lp-step`의
  `border-on-dark-strong`·`accent` 글자색은 밝은 배경에서 안 보인다.
  (2026-08-04 개정: 아래 §1-25에서 `.lp-how-*` 4장 카드는 조작 가능한
  데모(`.lp-demo-*`)로 교체됐다. 4단계 문구 자체는 그대로 살아 있다.)
- 카피가 단정하는 것들은 화면 코드로 확인했다(추측 아님) — `WorkPickStep.tsx`가
  `contentType==='movie'`만 TMDB 후보를, 나머지는 `otherType`+`toneText` 자유
  입력을 받는 것, `DoneStep.tsx`가 `result.downloads`의 첫 항목(원본 형식)을
  기본으로 걸고 나머지를 대안 버튼으로 두는 것.
- nav에 `이용 방법` 링크를 `#compare`보다 앞에 뒀다 — 방문자가 "이게 뭔지"보다
  "어떻게 쓰는지"를 먼저 궁금해할 순서라고 판단했다.
- 버전 `1.1.0`.

### 1-24. "라이트 vs 프로" 비교 — `COPY.plans` 하나를 랜딩과 설정 화면이 같이 읽는다 (2026-08-04)

베타 배포 후 리포트 다섯 번째: **"라이트랑 프로 차이가 궁금하다."** 설정 화면
카드에 한 줄 설명은 있었지만(`liteDesc`/`proDesc`), 소요 시간·크레딧 차감처럼
결정에 필요한 수치는 어디에도 없었다.

**`COPY.plans` 하나를 새로 만들어 랜딩과 설정 화면 둘 다 이걸 읽게 했다** —
복사해 두 곳에 붙였다가 한쪽만 고쳐지는 사고를 구조적으로 막는다.
`simpleCopy.test.ts`에 두 소비처가 실제로 `COPY.plans`를 참조하는지(문자열
없이 값만 베끼지 않았는지) 소스를 읽어 확인하는 테스트를 추가했다.

- **프로의 시간은 처음 파는 숫자다.** 라이트는 랜딩 "속도" 섹션과 같은 근거를
  재사용했고(461블록 13.4초 · 1,124블록 14.8초 → "약 15초"), 프로는
  2026-07-31 장편 타임아웃 실측(1,124블록, `PRO_THINKING_LEVEL=HIGH` ·
  `PRO_CHUNK_SIZE=250` — 프로덕션 설정 그대로)의 총 161.4초를 "약 2분 41초"로
  옮겼다. 두 값 모두 `simpleCopy.test.ts`가 `timeNote`에 적힌 실측 초에서
  재도출해 대조한다 — 손으로 고치다 반올림을 틀리면 테스트가 잡는다.
- **크레딧 차감 문구는 "1편" 고정이다.** §1-4(요청이 아니라 파일 단위 차감)에
  따라 청크 수와 무관하게 항상 1편이라, 숫자를 계산해 보여줄 필요가 없다.
- **랜딩 카드의 값 행은 `.lp-spec`(CPS 섹션과 같은 좌우 배치)을 재사용하지

### 1-25. "이용 방법"을 읽는 4단계에서 만지는 4단계로 (2026-08-04)

§1-23이 넣은 4장 카드는 정확했지만 **읽어야 알 수 있는 정보**였다. 진입장벽을
없애려고 만든 섹션인데, 방문자는 그 장벽이 낮다는 걸 여전히 글로만 들었다.

카드를 **직접 통과하는 데모**(`HowItWorksDemo`)로 바꿨다. 왼쪽은 4단계 스테퍼,
오른쪽은 실제로 만지는 무대다: 파일 칩을 드롭존에 **끌어다 놓으면** 작품 확인
→ 품질 선택 → 진행 바 → 완성된 자막·다운로드 순으로 넘어간다.

- **단계는 자동으로 넘어가지 않는다.** 사용자의 액션만이 다음 단계를 연다 —
  자동 재생하면 그냥 애니메이션이지 데모가 아니다. 유일한 자동 모션은 드롭존
  쪽으로 한 번씩 미는 파일 칩의 넛지뿐이다(안 그러면 끌 수 있는 줄 모른다).
- **드래그는 HTML5 DnD가 아니라 Pointer Events로 만들었다.** `dragstart`/`drop`은
  터치에서 아예 발화하지 않아 모바일에서 데모가 죽는다. 포인터 이벤트는
  마우스·터치·펜을 같은 코드로 받는다. `touch-action: none`이 없으면 끄는 동안
  페이지가 같이 스크롤되므로 칩에 걸어 뒀다.
- **드래그·탭·키보드 세 경로가 같은 곳에 도착한다.** 칩은 `<button>`이라 Enter로도
  넘어간다. 드래그 뒤에 따라오는 꼬리 `click`만 `movedRef`로 걸러내되, 한 틱 뒤에
  플래그를 되돌린다 — 안 그러면 다음 키보드 입력이 스스로 막힌다.
- **안내 문구는 기기에 따라 바뀐다** — `(pointer: coarse)`면 "눌러서 올려보세요".
  안내와 실제로 되는 동작이 어긋나면 데모가 고장 난 것처럼 보인다.
  미디어 쿼리는 `useEffect`+`setState`가 아니라 `useSyncExternalStore`로 읽는다
  (첫 렌더가 틀린 값으로 한 번 그려지지 않고, 도중에 설정을 바꿔도 따라간다).
- **무대 높이는 348px로 고정했다.** 단계마다 내용이 통째로 갈리는데 높이가 따라
  변하면 아래 섹션이 밀려 올라온다 — §1-20이 히어로 카드에서 이미 겪은 것.
- **결과 대사는 비교 섹션의 ZAMAK 항목에서 직접 읽는다**(`compare.engines`).
  데모용 복사본을 두면 같은 페이지가 두 개의 "우리 번역"을 팔고 CPS 숫자가
  조용히 갈라진다. 품질 카드의 이름·시간도 같은 이유로 `COPY.plans`에서 읽는다.
- **4단계 설명은 지우지 않고 스테퍼로 옮겼다.** 데모를 안 만지는 방문자와
  크롤러에게는 그 글이 이 섹션의 전부다.
- 모션 최소화 설정이면 넛지·패널 등장·진행 바가 전부 꺼지고, 품질 선택이 곧장
  결과로 간다(진행 단계에 아예 들르지 않는다).
- 버전 `1.3.0`.

### 1-26. CPS 섹션의 근거 각주 — "넷플릭스 규칙"이라고 단정하지 않은 이유 (2026-08-04)

CPS 섹션에 기준의 출처를 각주로 달았다. 처음 요청은 **"넷플릭스 규칙 적용"**
이었는데, 그대로 쓰면 탭 하나에서 거짓이 된다:

| 프로필 | target | hardMax | Netflix 성인 기준(≤12 CPS) |
|---|---|---|---|
| 영화·드라마 | 10 | 12 | 일치 |
| 예능·유튜브 | 8 | 11 | 더 엄격 |
| 강연·토크쇼 | 12 | **15** | **초과** |

그래서 "따른다"가 아니라 **"바탕으로, 영상 종류에 맞게 조정한다"**로 적었다.
근거는 `docs/standards/netflix-korean-gap-review.md` I.15와 `languages.ts`의
`shapes`. 속도 섹션의 실측 각주(`speed.note`)와 같은 자리·같은 크기에 뒀다 —
파는 숫자 바로 밑에 그 숫자의 근거를 붙이는 규칙을 페이지에서 반복한다.

### 1-27. 피드백 리워드 이벤트 — 인앱 자동, 카톡·이메일 수동 (2026-08-04)

인앱 피드백(별점/후속설문)과 카톡·이메일 문의를 서로 다른 지급 방식으로
갈랐다. **이유**: 인앱은 이미 `auth.uid()`로 유저가 특정되지만, 카톡·이메일은
앱 밖 채널이라 "누구에게 줄지"를 코드가 알 방법이 없다. 문의자가 가입
이메일을 남기는 것으로 대신하고, 대표가 `supabase/comp-credit.sql`로 수동
지급한다 — 이벤트 규모(베타)에서는 admin UI를 새로 만드는 비용이 안 맞는다.

두 경로 모두 새 `event_grants(user_id, event_code)` 테이블(`0012`)로 1인
1회를 보장한다. 이벤트 하나에 종속된 표가 아니라 범용 지급 이력으로
설계했다 — 다음 이벤트도 `event_code`만 새로 쓰면 재사용된다.

기한은 두지 않았다(2026-08-04 대표 결정) — 당분간 상시로 운영하다 필요할 때
접는다. 상세 설계는
`docs/superpowers/specs/2026-08-04-feedback-reward-event-design.md`.

### 2-1. 타임코드는 코드가 관리하고 AI는 대사만 다룬다

모델에는 **`[번호]` 표식 + 대사만** 보낸다(타임스탬프는 토큰 낭비). 응답은 **표식으로
대조해** 원본 타임코드와 재결합한다(`reassembleTranslatedChunk`).

AI가 자막을 합치거나 빠뜨려도 이후 자막이 밀리는 일이 ~~구조적으로 불가능하다~~
**⚠️ 2026-07-22 정정: 불가능하지 않다.** 타임코드의 출처가 항상 원본이라는 건
맞지만, 그건 "타임코드가 원본과 다른 값이 되진 않는다"는 보장이지 "타임코드와
대사의 짝이 맞는다"는 보장이 아니다. 아래 참조. API 추가 호출은 0.

**와이어 포맷: 줄마다 `[번호] 대사` — 2026-07-25 두 번 바뀜.**

**(1) 맨숫자 → 대괄호.** 과거엔 번호를 맨숫자로 보내고(`115\n8.`), 번호 인정 조건
3개(원본에 있던 번호 / 아직 미사용 / 단조 증가)로 `1999` 같은 숫자 대사를 번호로
오인하지 않게 방어했다. **이 방어가 실사용에서 뚫렸다**: 이탈리아 영화 샘플에
등장인물이 숫자를 세는 장면이 있어 대사가 `"8." "9." "10." …`처럼 순수 숫자였고,
청크(150블록)의 시퀀스 범위(예: 1~140) 안에 있는 값이라 3개 조건을 전부 통과 —
블록번호로 오인돼 본문에서 버려졌다. **실측(1480블록 샘플, 첫 청크 140블록):
마침표만 뗀 완벽한 번역에도 26개 블록이 유실.** 청크가 클수록(150→300) 오염이
증가하는 것도 확인됨(범위가 넓어져 낮은 대사 숫자를 더 많이 삼킴).

대괄호는 유효한 자막 텍스트가 아니므로 대사가 어떤 숫자든 표식과 절대 안 겹친다 —
조건 3개짜리 휴리스틱이 통째로 불필요해졌다. 이 김에 **단조 증가 요구도 제거**했다:
그 요구는 맨숫자의 모호함을 피하려고 있었을 뿐이라, 모호함이 사라지면 마커는 순서
상관없이 시작할 수 있다 — 부수 효과로 "모델이 번호를 역순으로 내보내면 직전 블록에
조용히 덧붙는" 버그(과거 TODO 9번, `HANDOFF.md`)도 같이 해결됐다.

**(2) 표식 전용 줄 → 줄마다 표식(현재).** (1)의 포맷은 표식이 본문 위 **독립된 줄**
이었다(`[82]\nBeh, insomma...`). 그 줄은 번역할 내용이 없는 **순수 구조 전용 줄**이라
모델이 이따금 그냥 안 찍었고, 그러면 그 텍스트는 자기 정체를 증명할 근거가 사라져
"그때 열려 있던 블록"에 흡수됐다. 흡수된 텍스트 앞뒤의 빈 줄이 본문 안에 들어가면서,
SRT로 다시 쓸 때 **그 블록이 두 조각으로 갈라져 번호·타임코드 없는 유령 블록이
생겼다**(400블록 실행에서 1건, 두 스타일에서 각각 다른 블록에 재현 — 파일 블록 수가
400→401이 되고 원래 블록은 미번역으로 폴백).

**근본 고침**: 표식을 본문과 **같은 줄에** 붙이고 **모든 줄에** 반복한다.
```
[81] Lui fa tutto quello che dici tu.
[14] 비용 생각하면 심장이 쿵 내려앉지만
[14] 그만한 가치가 있었어요
```
건너뛸 수 있는 구조 전용 줄이 **존재 자체를 안 하므로** 정체성이 텍스트와 함께
이동한다. 두 줄 자막은 같은 번호를 두 번 쓰는 것으로 자연히 표현된다. 파서
(`indexTranslatedBodies`)는 빈 부분을 걸러 join하므로 **본문에 빈 줄이 들어가는 것이
구조적으로 불가능** — 유령 블록 실패 모드가 원천 차단된다. 관용 처리 4가지: 표식만
있는 옛 포맷(하위호환), 표식 없는 바로 아랫줄(=이어지는 줄로 붙임), 코드펜스/서문/
에코된 타임스탬프(버림), **대괄호 안 숫자 뒤 잡텍스트**(`[177 me]` — 번호만 취하고
잡텍스트는 버림; 2026-07-25·07-28 하네스에서 재관측). **단, 빈 줄 뒤에 표식 없이
나오는 텍스트는 버린다** — 그건
표식이 누락된 고아이고 어느 블록 소속인지 근거가 없다. 위 블록에 갖다 붙이는 추측이
바로 오염의 원인이었으므로, 버리고 해당 블록은 정직하게 원문 폴백 + `unmatched`로
집계한다.

*실측(같은 400블록, 실모델 2회 실행)*: 정렬 실패 meaning 1건·cinematic 1건 → **양쪽
0건**, 유령 블록 0, 블록 수 정확히 400, 두 줄 자막 40·33개 정상 생성.

규칙 프롬프트(`translation_rules_ko.txt` / `_en.txt`)에도 "모든 출력 줄은
`[번호] 번역문` 형식", "번호 없는 줄은 버려진다", "두 줄로 나눌 땐 같은 번호를 두 번",
"대사가 숫자여도 번역문 자리에 대괄호 없이"를 명시해 이중 방어. 부수 수정: 블록 수
안내(`이 청크의 자막 블록 수: N개`)도 맨숫자 줄을 세던 버그(순수 숫자 본문이 있으면
과대 계산)를 고쳐 `parseSrtBlocks(...).length`로 구조 기반 카운트를 쓰게 했다.

**(3) 같은 번호 두 줄 → 한 번호 한 줄 + `|` 줄바꿈 (현재) — 2026-07-28.**
(2)의 "두 줄 자막은 같은 번호를 두 번"이 **블록 병합에 합법적 위장**을 제공했다.
269+270을 하나로 합쳐 번역한 출력은
```
[269] 이제 의회에서 임신 중절 합법화
[269] 법안 통과를 눈앞에 두고 있으니까요
```
인데, 이건 규칙대로 긴 줄을 쪼갠 정상 출력과 **글자 하나 다르지 않다.** 규칙이
"블록을 합치지 마"라고 금지한 행동을, 같은 규칙집의 줄바꿈 조항이 적법한 모양으로
표현할 수 있게 해준 셈이다. 검출도 불가능했다 — 마커 개수가 맞아버리니까.

**고침**: 한 번호는 정확히 한 줄. 두 줄로 보여야 하면 그 한 줄 안에 `|`를 넣고,
재조립(`indexTranslatedBodies`)이 `\n`으로 바꾼다. 같은 번호가 두 번 나오면 이제
**무조건 오류**이므로 블록 수 대조가 병합을 즉시 잡는다. 관용 처리는 유지 — 옛
포맷(같은 마커 반복)도 그대로 파싱되므로 하위호환은 공짜.

*실측(drama-episode.srt 461블록, flash LOW)*: 기존 포맷+긴 규칙 정렬실패 4건(전부
어순 역전에 의한 병합) → **새 포맷+lean 규칙 0건, thinking 0토큰.** 같은 파일
HIGH(정렬실패 0)가 $0.3908인데 새 조합은 $0.0770 — **5.1배 저렴하고 안정성 동일**
(`docs/tuning/experiment-log.md` 2026-07-28).

**왜 규칙을 줄이는 게 안정성을 올렸나**: 긴 규칙에서 LOW는 사고 1,854토큰을 쓰고도
실패했고, lean에서는 **사고 0으로 무결**했다. 규칙 준수에 추론이 필요했던 게 아니라
**지킬 규칙이 많아서** 추론이 필요했던 것이다. 규칙집은 3,237B→834B(ko)로 줄었고,
잘라낸 건 대부분 **코드가 이미 강제하는 항목**(2줄 상한·문장부호 — `enforceTextRules`)
이다. 코드가 소유한 규칙을 모델에게도 시키면 주의력만 갉아먹는다 — 타임코드에
적용한 원리(§2-1)를 규칙에도 적용한 것.

**이 변경이 고치지 못하는 것**: 모델이 스스로 자막 하나를 둘로 쪼개
"정상적으로 재번호"하는 별개의 실패 모드(2026-07-22 발견, B=2000 베타에서
재현) — 그 경우 밀린 번호도 표식 형태(`[N]`)로 나오고 원본에 실재·미사용이므로
여전히 통과한다. 대괄호는 "번호를 대사와 구분"하는 문제만 풀지, "모델이 잘못된
번호를 마커로 내보내는" 문제는 못 푼다. 재현 예시와 탐지·복구 방안은
[`tuning/chunk-size-model.md`](tuning/chunk-size-model.md) §8, 임시 완화책(B=100,
현재값)은 2-3 참조.

*실측 정렬 실패율 0.5~0.65%.* ⚠️ 이 수치는 "번호가 아예 안 붙은" 실패만 센다.
위 재번호 드리프트는 번호가 붙긴 붙으므로 **이 수치에 안 잡힌다** — 실제 오염률은
더 높을 수 있다.

### 2-2. 기본 경로는 청크당 모델 호출 1회 — 검증·재시도 없음

과거 `translationService`가 블록 수 검증 실패 시 200블록 청크를 개별 블록 200번
재귀 번역 + 3회 재시도까지 해서 **20분/5,000원 사고**를 냈다. 서버 쪽(`translationService`)은
지금도 청크당 1회 호출 + raw 반환이 기본이다 — 이 반작용 자체는 안 뒤집혔다.

**뒤집힘(2026-07-26): 클라이언트에 "상한 있는" 재시도를 도입.** 재시도가 전혀 없던
반작용이 반대편 극단이었다 — 일시적 네트워크 블립 한 번에도 청크를 영구 원문 폴백시켰다.
지금은 `app/lib/client/chunkRetry.ts`가 에러를 분류(`app/lib/translationErrors.ts`)해서
`transient`/`align`만 1회 재시도, `oversize`만 반으로 쪼개 1회, `quota`/`auth`는 파일
전체를 즉시 원문 폴백으로 돌린다(전역 중단이지 `throw`가 아니다 — 파일은 항상 완성됨).
재시도 예산은 파일 전체에 `max(3, ceil(totalChunks*0.2))`로 상한을 걸어서, 과거 사고처럼
청크 하나가 수백 번 재귀하는 게 **구조적으로 불가능**하다 — 최악의 비용 증가가 +20%로
고정된다. §9.6 참조.

검증·재시도·재귀 로직은 삭제하지 않고 `TRANSLATION_STRICT_MODE=true`(기본 off) 뒤에
보존했다.

**두 번째 뒤집힘(2026-07-28): "실패하면 원문 유지"를 기본값에서 최후 수단으로 강등.**
위 두 반작용은 모두 **청크 단위 재시도**만 다뤘는데, 실무에서 원문이 남는 대부분은
청크가 **성공한** 경우다 — 모델이 두 줄을 합치거나 한 줄을 건너뛰면 `translateOnce`가
`unmatched > 0`인 채로 성공을 반환하고, `chunkRetry`는 그걸 볼 기회조차 없다.
그래서 재시도 예산을 올리는 대응은 이 경로에 대해 **효과가 정확히 0**이고 비용만 는다.

지금은 본 패스가 끝난 뒤 `app/lib/client/recoverySweep.ts`가 원문으로 남은 블록만
시퀀스 번호로 수거해 **새 청크로 재포장**하고 다시 보낸다. 재포장이 이 결정의 전부다:
30개 청크에 흩어진 40줄을 청크째 다시 돌리면 30회지만, 모아서 묶으면 1회다. 비용이
"실패한 블록 수"를 따라가지 "그게 어느 청크에 있었나"를 따라가지 않는다.

**옛 사고와의 차이 — 블록 단위 경로가 없다.** 사고를 만든 건 재시도 자체가 아니라
"블록 수가 안 맞으면 블록 하나씩 재귀 번역"이었다(청크 1개 → 200회). 재포장이 있으면
그 경로는 필요하지도 않다: 잔여 20블록은 20회가 아니라 **1회**다. 여기에 최대 2라운드,
`max(2, ceil(청크수*0.5))` 호출 상한, 그리고 **한 라운드가 아무것도 못 건지면 즉시 중단**을
겹쳐서, §9.6의 +20%와 합쳐도 파일당 최악 비용이 본 패스의 **~1.7배로 고정**된다.

시퀀스 번호는 그대로 실려가므로 재조립이 각 번역을 원래 타임코드에 되붙인다 —
재포장은 요청 안에서 블록을 옮기지 타임코드를 옮기지 않는다(불변식 2 유지).
`translation-pipeline.md` §9.65 참조.

부수 효과로 화면 보고가 **줄 단위**로 바뀌었다. sweep이 블록 단위로 동작하니
"구간 2개 실패"는 사용자가 받지 않는 중간 상태를 설명하게 된다 — `failedChunks`는
진단용으로만 남기고, 화면은 sweep까지 끝난 뒤 남은 줄 수(`fallbackBlocks`)만 말한다.

### 2-3. ~~청크 크기 B=125, 동시성 K=14~~ ~~→ B=125(선택), K=16(유도)~~ ~~→ B·K 모두 근거 없는 동결값~~ ~~→ B=2000(청킹 없음)~~ ~~→ B=500 (2026-07-22 재역전)~~ ~~→ B=200~~ ~~→ B=150(문서화 안 됨)~~ → **B=100 (현재)**

유도 전체는 [`tuning/chunk-size-model.md`](tuning/chunk-size-model.md) §5.
**이 항목은 하루에 세 번 바뀌었으므로, 새로 유도를 시도하기 전에 반드시 그 절을 읽을 것.**

**결론: B는 계산으로 정할 수 없다.** 유도로 나오는 건 상한 두 개(출력 상한 → B ≤ 3,276,
타임아웃 → B ≤ 4,097)뿐이고 **둘 다 현재값의 16배 이상 떨어져 있다.** 그 안쪽은 전부
끝점 없는 매끄러운 트레이드다.

무너진 유도들:

1. ~~"클수록 싸다"~~ — `th=0` 실측으로 근거 소멸. 전 구간 비용차 6.5%.
2. ~~"`⌈1500/14⌉ = 108` 이상"~~ — **`K=14`에 근거가 없었다.** `git log -S` 추적 결과
   최초 커밋 `fb952ea`에서 주석 한 줄과 함께 물려받은 값이고, "K는 배분 선택"이라는
   서술은 14를 고른 이유가 아니라 14가 아무것도 위반하지 않는다는 **사후 확인**이었다.
   B의 하한이 그 K에서 나왔으니 **엄밀해 보이던 B=125가 임의값 위에 서 있었다.**
3. ~~"125엔 정렬 실패율 실측 기준선이 있다"~~ — **오독이었다.** 3회 측정 중 0.65%·0.22%는
   **B=200**에서 나왔고, 0.07%만 B=125인데 그건 프롬프트 개정과 같은 실행이라 교란됐다.
4. ~~1웨이브 규칙 (`K ≥ ⌈상한/B⌉`)~~ — **대표 결정으로 폐기.** 2웨이브면 시간이 2배지만
   애초에 1분도 안 걸리는 작업이라 무의미하고, 이 규칙은 K를 B에 묶는 일밖에 안 했다.

**추가로 정정된 사실**: "작은 B가 손실 반경을 줄인다"는 오랜 서술이 **틀렸다.**
기대 미번역 블록 = `p·m·B = p·⌈N/B⌉·B ≈ p·N`으로 **B가 소거된다.** 작은 B는 평균이
아니라 분산을 줄일 뿐이다("가끔 크게" → "자주 조금씩").

**실제로 B를 가르는 두 양은 둘 다 미측정이고 방향이 반대다**: 정렬 실패율 f(B)는
방향 불명이고, 인물 말투 일관성은 **큰 B를 선호**한다(청크가 서로를 모른 채 병렬
번역되므로 — §5-5의 `character_voice_registry`와 같은 문제, 이후 §2-9에서 글로사리·
존대관계 프리패스로 청크 크기와 무관하게 해결됨).

**결정: `B = 2000` = 크레딧 상한, 즉 청킹 없음** (2026-07-22 대표 결정). 내부 최적점이
없으니 **자기 근거가 있는 끝점**을 택했다 — 가장 싸고(`$0.3345`), 모델이 영화 전체를
문맥으로 보므로 위의 말투 일관성 축에서 최선이다.

대가를 명시해둔다: ① **all-or-nothing** — 실패 시 청크 1개가 아니라 파일 전체가 원문으로
남는다(기대 손실은 그대로지만 분산이 최대). ② 진행 링이 시간 추정에만 의존한다.
③ **출력 상한 여유가 3.8% → 61%로 줄었다** — ⚠️ `t_out`이 영어 실측 16이라, 비영어
자막에서 30 근처가 되면 상한을 넘겨 **파일 전체가 잘린다.** 비영어 원어를 받기 전에
재측정 필수(§아래 "비영어 원어 커버리지" 항목과 같은 건이다).

`K=16`은 이제 무효다(`min(m,K)=1`). B를 낮추면 되살아나도록 남겼다.
`constants.test.ts`는 **출력 상한·타임아웃 두 개만** 강제한다 — 임의의 B를 꽂아
실험하는 걸 막지 않기 위해서다.

**부수 수정**: `TIMING.FLASH_BATCH_MS = 60초`가 B·N 무관한 상수였다. 청크가 여러 개일
땐 실제 진행률이 가려줬지만 청크 1개에선 링의 유일한 근거라, 상한 파일에서 **60초에
99% 찍고 87초를 더 기어가는** 상태가 됐다. 실측 생성률 기반 `estimateTranslationMs()`로
교체했다(청크 모델과 같은 파라미터를 쓰므로 재측정 시 같이 갱신). ⚠️ 이 계산은
2026-07-26에 모델별 고정값으로 다시 대체됐다 — §2-7 참조.

### 2-3-1. B=2000 폐기, B=500으로 재역전 — 2026-07-22 대표 실사용 발견

**당일 저녁 베타 테스트 중 대표가 직접 재현.** 639번 자막이 두 개로 쪼개지면서
그 뒤 모든 번호가 하나씩 밀렸다 — 위 2-1에 기록한 재번호 드리프트 그 자체다.
대표 진단: **AI 어텐션이 청크 600줄 근처부터 흐려진다.** 코드로 증명된 메커니즘은
아니고 경험적 관찰이지만, B=500에서는 재발하지 않았다.

**결정: B=2000 폐기, `SERVER_CHUNK_SIZE=500`으로 되돌린다.** 근거는 "이론상 최적"이
아니라 "실사용에서 사고가 안 났다"는 경험적 안전선이다 — §5의 계산 불가 결론과
모순되지 않는다(계산은 애초에 이 실패 모드를 다루지 못했다).

**이걸로 2-1의 조용한 오염이 고쳐진 건 아니다.** B=500도 사고가 나면 그 청크의
나머지(최대 500블록)가 여전히 밀린 채로 나가고, `matched` 카운터는 여전히
100%로 집계한다. B를 낮춘 건 **사고 확률을 낮췄다고 믿을 근거**(경험적 관찰)일
뿐, 사고를 탐지하거나 막는 코드는 아직 없다.

이전 결정의 근거였던 것들은 여전히 유효하다: thinking=0이라 비용 곡선은
평평하고(B=500도 6.5% 구간 안), 손실 반경은 청크 전체 API 실패 기준으로는
B와 무관하다. 다만 **이번 사고는 청크 전체 실패가 아니라 청크 "안에서" 부분
오염**이라 그 무관성 논증이 적용되지 않는다 — 이 오염은 평균 B/2블록에
비례하므로 B를 낮추면 실질적으로 피해가 준다(2000이면 최대 1,361블록,
500이면 최대 500블록).

`gemini-limits.md` §4 참조). 원래 측정값은 $0.2982 / $0.9203 / $0.3192였고, 배율

**결정: `SERVER_CHUNK_SIZE=100` 유지, `THINKING_LEVEL=LOW` 유지**(변경 안 함).
MEDIUM도 이번 사고를 없앴지만 비용이 LOW·B=100의 약 2.8배다 — §2-4가 이미 "MEDIUM과

**대사 품질**을 봤고 이번 건 **마커 형식 무결성**이라 다른 축이다. B를 줄이는

**주의할 점**:

  항상 0%"라는 결론은 아직 못 낸다 — 표본을 더 쌓기 전까진 잠정 채택.
  ⚠️ TODO: 이 표본 수 문제가 실제로 해소됐는지 다음에 확인할 것.
- 이건 §2-3-1·§2-3-2의 **재번호 드리프트**와는 메커니즘이 다른 **별개의 실패
  모드**다 — 둘 다 B를 줄이면 완화되지만 원인(모델이 청크 뒷부분에서 어텐션을
  잃는다 vs 모델이 인접 토큰을 마커 안에 잘못 복사한다)은 별개다.

  해당 블록으로 귀속한다(잡텍스트는 버림). `"8."`/`"1999"` 같은 순수 숫자 대사는
  대괄호가 없어 여전히 마커로 오인되지 않는다 — §2-1 (1)의 보장은 유지.
  B=100 완화는 발생 확률을 낮추는 1차 방어로 남고, 파서 흡수가 발생 시 피해를
  막는다. 실측·회귀는 `srt.test.ts`, `experiment-log.md` 2026-07-28 항목.
- K=16과의 상호작용은 `chunk-size-model.md` §5-6 참조 — 크레딧 상한 파일(2,000블록)
  기준 B=100은 `⌈2000/100⌉=20 > K=16`이라 **2웨이브**가 된다(1웨이브 규칙은 이미
  폐기돼 위반은 아님).

### 2-4. THINKING_LEVEL은 LOW — 2026-07-21 확정

`thinkingBudget: 0`은 이 모델이 무시한다(비활성화 불가). 실제로 먹는 건 `thinkingLevel`.

**MINIMAL과 LOW 모두 실사용에서 `thoughts=0`**으로 측정됐다 — 비용이 같으므로 품질이
나은 LOW를 코드 기본값으로 삼았다(`constants.ts`). env로 덮을 수 있다.

**MEDIUM과의 품질 비교를 대표가 직접 수행한 결과 유의미한 차이가 없어 LOW로 확정했다.**
MEDIUM/HIGH는 thinking 토큰을 실제로 소비해(출력 단가 = 입력의 6배, 요청마다) 비용·시간이
3~4.5배로 뛰는데 그만한 값을 못 한다. HIGH는 편당 마진이 적자였다.

**실측 원가: 1,480블록 영화 1편 ≈ 400원** (LOW, B=125, 12청크). 프롬프트를 크게 바꾸지
않는 한 이 수치가 기준이다.

⚠️ 단, `thoughts=0`은 **프롬프트 의존적**이다. 짧은 청크에 긴 지침(철학 파일)을 붙인
연기 테스트에서는 LOW인데도 `thoughts=781`이 나왔다. 프롬프트를 크게 늘리면 이 결정의
전제가 무너지므로 재측정할 것 — `th≠0`이면 청크를 크게 만들수록 유리해져 B=125의 근거도
같이 흔들린다.

### 2-4-1. Pro는 LOW도 공짜가 아니다 — MINIMAL 미지원 (2026-07-26)

§2-4의 "MINIMAL·LOW 모두 `thoughts=0`"은 **flash 실측**이었다. Pro(`gemini-3.1-pro-preview`)에
그대로 가져다 쓸 수 없다는 게 대표가 967블록 파일을 고급번역으로 돌려본 뒤 확인됐다 —
이론 원가(constants.ts 추정 ~320원)보다 실제 청구(971원)가 3배 가까이 나온 게 발단.

**MINIMAL을 아예 설정할 수 없다.** API가 pro-preview에서 `ThinkingLevel.MINIMAL`을

**LOW가 pro에서 실제로 설정 가능한 최저값**이다.

**그 LOW조차 flash처럼 안정적으로 `thoughts=0`이 아니다.** 967블록 파일(B=100, 청크 10개,

| 2 | 2,502 | 1,930 | 1,038 |

prompt 크기와 뚜렷한 상관도 안 보인다. thoughts 합계(27,845)만으로 이 파일 번역 비용의

**영향**: `constants.ts`의 `MAX_BLOCKS_PER_CREDIT` 코멘트가 인용하는 pro 원가(2,000블록
$0.49)는 flash의 `th=0`을 가져다 쓴 추정치라 이 실측과 안 맞는다 — **실제 pro 원가는 그보다
높을 가능성이 크다.** 크레딧 가격이 이 worst case를 못 넘기면 편당 적자가 날 수 있다 —
재검토가 §4 "다음" 목록에 있다.

**미결**:
- MEDIUM(현재 `PRO_THINKING_LEVEL` 코드 기본값)이 LOW보다 품질·비용 면에서 나은지 미측정
  — 지금까지는 LOW가 "MEDIUM보다 저렴할 것"이라는 가정 하에 낮은 값으로 취급돼 왔는데,
  LOW 자체가 이미 상당한 thinking을 쓰므로 그 가정도 재확인 필요.
- LOW의 들쭉날쭉함이 프롬프트 길이·내용 등 어떤 변수에 좌우되는지 미측정.
- 이 변동성이 flash에도 똑같이 있는지(§2-4 flash 실측은 200블록 표본 3개뿐이라 표본이
  작다) 재확인 여지 있음.

### 2-5. 리딩스피드(CPS) 타임코드 자동 조정 — 2026-07-25

**문제**: 한국어는 정보 밀도가 높아 영어 원문 타이밍 그대로면 번역문이 화면에 너무 빨리
지나가 못 읽는 블록이 생긴다. 목표는 **코드가 자체적으로** 이런 블록의 표시창을 넓혀
읽기 속도를 낮추는 것 — 단 자막끼리 절대 겹치지 않게.

**결정**: 재조립이 끝나 전체 파일이 순서대로 합쳐진 직후(`useTranslation`), `srt.ts`
`adjustSubtitleTiming`으로 **한 번의 전역 패스**를 돌린다.

- **임계값 3단 (2026-07-25 갱신)**: 단일 타깃(12)에서 **권장 밴드 8~10 + 하드 상한 12**로
  바꿨다.
  - `CPS_HARD_MAX`(12 = Netflix 한국어 성인물 상한): **이 값을 넘는 블록만** 손본다(위반 판정).
  - `CPS_TARGET`(10 = 밴드 위쪽 끝): 손보는 블록의 **착지 목표**. 밴드 꼭대기를 노려 gap을
    최소로 쓰면서 "권장"에 안착. 방 없으면 닿는 데까지.
  - `CPS_RECOMMENDED_MIN`(8 = 밴드 아래 끝): 목표가 10이라 그 아래로는 자동으로 안 내려간다
    (강제 로직 아님, 밴드 하한을 이름으로 박아둔 것).
  - 10~12 사이 블록은 상한 밑이라 손대지 않는다. "12를 넘으면 8~10으로 데려오고, 이미 상한
    밑이면 그대로 둔다"가 요지.
- **방향**: 필요한 만큼만, **end를 먼저 뒤로**(자막이 늦게 사라지는 게 lead-in보다 자연
  스럽다) 밀고 모자라면 **start를 앞으로** 당긴다. **창은 늘리기만 한다**(줄이지 않음).
- **겹침 불가 보장**: 앞 블록은 *조정된* end, 뒤 블록은 *원본* start를 경계로 쓰는
  비대칭 + `MIN_SUBTITLE_GAP_MS`(기본 84ms ≈ 24fps 2프레임). 이 덕에 인접 두 블록이 같은
  침묵을 이중으로 먹지 못하고, 항상 `start_{i+1} ≥ end_i + gap`. 타이밍이 깨진 블록은
  건드리지 않고 벽으로 취급해 그 방향 확장을 막는다.
- **첫 블록 backward (2026-07-25 버그픽스)**: 초기 구현은 첫 블록(및 깨진 블록 바로 뒤)의
  start를 아예 못 당겼다(`prevEnd == null` → backward 금지). 그 결과 앞이 완전히 비어있는
  첫 자막이 27.8cps로 방치됐다. `prevEnd` 초기값을 **0**으로 바꿔 첫 블록은 0초까지의 빈
  프리롤로 start를 당기게 했다. 깨진 블록 뒤는 여전히 `null`(불명 구간 침범 금지)로 보수적
  유지. 실측(1480블록)에서 "여유 있는데 미조정"이 10→2로 줄고 겹침은 0.
- **위치가 클라이언트 최종 합류 지점인 이유**: 청크 경계를 넘는 이웃 겹침까지 막으려면
  전체가 한 번에 순서대로 존재하는 유일한 지점에서 돌아야 한다.

**불변식과의 관계**: 블록 수·시퀀스·본문은 그대로 두고 타임코드만 재작성한다 → "타임코드는
코드가 소유"(§2-1)의 연장이지 위반이 아니다.

**남은 한계**: 사이 침묵을 **end 우선 그리디**로 배분해, 연속 밀집 구간에서 뒤 블록이 손해를
볼 수 있다(실측 잔여 2블록). gap 비례 분할(2패스)은 필요해지면 후속. gap이 부족하면 목표까지
못 내려가고 가능한 만큼만 조정한다(부분 개선 허용).

### 2-6. 줄바꿈 임계값(25자)과 2줄 상한 — 2026-07-25

**문제**: `translation_rules_ko.txt` 규칙 8(줄바꿈)이 "25자 넘으면 나눠라"만 있고 왜
25자인지, 그리고 나눈 뒤에도 넘치면 몇 줄까지 허용되는지가 없었다. 영문판
(`translation_rules_en.txt`)은 "최대 두 줄 + 줄당 42자"로 상한이 명시돼 있는데 한국어판만
빠져 있었다 — 실제로 아주 긴 원문 한 줄이 같은 번호로 3줄 이상 쪼개져도 프롬프트도 코드
(`indexTranslatedBodies`)도 막지 않는 상태였다.

**결정**:
- **25자 근거**: 별도로 새로 유도하지 않고 이미 있는 `CPS_TARGET`(10자/초, §2-5)에
  근거를 붙였다 — 10자/초로 편하게 읽히는 한 줄의 길이는 대략 2.5초 분량인 25자다. 그
  이상이면 한눈에 읽기 부담스러운 길이로 보고 나누는 기준으로 삼는다. CPS_TARGET 자체를
  바꾸면 이 25자도 같이 재검토해야 하지만, 지금은 상수화(`constants.ts`)하지 않고
  프롬프트 텍스트에 값으로만 남겨뒀다 — 재조립처럼 코드가 강제하는 값이 아니라 모델에게
  주는 가이드라인이라 굳이 코드/문서 다중 동기화 대상으로 승격할 필요가 없다고 판단.
- **2줄 상한은 별도 규칙(9번)으로 분리**: 애초에 규칙 8 안에 트리거·분할법·예시·번호
  유지·2줄 상한·초과시 압축까지 욱여넣었더니 번호 하나가 너무 많은 지시를 겸했다(마커
  스킴에서 이미 한 번 겪은 "지시가 뭉치면 일부가 씹힌다" 실패 패턴, §2-1). 2줄 상한과
  초과시 압축 지시만 떼어 규칙 9로 분리했고, 이하 규칙 번호(화자 표시·태그 보존·우선순위)는
  한 칸씩 밀렸다. 우선순위 규칙(현재 12번)은 번호가 아니라 "줄 길이"라는 개념으로
  지칭하므로 재번호와 무관하게 그대로 둠.
- **코드 레벨 강제는 안 함**: `indexTranslatedBodies`(`srt.ts`)는 같은 마커의 줄 수를
  제한하지 않는다 — 모델이 규칙을 어기고 3줄 이상 내면 그대로 통과된다. 이건 프롬프트
  레벨 가이드라인이지 재조립 불변식(블록 수·마커 무결성)이 아니므로, 코드에서 강제하는
  건 지금 범위 밖으로 남겨둔다.

**보강 (2026-08-18) — 권장선 16자를 프롬프트에만 넣었다.** Netflix 한국어 기준은 한 줄
16자(공백·문장부호 포함)로 우리 25자보다 짧다(`docs/standards/netflix-korean-gap-review.md`).
25자를 그대로 두면 한눈에 들어오지 않는 줄이 계속 나오고, 25→16으로 **내리면** 2줄 분할이
급증하고 "나누고도 넘치면 압축해"가 상시 발동해 의미 누락 위험이 올라간다. 그래서 값을
바꾸는 대신 규칙 2를 **두 수**로 썼다 — 권장선 16자("되도록 그 안에 맞춰")와 강제선
`{{lineMaxChars}}`(25자, "넘으면 반드시 나눠"). 16자는 **번역문의 길이에 거는 압력**이지
줄 수를 정하는 값이 아니다.

- **코드는 16자를 모른다.** `enforceTextRules`의 접기(`linesJoined`)는 여전히
  `lineMaxChars`(25)로 판정하므로, 모델이 17~25자를 두 줄로 나누면 코드가 도로 한 줄로
  접는다. 이건 버그가 아니라 "강제하지 말고 권유만"이라는 요구의 직접적 귀결이다.
- **`languages.ts`는 안 건드렸다.** `lineMaxChars`는 프롬프트와 접기 판정이 함께 쓰는
  값이라, 여기서 16으로 내리면 프롬프트뿐 아니라 접기 동작까지 같이 바뀐다 — 그건 "권유"가
  아니라 강제다. 16자를 실제로 강제하기로 결정하면 그때 이 값을 내리는 것이 유일한 자리다.
- **`{{lineMaxChars}}` 자리를 하나 더 늘렸다**: "원문이 두 줄이어도 **이어서
  {{lineMaxChars}}자 안이면** 한 줄로 합쳐". 이전 문구("한 줄에 들어가면 합쳐")는 권장선이
  생기면서 16자인지 25자인지 모호해졌고, 접기를 실제로 수행하는 코드의 기준은 25자다.

**후속 (2026-08-19) — 강제선을 25자 → 19자로 내렸다(권장선 16자는 유지).**
바로 위에서 "16자는 프롬프트에만"이라고 결정한 다음 날 강제선까지 손댔다. 순서가 이렇게
된 이유는 실측을 그 사이에 했기 때문이다.

**측정**: `samples/subtitles/Marx può aspettare (…).ko.srt` (1,126블록 / 1,788줄).
⚠️ **이 파일은 전문 번역가의 자막이 아니라 우리 사이트의 이전 출력이다** — 25자를
지시했을 때 우리 파이프라인이 실제로 내놓은 결과다. 그러므로 아래 수치는 "좋은 자막은
이렇다"가 아니라 **"25자를 시키면 우리가 이렇게 쓴다"**로만 읽어야 한다. (한때 이걸
레퍼런스로 착각해 "접기 상한을 풀자"는 정반대 결론까지 갔다 — 전제를 먼저 확인할 것.)

- 줄 길이: 중앙값 11자 / p75 14자 / p90 17자 / p95 19자 / 최대 29자
- **25자 초과 1줄(0.1%)** — 모델은 준 숫자를 거의 완벽히 지킨다. 이건 품질 지표가 아니라
  **순응도 지표**이고, 19를 주면 19를 지킬 것이라는 근거다.
- 19자 초과 3.8% / 16자 초과 13.1%

**왜 19인가 (= 16 + 3)**: 2줄 상한이 있으니 실제 예산은 `상한 × 2`이고, 이걸 넘는 블록만
"나눠도 안 들어가서 **깎아야** 하는" 블록이다 — 규칙 2의 "나누고도 넘치면 압축해"가
발동해 의미가 새는 자리다.

| 한 줄 상한 | 블록 예산 | 압축 필요 블록 |
|---|---|---|
| 16자 (엄격) | 32자 | 55개 (4.9%) |
| **19자 (채택)** | 38자 | **10개 (0.9%)** |
| 25자 (이전) | 50자 | 0개 |

16자를 그대로 강제하면 20블록에 1개를 깎아야 하지만, +3자면 110블록에 1개로 떨어지고
그 10개도 총량 39~45자라 몇 글자만 다듬으면 되는 수준이다. **+3은 임의의 여유가 아니라
압축 압력 곡선의 무릎이다.**

**접기가 예산과 저절로 일관돼진다**: `enforceTextRules`의 접기는 `lineMaxChars`로
판정하므로 자동으로 19가 된다. 되돌리는 블록이 341개 → 126개로 주는데, 이게 옳은 이유는
합쳤을 때의 길이로 설명된다 — `아버지가 우리와 함께 / 계시지 않는다는 겁니다`는 합치면
24자라 **합치는 순간 19자 상한을 스스로 위반한다**. 예산을 넘는 건 두 줄로 두는 게 맞고,
`제 아내와 / 딸 카밀라`(11자) 같은 군더더기 분할은 19 아래라 여전히 접힌다. 한 상수가 두
역할(분할 트리거·접기 예산)을 모순 없이 겸한다.

**남은 위험**: 25자는 한국어가 자연히 그 아래라 거의 안 물리는 상한이었다(초과 0.1%).
19자는 현재 줄의 3.8%를 실제로 건드리므로, **순응도를 관찰한 적 없는 구간에서 처음
시험하는 것**이다. `CPS_TARGET`(10자/초)에서 유도한 25자 근거는 이제 이 값과 어긋나지만,
19자 × 2줄 = 38자는 10자/초로 3.8초라 노출 시간과도 무리 없이 맞는다.

**후속 (2026-08-21) — 강제선을 19자 → 18자로 다시 내렸다.** 재측정은 하지 않았다 —
위 표의 압축 압력 곡선(16자 4.9% → 19자 0.9%)을 다시 실측할 때까지, 18자에서 압축이
얼마나 늘어나는지는 아직 관찰값이 없다. 다음에 이 상수를 또 바꾸기 전에 §2-6의 실측을
반복해 곡선이 여전히 같은 모양인지 확인할 것.

### 2-7. ~~진행 링 추정 = 실측 생성률 계산~~ → **모델별 고정값 (flash 30초 / pro 3분)** — 2026-07-26

**문제**: `estimateTranslationMs(blocks, chunkSize, concurrency)`는 실측 생성률로

추종은 정확했지만 **랜딩 문구는 "2분"이라는 숫자 하나를 약속**하고 있어서, 같은 화면에서

**결정**: 추정을 **모델별 상수** `TRANSLATION_ESTIMATE_MS`로 바꾸고(flash 30,000ms /

찍히므로, 추정이 짧으면 거짓말이 아니라 **느린 크롤**로 열화된다 — 그게 고정값을 써도

**주의할 점**:
- **pro 3분은 미측정 자리표시자다.** flash 실측(23초)에 여유를 얹은 30초와 달리, pro는
  하네스로 돌려본 적이 없다. 더 조이기 전에 반드시 측정할 것.
- **카피의 "30초"는 flash 기준**이다. 고급번역(pro)을 고르면 링은 3분으로 도는데 랜딩엔
  30초라고 쓰여 있다 — 지금은 기본값이 빠른번역이라 허용 범위로 봤지만, pro를 전면에
  내세우게 되면 문구를 모델별로 갈라야 한다.
- 파일 크기를 안 본다. 크레딧 상한(2,000블록)에 가까운 파일은 30초를 넘길 수 있고, 그때
  링은 99%에서 기다린다. 실측 생성률 기반 계산이 필요해지면 §5-7의 유도가 그대로 남아
  있으니 되살리면 된다.

### 2-8. AI가 번역 규칙을 가끔 무시하는 문제 — 기계적 규칙만 코드가 강제 (2026-07-26)

**문제**: `translation_rules_ko.txt`의 12개 규칙 중 재조립(`indexTranslatedBodies`)이
실제로 강제하는 건 번호 무결성(1·2번)뿐이고, 나머지는 프롬프트 텍스트로만 존재해
모델이 이따금 어겨도 코드가 감지·수정하지 않았다. 원인은 세 층이었다: ①기계적 규칙도
코드 강제가 없었다 ②청크가 서로 문맥을 모른 채 병렬 번역돼 인물 말투 같은 파일 전체
일관성이 필요한 규칙은 프롬프트만으로 원천적으로 안 풀린다(§2-9 글로사리·존대관계
프리패스가 이 문제를 해결) ③과거 규칙 8이 트리거·분할법·예시·2줄상한을

부분 준수가 나온다.

**결정**: 정답이 **하나뿐인** 기계적 규칙만 `app/lib/srt.ts`의 `enforceTextRules`로
코드가 강제한다 — 문서 지도는 `translation-pipeline.md` §9.7.
(아래 규칙 번호는 2026-07-28 기준 `translation_rules_ko.txt`. 언어별 독립 파일로
합친 뒤 번호가 바뀌었으니 §2-12 참고.)
- **말줄임표 정규화**: `..`/`...`/`....` 등 마침표 2개 이상 연속 → `…` 한 글자.
  프롬프트(규칙 10)도 `…` 사용을 명시하도록 같이 갱신했다 — 코드가 사후에 고쳐주더라도
  모델이 처음부터 올바른 형태로 내는 게 더 낫기 때문.

**스코프에서 뺀 것과 이유**:
- **규칙 7 (줄 길이 초과 시 의미 단위로 두 줄 나누기)**: 어디서 끊어야 자연스러운지는

돌리는 사람이 표기 일관성만 원해도 무조건 느린 모델을 강요당한다 — 실제로는 정반대
관계(플래시가 청크당 값싸므로 글로사리 이득이 더 크다)일 수도 있다. 기본값은 OFF —

처음 켜는 진입 장벽만 남는다.

`composer.test.ts`에 이 기능 도입 전과 바이트 단위로 동일함을 잠그는 회귀 테스트가 있다.

### 2-10. TMDB 검색이 여러 개 맞으면 인기도로 자동 선택하지 않고 사용자에게 고르게 한다 — 2026-07-26

**문제**: `enrich`(구 `enrichMovie`)는 TMDB 검색 결과 중 항상 인기도(연도 일치 우선) 1등만
골라 바로 진행했다. 흔한 제목·리메이크·동명 시리즈처럼 매치가 여러 개면, "다시 검색"을
눌러도 매번 같은 기준으로 같은(또는 여전히 엉뚱한) 1등을 다시 뽑을 뿐이라 사용자가
원하는 작품으로 수렴할 방법이 없었다.

**결정**: TMDB 검색(`tmdb.ts` `searchCandidates`)과 상세조회(`lookupById`)를 분리하고,
검색 결과가 **정확히 1개면 지금처럼 자동으로 완전히 진행**하되, **2개 이상이면
era/tone 추출(Gemini 호출)을 미루고 후보 목록만** 반환한다(`enrichMovie.ts`
`searchMovie` → `{status:'ambiguous', candidates}`, 최대 `MAX_ENRICH_CANDIDATES`개 —
기본 5, `constants.ts`). `InfoStep.tsx`가 포스터·제목·연도·영화/드라마 뱃지로 후보
카드를 보여주고, 사용자가 클릭하면(`onSelectCandidate`) `/api/enrich`를 선택 모드
(`{candidate}`)로 다시 호출해 `enrichMovieById`가 상세조회+era/tone 추출을 마무리한다.
후보가 1개뿐이면 이 UI는 아예 안 뜨므로(백엔드가 바로 `found`를 반환), 흔치 않은
케이스에서만 클릭 한 번이 추가되고 나머지는 기존 흐름 그대로다.

**부수 정리**: `enrichMovie`/`enrichFromTmdb`/`tmdb.ts`의 `lookupTitle`은 이 변경으로
프로덕션 경로에서 완전히 대체되어(호출하는 곳이 테스트뿐이었음) 삭제했다 — `searchMovie`
+ `enrichMovieById`가 그 자리를 대신한다.

**주의할 점**:
- 후보 카드에 감독은 안 보인다 — TMDB 검색 응답 자체에 크레딧 정보가 없어서, 후보마다
  상세조회를 하면 가벼운 검색이라는 전제가 깨진다. 포스터·연도·줄거리 스니펫만으로
  구분 가능하다고 판단했다.
- `MAX_ENRICH_CANDIDATES`는 "화면에 몇 개 보여줄지"만 자르는 값이다 — 이 상한
  자체는 안 바뀐다. **다만 "1개 초과면 무조건 선택 UI가 먼저 뜬다"는 이 절의
  결정은 §6-4에서 뒤집었다**: 지금은 1순위를 자동 해소하고, 선택 UI는 사용자가
  "아니에요"를 눌러야만 나타난다.

### 2-11. 도착어 6개 추가 — 언어별 값은 표 하나로 모으고, 존대 축은 언어 중립으로 저장한다 — 2026-07-27

**문제**: 도착어가 한국어뿐이었다. `TARGET_LANGS`에 en/ja/es/fr/zh가 `enabled: false`로
스캐폴딩돼 있어서 "플래그만 켜면 된다"고 적혀 있었지만, 실제로는 켜면 **잘못 번역된다**:
`translationContent.ts`의 `getLanguageConfig`가 ko/en만 분기하고 나머지는 전부 영어 룰로
폴백했고(중국어를 고르면 영어 자막 규칙으로 번역됐다), `parseTargetLanguage`는 50자 이하
아무 문자열이나 통과시켰다. 줄 길이(25자)·문장부호(마침표 제거)·리딩스피드(12 CPS)·
글로사리(`GlossaryTerm.ko`)·존대관계(`'존댓말'|'반말'|'혼용'`)가 전부 한국어 전제로
하드코딩돼 있었다.

**결정 1 — 언어별 값은 `app/config/languages.ts` 한 표에 모은다.** 한 행이 picker
표시(label/mono/enabled), 프롬프트(promptLabel/lineMaxChars/formality), 후처리
(trailingPunctuation/reading)를 전부 들고 있다. 다른 파일에 `if (lang === 'ko')`를
다시 만들지 않는 것이 이 결정의 핵심이다 — 그 분기가 곧 "언어를 늘렸는데 한 곳만 안
고쳐진" 버그다. 활성 언어: 한국어·영어·일본어·스페인어·프랑스어·중국어(간체)·독일어.

**결정 2 — 룰 프롬프트를 공통 형식 + 도착어 델타로 쪼갠다.** *(2026-07-28에
뒤집힘 — 아래 §2-12.)* 번호 무결성·블록 수·2줄 상한 같은 **불변식**은 언어와
무관하므로 `translation_rules_format.txt` 하나가 갖고 (`{{lineMaxChars}}`만 언어별
치환), 문체·말투·문장부호만 `translation_rules_<code>.txt`에 남긴다. 7벌 복사였다면
불변식 1(블록 수 계약)이 언어마다 조금씩 다른 문장으로 갈라졌을 것이고, 그
드리프트는 자막 밀림으로 나타난다.

**결정 3 — 검증은 화이트리스트로 조인다.** `parseTargetLanguage`가 **enabled 코드만**
통과시키고, 프롬프트 빌더(`requireTargetLang`)는 모르는 코드를 만나면 던진다. 이전처럼
조용히 다른 언어 규칙으로 폴백하면, 사용자는 "왜 중국어를 골랐는데 영어 자막 관행이
적용됐는지" 알 방법이 없다. 실패가 보이는 쪽이 낫다.

**결정 4 — 존대/격식은 언어 중립으로 저장하고 표시할 때만 그 언어의 어휘로 번역한다.**
`SpeechRelation.speech`는 `'formal' | 'informal' | 'mixed'`이고, 프롬프트·UI에 나갈 때만
`TargetLang.formality`의 라벨(존댓말·반말 / 敬語·タメ口 / usted·tú / Sie·du / vous·tu)로
바뀐다. 모델에 "formal"만 던지면 어떤 문법 형태를 쓰라는 건지 알 수 없으므로 라벨은
반드시 그 언어의 말로 나가야 한다. `GlossaryTerm.ko`는 `target`으로 이름을 바꿨다.
**영어·중국어는 문법적 말투 축이 없어 `formality: null`** — 추출 프롬프트에서 관계
파트를 아예 빼고, `<speech_relations>` 태그도 만들지 않는다. 없는 축을 만들어내는 것보다
표기만 고정하는 게 정확하다.

**결정 5 — 후처리도 언어를 따른다.** 문장 끝 마침표 제거는 **한국어·일본어·중국어 자막
관행**이지 보편 규칙이 아니다. 영어/스페인어/프랑스어/독일어는 문장부호를 유지하는 게
표준이므로 `trailingPunctuation`이 빈 문자열이고 `enforceTextRules`가 그 단계를 건너뛴다.
리딩스피드도 마찬가지 — 라틴 문자는 글자당 정보량이 작아 20 CPS대가 정상이고, 한국어의
12를 그대로 쓰면 라틴계 자막이 불필요하게 늘어난다(`tuning/reading-speed.md`).

**확인 방법**: 5개 언어에 실제 Gemini 호출로 12블록을 번역해 블록 수 12/12·미매칭 0을
확인했다(2026-07-27). 재현은 opt-in 스모크 테스트 —
`LIVE_LANG_SMOKE=1 npx vitest run app/lib/prompts/liveLang.smoke.test.ts`.

**남은 것**: 한국어 외 리딩스피드 값은 공개 스타일 가이드 기반 **추정치**다
(`tuning/reading-speed.md`). cinematic 철학 파일은 여전히 한국어 전용이지만, 스타일이
UI에 노출되지 않아(`page.tsx`가 `'meaning'` 하드코딩) 이번 범위 밖이다.

지도(`translation-pipeline.md` §7)대로 7개 파일을 같이 점검한다. 모델이 도착어로
된 규칙을 읽는 이득이 드리프트 리스크보다 크다고 판단했다.

**확인**: `composer.test.ts`가 언어마다 규칙 파일의 고유 문구·줄 길이 숫자·헤딩
미사용을 검사. `LIVE_LANG_SMOKE`는 기존과 동일.

### 2-13. 다중 자막 포맷은 가장자리 어댑터, 출력은 원본 형식 + SRT — 2026-07-28

**문제**: 사용자가 올리는 자막이 SRT만이 아니다. VTT(웹), SMI(국내 구형), ASS/SSA
(팬서브)가 흔하고, 업로드 게이트가 `.srt`만 받으면 그 파일을 쓰려면 사용자가
직접 변환해야 한다. 그리고 VTT를 올린 사람은 VTT를 돌려받길 기대한다.

**결정**: 업로드 직후 `app/lib/subtitles/`에서 포맷을 감지·파싱해 **정규 SRT 문자열**로
바꾼 뒤, 기존 파이프라인(`parseSrtBlocks` → 청킹 → Gemini → 재조립)은 손대지 않는다.
AI 와이어 포맷(`[N] 대사`)과 프롬프트 규칙은 포맷 비종속이라 **거의 변경 없음**
(철학 문구의 "SRT 구조" → "자막 블록 구조" 정도).

| 포맷 | 파서가 하는 일 | 잃는 것 |
|---|---|---|
| VTT | cue 타임(`.` ms) → cues, 태그 strip | (라운드트립 시 없음 — 아래) |
| SMI | `SYNC Start` + 다음 sync로 end, `&nbsp;`는 클리어 | CSS/클래스; UTF-8 실패 시 EUC-KR/CP949로 디코드 |
| ASS/SSA | `[Events]` Dialogue만, override strip | Style/위치/karaoke/레이어 |

**출력은 SRT로 재조립하지 않고 원본에 끼워넣는다(splice)**. 파서가 큐를 뽑을 때
대사와 타임코드 토큰이 **원본 문자열 어디에 있는지**(`CueRef.text`/`start`/`end`
= 문자 오프셋)를 같이 기록해두고, 번역이 끝나면 원본을 뼈대로 그 구간만 치환한다.

정규 SRT에서 VTT를 새로 써내는 방식(writer)도 검토했지만 각하했다. writer는
우리가 모델링한 것만 복원할 수 있어서 VTT의 NOTE/STYLE/REGION·cue id·cue settings,
ASS의 `[Script Info]`/스타일/레이어가 통째로 날아간다. splice는 **모르는 건 애초에
다시 쓰지 않으므로** 보존이 노력이 아니라 구조적 보장이 된다. 검증도 한 줄로 끝난다 —
"슬롯에 원래 내용을 그대로 넣으면 원본과 동일"(`spliceIdentity` 테스트).

**타임코드는 움직였을 때만 재기입한다.** 그래서 CPS 확장이 건드리지 않은 큐는 원본
토큰 표기(`00:10.000` 같은 짧은 형태)까지 그대로 남는다.

**1차 범위는 VTT만.** ASS/SMI는 파싱은 되지만 writer가 없어 `.srt`로만 내려간다
(`SubtitleDoc.roundTrip = false`). ASS·SMI writer와 그 타임코드 트레이드오프는
`docs/TODO.md`. 완료 화면은 항상 **원본 형식 + SRT 두 버튼**을 주고, splice가 어떤
이유로든 실패하면 SRT 단독으로 조용히 물러선다 — 직렬화 버그로 다 끝난 번역을 못
받는 일은 없어야 한다.

**이중 언어 SMI는 거절한다.** KRCC+ENCC처럼 실질 트랙이 2개 이상이면
`BilingualSmiError`로 업로드 단계에서 돌려보낸다. 이전에는 SYNC마다 "비어 있지 않은
첫 `<P>`"를 골랐는데, 한쪽이 `&nbsp;`인 구간이 흔해서 큐마다 언어가 갈리는 파일이
나왔다 — 깨진 파일보다 나쁜, 멀쩡해 보이는 오역이다. 트랙 선택은 UI가 필요해
`docs/TODO.md`로 미뤘다.

### 2-15. Pro 사고 레벨을 HIGH로 올린다 — MEDIUM은 LOW 대비 이득이 없었다 (2026-07-28)

**문제**: 대표가 초창기 CLI 프로토타입(HIGH, B=120, 타임스탬프 통째 전송)의 번역

**레버 1 — 사고 레벨(LOW/MEDIUM/HIGH) × 청크 크기(B) 조합 측정**:

(461블록, gap-based 하네스)에 B∈{250,500,1000}×LOW/MEDIUM 4런 + B∈{250,500}×HIGH
2런, 총 14런.

| 조건 | 사고/블록 | 정렬실패 | 비고 |
|---|---|---|---|
| full-movie, LOW (4개 B) | 0.08~10.7 | 0~2/1874 | B가 클수록 사고 급감(2000: 0 / 250: 10.7) |
| full-movie, MEDIUM (4개 B) | 0.85~22.7 | 0~24/1874 | **LOW보다 나은 셀이 하나도 없음**, B=1000에서 최악(24건) |

**발견 1 — MEDIUM은 기각.** full-movie 4쌍 중 MEDIUM이 LOW보다 나은 셀이 0개,
나쁜 셀이 3개(최대 B=1000에서 정렬실패 2→24), 비용은 항상 더 비쌈(최대 2.3배).

모델이 번역을 "더 잘하려" 문장을 재구성하다 블록 경계를 건드리는 것으로 보임 —
지난 세션 flash lean-prompt 결론(사고 0으로 HIGH급 안정성)과 같은 방향.

**발견 2 — 사고 비용은 B에 대해 급격히 준다(HIGH 포함).** 구 CLI(B≈120)의

**2.4배 절감**, 정렬실패는 0/461 그대로. 이유는 청크 수만큼 반복되는 "이 작업이

**발견 3 — HIGH에서는 B=250과 B=500이 사고·비용 거의 동일(차이 2%)한데 시간은

붙던 것과 반대 방향 — HIGH는 이미 사고를 충분히 태우는 모드라 청크 분할에

### 2-16. Pro HIGH 장편 300초 타임아웃 — 통과(여유 2.1배), 그리고 하네스가 잘못된 걸 재고 있었다 (2026-07-31)

§2-15가 "실측 전까지 가정"으로 남겨둔 항목을 닫는다. **결론: 통과. 최장 단일 청크
141.5s / 300s(47%).** 배경 잡 + 폴링 구조(레버3)는 필요 없다.

**측정보다 먼저 고쳐야 했던 것 — 하네스가 프로덕션이 아닌 설정을 재고 있었다:**

1. `scripts/prompt-ab.mts`가 청크 크기를 `SERVER_CHUNK_SIZE`(flash의 100)로
   **하드코딩**하고 있었다. `PRO_CHUNK_SIZE`(250)를 도입한 게 §2-15인데 하네스는
   같이 안 고쳤다. 그대로 돌렸으면 **B=100의 Pro**를 쟀을 것이고, 그건 §2-15가
   "HIGH를 비싸게 만든 원인"으로 지목한 바로 그 설정(1,405원)이다. →
   `chunkSizeForModel(TRANSLATION_MODEL)`로 교체.
2. **청크별 소요 시간을 아예 안 쟀다.** 하네스는 런 전체 `seconds`만 보고했는데,
   300초는 `CHUNK_TIMEOUT_MS`로 **단일 요청**에 걸린다. 총시간으로는 이 질문에
   답할 수 없다. → 모델 호출마다 wall-clock을 기록하고 **최장청크**를 리포트에
   추가(재시도는 각각 별도 기록 — 타임아웃이 시도마다 독립적으로 걸리므로).

**교훈: 실험 도구는 프로덕션 상수를 공유해야지 복사하면 안 된다.** 1번은 상수
하나가 갈라진 지 사흘 만에 하네스를 조용히 무효화했다.

**결과 (full-movie 1,124블록 · 이탈리아 장편 · HIGH · B=250 · K=16):**

| | 값 |
|---|---|
| 최장 단일 청크 | **141.5s / 300s (47%)** |
| 총 시간 | 161.4s (5청크, 1웨이브) |
| API 실패 · 정렬실패 | 0 · **0.00%** (스윕 1회로 21블록 회수) |
| θ (thinking/블록) | **44.0** (가정 40) |
| 비용 | $0.8888 = 1,500원 → **1.34원/블록** |

**파일 길이는 이 질문과 무관하다 — 이게 실측보다 강한 근거다.** 청크 크기는
`chunkSrtBlocksAtGaps`의 tolerance 20%가 **300블록으로 하드 바운드**한다
(`maxSize = targetSize + tolerance` = 250+50, `app/lib/srt.ts`). 파일이 길어지면
청크 *수*만 늘고 청크 *크기*는 300을 못 넘는다. 크레딧 상한(2,000블록)도 8청크
≤ K=16이라 1웨이브라 큐잉도 없다. 따라서 **어떤 길이든 최장청크는 이 수준**이다.

**부수 소득 둘:**

- `chunk-size-model.md` §5-2-1이 예측한 "300초 예산의 48%"에 대해 실측 47.2% —
  **오차 1%p 이내**. θ·v 모델이 맞았다.
- **"장편은 더 쌀 것"이라는 추측은 틀렸다.** LOW에서 full-movie의 thinking이
  drama의 1/400이었던 게 근거였는데, HIGH에서는 두 파일이 θ≈40~44로 수렴한다.
  HIGH의 θ는 파일 특성보다 사고 레벨이 지배한다(`cost-per-block.md` §4-1).
  크레딧 상한 원가는 2,492원 → **2,670원**으로 올라갔다. 프로 크레딧을 가입
  보너스에서 뺀 §1-10-1 결정과 같은 방향이다.

## 5. 베타 리디자인 (2026-07-29)

랜딩·위저드·`/mypage`를 새 디자인으로 갈아엎은 마지막 배치의 결정들. 개별 태스크
커밋에 흩어져 있던 근거를 한곳에 모은다.

### 5-1. 번역권 라이트/프로 분리

**결정**: 크레딧을 `lite_balance`/`pro_balance` 2종으로 나눈다
(`supabase/migrations/0004_credit_tiers.sql`, `settle_order`에 `p_kind` 인자 추가,
기본 `'lite'`).

**근거**: 프로(HIGH thinking)는 라이트(flash)와 원가 구조 자체가 다르다 —
thinking 토큰이 **출력 단가**로 과금되고(§2-4-1), 파일에 따라 블록당 비용이
3.7배까지 흔들린다(`tuning/cost-per-block.md`, §4 "다음" 목록 10번 항목). 하나의 공유 잔액이면
사용자가 싼 라이트 크레딧으로 비싼 프로 경로를 그대로 쓸 수 있어 원가와 판매
단가가 어긋난다. 분리하면 각 티어가 자기 원가만 커버하면 되므로 가격 논리가
성립한다. 마이그레이션은 기존 잔액을 전부 `lite_balance`로 이관해 아무도
크레딧을 잃거나 공짜 프로 크레딧을 받지 않는다.

### 5-2. 초대 코드·친구 초대 미도입

**결정**: 베타에 초대 코드나 친구 초대 보상 구조를 넣지 않는다. 가입 자체가
게이트다(§1-3).

**근거**: 어뷰징 방어는 이미 Google 로그인이 사실상 신원 확인을 대신한다(§1-3).
초대 코드·추천 보상은 그 위에 **운영 부담**(코드 발급·추적·부정 사용 방지)만
추가하고 막는 리스크는 새로 없다 — 익명 API 유출처럼 구조적 방어가 필요한
문제가 아니라, 다계정 어뷰징처럼 이미 "우선순위 낮음"으로 수용한 리스크(§1-3)와
같은 급이다.

### 5-3. 결제 서버 코드 존치·UI만 제거

**결정**: 토스페이먼츠 연동 서버 코드(`app/lib/server/toss.ts`,
`/api/payments/*`, `settle_order`)는 그대로 두고, 위저드에서 `PurchaseStep`
진입점만 뺀다(커밋 `24180b1`). 번역권이 떨어지면 결제 대신
대기자 등록(`ExhaustedStep.tsx` → `waitlist` 테이블)으로 보낸다.

**근거**: 결제 코드를 걷어내 별도 feature 브랜치로 옮기면, 리디자인이 끝나고
다시 합칠 때 그 사이 벌어진 브랜치 차이를 병합해야 한다 — **feature 브랜치를
썩히는 비용**이다. 코드를 지우지 않고 진입점만 빼면 그 비용이 아예 없다. 다시
붙일 때 할 일은 `docs/TODO.md`의 "결제 오픈 시 후속 작업" 절에 정리했다 —
`settle_order`에 이미 있는 `p_kind` 전달 + 프로 팩 가격 정책 결정.

### 5-4. 결과물만 보관·원본 미보관

**결정**: `supabase/migrations/0007_job_results.sql`이 번역 **결과물**만
Storage(`results` 버킷)에 저장한다. 업로드된 **원본 자막은 저장하지 않는다**.

**근거**: 원본은 사용자의 저작물이고, 우리가 그걸 들고 있어야 할 이유가 없다
(§1-11의 "무저장 구조가 핵심 방어 논리"와 같은 원칙). 결과물은 다르다 —
크레딧 1개를 내고 산 것이므로 다시 받을 수 있어야 사용자에게 의미가 있다.
저장 범위를 결과물 하나로 좁히면 개인정보·저작권 노출면도 그만큼 좁아진다.

### 5-5. 보관 30일을 cron 없이 UI가 지킴

**결정**: 결과물 보관 기한은 30일이지만, 만료된 객체를 Storage에서 실제로
지우는 정리 작업(cron)은 이번 배치에 넣지 않는다. `isExpired`
(`app/lib/jobHistory.ts`)가 UI에서 다운로드 버튼만 잠근다.

**근거**: 베타 규모(~30명, 파일당 수백 KB~수 MB 텍스트)에서 지우지 않고 쌓이는
비용이 무시할 만한 반면, cron 인프라(스케줄러·실패 재시도·orphan 처리)를 미리
놓는 건 과설계다. UI 잠금은 "사용자가 만료 후 못 받는다"는 약속을 이미 지키고
있고, 실제 삭제는 스토리지 사용량이 문제가 될 때 붙여도 늦지 않다. 후속 작업은
`docs/TODO.md`.

### 5-6. 완료 리포트에 미계측 수치를 넣지 않음

**결정**: 완료 화면의 "적용 내역" 리포트는 실측된 항목만 보여준다 — CPS(길이 예산)
조정처럼 코드가 아직 계측하지 않는 항목은 넣지 않는다.

**근거**: `computeCps`(`srt.ts`)는 존재하지만 어떤 기능에도 연결돼 있지 않다
(`docs/TODO.md` "고급 번역" 절). 계측되지 않은 수치를 리포트에 올리면 실제로는
안 하는 조정을 한 것처럼 보여 사용자를 오도한다 — 이 프로젝트가 반복해서 지킨
원칙(예: §1-12의 "가변 없는 고유 주장만 남긴다")과 같은 결이다. 계측이 붙으면
그때 항목을 추가한다.

### 5-7. 첫 번역 전 저작권 동의 모달 — §1-11의 "모달 없음"을 뒤집는다

**결정**: 첫 번역 직전에 닫기 없는 필수 동의 모달을 세운다
(`app/components/beta/CopyrightModal.tsx`, 기록은
`supabase/migrations/0008_copyright_consents.sql`에 동의 버전과 함께 남는다).
§1-11이 고른 상시 고지 세 지점 중 signup-wrap·푸터는 **그대로 둔다** —
모달이 그것들을 대체하는 게 아니라 위에 얹힌다. (드롭존 아래 권리·무저장
문구는 2026-07-31 UI 정리로 제거 — 동의는 모달·약관이 담당.)

**뒤집은 이유는 마음이 바뀌어서가 아니라 전제가 바뀌어서다.** §1-11은 이틀 전에
쓰였고, 그때 ZAMAK이 저작권에 대해 지고 있던 위험은 **번역이라는 행위 그 자체**뿐이었다
— 원본도 결과물도 남지 않으니 나중에 문제 삼을 대상 자체가 존재하지 않았고, 그래서
"무저장 구조가 핵심 방어 논리"라고 쓸 수 있었다. 그 상태에서 모달은 순수한 마찰
비용이라 §1-8의 "30초면 번역돼요"와 맞바꿀 이유가 없었다.

같은 브랜치의 §5-4가 그 전제를 없앴다. 이제 결과물은 30일간 비공개 버킷에 실제로
남고(`0007_job_results.sql`), `/mypage`에서 다시 받을 수 있다. **우리가 들고 있는
2차적저작물이 생겼다**는 뜻이다 — 권리자 신고가 들어오면 지울 대상이 있고(§1-11 ③
개정), 반대로 "누가 올렸고 무슨 근거로 올렸나"를 답해야 할 대상도 생겼다. 이 위치에서
필요한 건 상시 고지가 주는 *열람 가능성*이 아니라, 사용자별로 **입증 가능한 명시적
동의**다 — 언제, 어느 버전에 동의했는지가 행 하나로 남아야 한다. 상시 고지 문구는
그 행을 만들지 못한다.

**마찰 비용은 인정하고 받는다.** 다만 계정당 평생 1회이고 첫 번역에만 걸리므로,
반복 사용자의 체감 속도(§1-8이 지키려던 것)는 그대로다. 모달이 매 번역마다 서거나
업로드 시점으로 앞당겨진다면 그때는 §1-11의 원래 논거가 다시 유효해진다.

### 5-8. 디자인 토큰을 핸드오프 이름으로 전면 리네임하고, 오타는 스크립트로 막는다

**결정**: `app/globals.css`의 토큰 이름을 `design_handoff_zamak_brand`의 이름
체계로 전부 바꾼다 (`--ink-3` → `--text-secondary`, `--wash` → `--fill-hover`,
`--radius` → `--r-card` 등). 동시에 핸드오프에만 있던 토큰
(`--on-ink`, `--track`, `--scrim`, `--focus-ring`, `--shadow-knob`,
`--placeholder-stripe`, `--ease-apple`, 타이포 스케일 18단계)을 추가하고,
컴포넌트 레이어와 TSX에 하드코딩돼 있던 같은 값들을 토큰 참조로 바꾼다.

**이름 충돌이 리네임의 진짜 이유다.** 핸드오프의 `--ink`는 본문 텍스트
(#1d1d1f)인데 기존 코드의 `--ink`는 브랜드 블랙(#161614)이었다. 두 체계를
공존시키면 `--ink` 한 이름이 문서와 코드에서 서로 다른 색을 가리키게 되고,
그 상태로 핸드오프를 보고 작업하는 사람은 33곳에서 조용히 틀린다. 별칭
추가로는 이 충돌만은 풀 수 없어서 — 별칭을 붙일 수 없는 유일한 이름이 하필
`--ink`다 — 전면 리네임이 남는 선택지였다.

**대신 오타 위험을 도구로 상쇄한다** (`scripts/check-tokens.mjs`,
`npm run check:tokens`). CSS 변수는 오타가 나도 빌드가 통과하므로 리네임의
실질 위험은 "이름을 틀리게 쓰는 것"이었다. 정의 집합과 참조 집합을 대조하는
가드를 먼저 만들고 리네임을 진행했다. 남는 위험은 오타가 아니라 *잘못된
토큰으로의 정상 치환*이고, 그건 프리뷰로 잡는다.

**보더는 값이 아니라 역할로 나눈다.** 기존 `--border`(0.1)는 핸드오프에 없는
값이라 역할별 네 단계(`subtle`/`chip`/`input`/`step`)로 흩어 보냈다. 구분선이
0.05, 카드·칩이 0.07로 내려가 실제로 조금 옅어졌다 — 의도한 변화다.

**타이포 스케일은 크기만 토큰이고 나머지는 두 갈래다.** `@theme`의
`text-h1`류 유틸리티는 크기+자간+행간을 함께 싣지만, 스케일에서 의도적으로
벗어나는 손으로 쓴 CSS(`.head h2`의 800/-0.025em 등)는 크기만 `var(--fs-*)`로
가져다 쓴다. TSX의 인라인 px 112곳과 CSS의 53곳을 스케일로 스냅하면서
13.5→13, 11.5→12, 18→17, 20→19, 24→22처럼 조금씩 움직인 값이 있다.

**굵기는 400이 아닌 단계에만 싣는다** — 이건 실패를 겪고 좁힌 규칙이다.
처음엔 스펙대로 전 단계에 굵기를 박았는데, 유틸리티는 컴포넌트 레이어를
이기므로 `text-caption`이 `.btn`의 500을, `text-mono-step`/`text-caption`이
`.zchip`의 브랜드 600을 조용히 400으로 깎았다. 400은 어차피 초기값이라
토큰이 얻는 게 없고 잃는 것만 있었다. mono/micro 단계는 스펙이 굵기를 주지
않으므로 아예 싣지 않는다.

**이 계열의 버그는 `check:tokens`가 못 잡는다.** 토큰 이름은 다 맞고 참조도
다 유효한데 *어느 레이어가 이기느냐*가 틀린 것이라, 정적 대조로는 보이지
않는다. 같은 뿌리로 mono 폰트도 원래부터 죽어 있었다 — `--font-jetbrains-mono`이
`<body>`에 붙는데 그걸 참조하는 `--mono`는 `:root`에 선언돼 있어서, `<html>`
시점에 guaranteed-invalid로 계산되고 그 빈 값이 그대로 상속됐다
(`app/layout.tsx`, 폰트 변수를 `<html>`로 옮겨 해결). 토큰 작업의 검증은
스크립트가 아니라 **브라우저에서 계산값(getComputedStyle)을 읽는 것**이
최종 관문이다.

### 5-9. 작품 확인을 설정 화면 안에서 한다 — 업로드 직후 'workPick'을 거치지 않는다

**결정**: `handleFile`이 업로드 후 `'workPick'`이 아니라 `'settings'`로 보낸다
(`app/hooks/useWizard.ts`). TMDB 검색은 설정 화면이 떠 있는 동안 돌고, 설정
화면이 자체 검색 중 상태를 렌더링한다. 검색이 notFound로 돌아오거나(§6-4)
ambiguous의 1순위 자동 해소 자체가 실패했을 때만 `runEnrich`가 `'workPick'`으로
보낸다.

**의도는 원래부터 이거였다.** 확신 있는 매치는 "목록이 하나면 물어볼 게
없다"는 이유로 설정에서 인라인 확인하도록 되어 있었는데, `handleFile`이
검색이 끝나기도 전에 무조건 `'workPick'`을 띄우는 바람에 사용자는 매번 후보
화면을 한 번 보고 지나갔다. 즉 라우팅과 실제 진입점이 서로 다른 말을 하고
있었다. (ambiguous를 곧장 후보 화면으로 보내던 옛 라우팅 함수
`nextScreenAfterUpload`는 §6-4에서 1순위 자동 채택으로 대체되며 삭제했다.)

**핸드오프(`design_handoff_zamak_brand`)도 같은 플로우다** — 업로드 → 설정
(자동 인식 확인 카드), "아니에요"를 눌렀을 때만 작품 선택 화면. 프로토타입은
검색이 즉시 끝나는 척하므로 검색 중 상태가 없고, 그 상태는 우리가 추가했다
(`TranslateSettingsStep`의 `searching` prop).

**대가**: 검색이 느리면 사용자가 빈 작품 카드 자리에서 스피너를 본다. 이전
구조는 그 대기를 후보 화면이 흡수했다. 검색이 눈에 띄게 느려지면 업로드
화면의 "읽는 중…"을 검색까지 늘리는 쪽(프로토타입의 1.4s 홀드)이 다음 후보다.

### 5-10. 피드백을 완료 화면 한 번이 아니라 재방문 때 한 번 더 받는다

**결정**: 완료 화면(`DoneStep.tsx`)은 지금처럼 별점만 받는다. "실제로
쓰셨나요·뭐가 문제였나요"는 별도로, 앱에 다시 들어왔을 때 모달로 묻는다
(`app/hooks/useFeedbackFollowup.ts`, `app/components/beta/FeedbackFollowup.tsx`).
대상과 시점은 서버 함수 `pending_feedback_job()`
(`supabase/migrations/0009_beta_metrics.sql`)이 정한다: 완료 6시간 경과,
보관 30일 이내, 아직 응답도 해제도 안 한 가장 최근 job 하나.

**근거**: 완료 화면에 서 있는 시점에 "실제로 썼는지"를 물으면 답이 나올 수가
없다 — 사용자는 방금 파일을 받았을 뿐 아직 열어보지도 않았다. 그 질문에
그 자리에서 억지로 답을 받으면 "예상"이 "실측"인 것처럼 저장되어, 표본
30명짜리 베타에서 가장 중요한 신호(①돈 낼 만한 품질인가)를 오염시킨다.
그래서 완료 화면은 즉답 가능한 것(별점)만 남기고, 답이 나중에야 존재하는
질문은 나중으로 미룬다.

**시점 판단은 서버가 갖는다.** 클라이언트가 "충분히 지났다"를 스스로
계산하게 두면 여러 기기·여러 탭에서 각자 다른 답을 낸다. `pending_feedback_job()`
하나가 "나중"의 정의(6시간~30일, 미응답, 미해제)를 소유하므로 어디서 열어도
같은 대상이 뜬다. 30일 상한은 자막 결과물의 보관 기한(§5-4)과 맞춘 것 —
그 이후엔 물어봐도 사용자가 다시 열어볼 파일이 없다.

**문제 유형을 자유 서술이 아니라 6개 칩으로 받는다** —
`mistranslation`/`speech-level`/`naming`/`too-long`/`unnatural`/`timing`. 각
값이 파이프라인의 서로 다른 파일로 이어지므로(오역 → 프롬프트, 존댓말 →
글로사리·존대관계, 표기 → `sanitizeCastSheet`, 타이밍 → `adjustSubtitleTiming`
…), 손으로 분류해야 하는 자유 서술은 30명 규모에서 실제로는 처리되지 않는
신호다. 문제가 된 줄은 SRT 시퀀스 번호(정수)만 저장한다 — 그 줄의 텍스트는
이미 보관 중인 결과물(0007)에서 읽으므로, "원본 내용은 어디에도 기록하지
않는다"는 개인정보처리방침 문구를 건드리지 않는다.

**대가**: 재방문이 없는 사용자(파일 하나 받고 다시는 안 옴)는 이 질문에
영원히 답하지 않는다. 30명 베타에서는 재방문 자체가 §3의 신호(실제로 쓸
것인가)이므로 감수한다 — 오히려 "재방문했는지"가 별도로 물을 필요 없는
행동 로그다.

### 6-4. 후보가 여럿이어도 1순위를 자동 채택한다 — 선택 화면은 "아니에요"를 눌러야만 뜬다

**뒤집힌 결정.** §2-10은 TMDB 검색이 2개 이상(ambiguous)이면 무조건 선택 UI를
먼저 보여주기로 했다("1개 초과면 무조건 선택 UI가 뜨는 기준 자체는 안 바뀐다").
프로토타입 동작(1순위로 바로 진행, 틀렸을 때만 목록)과 어긋난다는 지적을 받고
되돌렸다.

**결정**: `runEnrich`(`app/hooks/useWizard.ts`)가 ambiguous 응답을 받으면 그
자리에서 `candidates[0]`을 `runSelectCandidate`로 즉시 해소한다. 성공하면
확신 있는 매치와 완전히 같은 경로 — `autoMatched=true`로 설정 화면의 확인
배너("'X'로 인식했어요. 맞나요?")가 뜬다. 사용자가 "아니에요"를 눌러야만
`workPick` 화면에 전체 후보 목록이 나타난다. 후보 해소 자체가 실패한 경우에만
(드묾 — 두 번째 API 왕복이 실패) 예전처럼 `workPick`으로 바로 보낸다.

**후보 목록이 사라지지 않게 하는 게 핵심이었다**: `useEnrich`의 `selectCandidate`가
찾아온 결과를 `found`로 반영하면서 기존 `candidates` state를 비웠었는데(검색
결과 화면 전환용 정리), 그러면 "아니에요"를 눌렀을 때 빈 목록이 뜬다. 그래서
`selectCandidate`에만 `preserveCandidatesOnFound` 플래그를 추가해 이 경로에서는
지우지 않는다 — 새 검색(`enrich()`)은 여전히 매번 목록을 통째로 교체한다.

**대가**: ambiguous인 경우 `/api/enrich` 왕복이 한 번 더 늘어난다(검색 →
1순위 해소). 서버가 후보 목록과 함께 1순위를 미리 enrich해서 내려주면 왕복을
줄일 수 있지만, 그러면 `workPick`의 수동 재검색(`searchWork`)도 매번 자동
확정돼버려 사용자가 목록 자체를 볼 방법이 없어진다 — 그래서 클라이언트에서
두 번 호출하는 쪽을 택했다. 크레딧 소모는 없다(§2-10과 동일하게 `/api/enrich`는
과금 대상이 아님).

**부수 삭제**: 이 경로가 `nextScreenAfterUpload`(순수 함수, `'found'`↔그 외로만
분기)를 대체했다. ambiguous가 이제 "자동 해소 성공 시 settings, 실패 시
workPick"으로 갈라지면서 상태 하나만으로는 다음 화면을 못 정하게 됐다 —
함수와 테스트를 지우고 §5-9의 서술도 이 절을 가리키도록 고쳤다.

### 6-5. ~~진행 추정 = 모델별 고정값~~ → **파일별 실측 계산 + 지수 이징** (2026-07-31)

§2-7에서 실측 생성률 계산을 모델별 고정값으로 되돌렸다. 이번에 **다시 뒤집는다.**

**되돌렸던 이유와, 지금은 왜 유효하지 않은가**
- §2-7의 근거는 "랜딩 카피가 시간 하나를 약속하는데 파일마다 다른 시간을 말하면
  같은 화면에서 모순"이었다. 그런데 진행 화면은 이미 `COPY.progress.pct`로
  **초 단위 숫자를 그리고 있었다** — 파일별로 다른 숫자를 말하는 건 이미 하고
  있었던 셈이다.
- 오히려 설정 화면(`page.tsx`)과 진행 바가 **다른 근거**를 쓰고 있던 게 문제였다.
  이번에 둘 다 `estimateRunMsFromBlocks`/`FromChunks` 한 함수에서 뽑게 했다.
- §2-7이 "필요해지면 §5-7의 유도가 그대로 남아 있으니 되살리면 된다"고 명시해
  뒀다. 그 조건이 왔다.

**결정**: `docs/tuning/chunk-size-model.md` §1·§2의 실측 파라미터와 공식을
`app/lib/progressEstimate.ts`로 옮긴다. `TRANSLATION_ESTIMATE_MS`는 **블록 수를
모를 때의 폴백 전용**으로 격하하고, pro는 180초(미측정 자리표시자) → **165초**
(2026-07-31 실측 161.4초)로 고친다.

**§2-7의 안전성은 이징이 대신 지킨다.** 바는
`max(실제 청크 착지분, 밴드 끝을 향한 지수 이징)`으로 그린다. 지수 이징은 천장에
**도달하지 못하므로** 추정이 짧아도 거짓말이 아니라 크롤로 열화된다 — §2-7이
고정값을 써도 된다고 본 근거가 바로 그 성질이었고, 그건 그대로 살아 있다.

**Pro가 이 변경을 강제했다.** `PRO_CHUNK_SIZE=250`·`SERVER_CONCURRENCY=16`이라
1,124블록 파일은 청크 5개가 전부 한 웨이브다 — `onCompleted`가 142초 동안 한 번도
불리지 않는다. 청크 착지에만 기대는 바는 그동안 25%에 멈춰 있다. "다음 청크 착지를
천장으로 삼는" 안을 설계 중에 기각한 것도 같은 이유다.

**함께 고친 것**
- 글로사리를 끄면 그 단계가 '건너뜀' 배지가 아니라 **목록에서 사라진다**. 15–25
  밴드는 context가 흡수한다 — 행만 숨기면 바가 순간 점프한다.
- **타임코드 검증이 한 프레임도 안 그려지던 버그.** `useTranslation`에서
  `stage:'finalizing'`과 `stage:'done'`이 같은 tick에 있어 React가 배치했다.
  표시를 실제 검증 작업 앞으로 옮기고 `MIN_VERIFY_MS`(2초) **최소 노출**을
  보장한다. 고정 대기가 아니라 최소 보장이며, 취소는 즉시 깨운다. 하지 않은 일을
  했다고 하는 게 아니라 한 일을 볼 수 있게 만드는 것이다.

**주의할 점**
- `chunk-size-model.md` §1의 v·t_out·θ를 고치면 **UI 추정이 함께 움직인다.**
  이제 그 표는 문서가 아니라 런타임 파라미터다.
- 2웨이브 flash 런은 `⌈m/K⌉` 때문에 ~21% 과대 추정된다. 실측 보정이 첫 웨이브
  착지 후 잡지만, 웨이브 경계가 더 중요해지면 모델 자체를 손봐야 한다.
- 랜딩 카피 "12초"는 그대로다. 파일 크기를 명시한 문구라 모순되지 않는다.
  §2-7에 남아 있는 "pro를 전면에 내세우면 문구를 모델별로 갈라야 한다"는 여전히
  미해결이다.

설계 문서: `docs/superpowers/specs/2026-07-31-progress-ui-design.md`

### 6-6. 상시 고지 3지점을 동의 모달 1지점으로 합친다 — §1-11을 좁힌다 (2026-08-02)

**배경**: §1-11이 약관·처리방침을 상시 노출할 세 지점을 골랐다 — ① 업로드
드롭존 아래 ② 가입 CTA 아래 signup-wrap ③ 푸터 링크. §5-7이 첫 번역 앞에 저작권
동의 모달을 추가하면서도 "상시 고지 세 지점은 그대로 두되"라고 못 박았다.

**무슨 일이 있었나**: 베타 리디자인에서 ①과 ②가 화면 정리 과정에 빠졌다. 대표
판단은 "그 위치에 UI적으로 굳이 필요 없다"였고, 그 판단 자체는 유지한다. 문제는
남은 게 푸터 링크 하나뿐이라 **browsewrap만 남았다**는 것 — §1-11이 signup-wrap을
고른 이유가 정확히 "푸터 링크 단독보다 효력이 안정적"이어서였다.

**결정**: 뺀 두 지점을 되살리지 않는다. 대신 **이미 있는 `CopyrightModal`이
약관·개인정보처리방침 동의까지 함께 받는다.** 새 UI는 하나도 늘지 않는다.

이게 되살리기보다 나은 이유:
- 이 모달은 닫기 수단이 없는 **필수 게이트**다. 체크 없이는 못 지나가므로
  browsewrap이 아니라 clickwrap이고, 이건 뺀 두 지점보다도 강하다.
- 동의 **시점과 버전**이 `copyright_consents`에 남는다. 상시 고지는 "그 자리에
  문구가 있었다"를 나중에 증명해야 하지만, 이쪽은 행이 증거다.
- 처리방침의 법정 의무는 제30조의 **"공개"**지 동의가 아니다. 그건 푸터 링크가
  계속 충족한다. 빠져 있던 건 동의의 흔적뿐이었고 그게 여기서 채워진다.

`COPYRIGHT_NOTICE_VERSION`을 `2026-08-02`로 올렸다. 07-29 문구에 동의한 계정은
한 번 더 묻는다 — 옛 문구에 대한 동의는 새 문구에 대한 동의가 아니고, 그 재질문이
이 결정의 실효를 만드는 부분이다.

**남은 것**: 결제를 열면 구매 화면에도 별도 동의가 필요하다(전자상거래법). 그건
`feature/payments`가 UI를 다시 그릴 때 같이 본다.

### 6-7. 용어집을 플래그로 끈 채 베타를 연다 — 주석 처리가 아니라 (2026-08-02)

**결정**: 글로사리·존대관계 프리패스(§2-9)를 베타 오픈에서 접는다. 기능은 도는데
편집 화면이 덜 만들어졌고, 반쯤 만든 컨트롤을 내보내는 것보다 없이 내보내는 게
낫다. 베타 기간 중 다시 켠다.

**방식이 결정의 핵심이다.** 처음엔 JSX를 `{false && ...}`로 감쌌는데 그건 틀렸다
— 토글 상태가 **브라우저별로 저장**되기 때문이다(`zamak.castSheet.enabled`,
`useCastSheet`). UI만 숨기면 한 번이라도 켜본 사람은(사전 테스터 전원, 개발 노트북
포함) 파일마다 추출 호출이 계속 나가고, ETA에 `GLOSSARY_WAIT_MS`가 더해지고,
진행 바가 4단계로 도는데 **끌 방법이 없다**. 같은 빌드가 사람마다 다르게 도는 것도
문제다.

그래서 `GLOSSARY_UI_ENABLED`(`config/constants.ts`) 하나를 양쪽에서 읽는다 —
설정 화면의 렌더 조건과 `readStoredEnabled()`의 앞단. 꺼져 있으면 저장된 값을
무시하므로 끈 건 정말 꺼진다. 저장값 자체는 지우지 않는다: 다시 켤 때 각자의
선택이 그대로 돌아온다.

### 6-8. 파비콘을 새 마크로 교체하다가 `lib/brand.ts`가 통째로 낡아 있던 걸 발견했다 (2026-08-03)

**요청**: 대표가 새 파비콘(`icon.svg`, `apple-icon.svg`)을 전달하며 메타정보도
다시 확인해 달라고 함. 새 파비콘은 검은 잉크 + 노란 포인트 배색의 괄호 모티프
(`[  ]`, 가운데 노란 칩) — 헤더의 실제 워드마크(`public/brand/zamak-logo.png`,
검정+노란 점)와 같은 계열이다.

**교체**: `app/icon.svg` 내용 교체. `apple-icon`은 Next 정적 파일 컨벤션상
`.svg`를 못 받는다(`jpg`/`jpeg`/`png`만) — 받은 SVG를 `sharp`로 180×180 PNG로
래스터화해 `app/apple-icon.png`로 넣고, 기존 동적 생성기 `apple-icon.tsx`(옛
다이아몬드 마크, ImageResponse)는 지웠다.

**그러다 `app/lib/brand.ts`가 완전히 낡아 있는 걸 발견했다.** 이 파일의 `BRAND`
상수는 주석에 "Simple theme tokens in globals.css를 따른다"고 적혀 있었는데,
실제 `globals.css`의 `:root`(헤더 주석: "ZAMAK Design Tokens ... Black +
yellow-point brand ... No blue", 출처 `design_handoff_zamak_brand`)는 이미
검정+노랑 배색으로 넘어가 있었다. `BRAND`는 옛 크림색+초록(`bg #FAF8F4`,
`accent #3A9B72`) 그대로였다 — 어느 시점에 CSS 토큰이 바뀌었는데 이 파일만
안 따라간 것. 이 상수를 쓰는 곳은 OG 이미지(`opengraph-image.tsx`, `twitter
-image.tsx`가 재수출)와 방금 지운 옛 `apple-icon.tsx`뿐이라, **공유 링크로 사이트를
보는 사람에게만 보이는** 자리다 — 실제 화면(헤더 로고, 버튼, 전부 CSS 변수 참조)은
문제없이 새 배색이었다. 아무도 공유 미리보기를 눈으로 확인한 적이 없어서 안
걸렸던 것으로 보인다.

`BRAND`를 `globals.css` 값으로 다시 맞췄다(`bg`→`--bg`, `ink`→`--ink-strong`,
`accent`→`--accent` 등). 고치면서 OG 이미지를 실제로 렌더링해 보니 **마크 자체가
안 보였다** — `position: 'absolute', inset: 0`을 쓴 두 div가 Satori(next/og
렌더러)에서 크기 0으로 접혔다. `inset` shorthand가 지원 안 되는 것으로 보인다.
`top/left/right/bottom: 0`으로 풀어쓰니 바로 나타났다. 색 문제와 무관한 별개
버그였고, 언제부터 안 보였는지는 알 수 없다 — 공유 미리보기라 아무도 안 봤다.

**같은 자리에서 메타 설명(`SITE.description`)의 "7개 도착어"도 정정했다.**
`languages.ts`의 `TARGET_LANGS`는 7개 항목이 `enabled: true`지만, 마법사엔
`setTargetLang`을 실제로 호출하는 UI가 없다 — `DEFAULT_TARGET_LANG`('ko')에
고정이다(CLAUDE.md: "도착어는 한국어만 활성"). `simpleCopy.ts`의 랜딩 문구는
이미 이런 종류의 과장을 걸러내는 회귀 테스트가 있지만(§1-15), 이 문자열은
`lib/brand.ts`에 따로 있어서 그 스윕 밖이었다. "SRT · 7개 도착어" → "한국어로
번역 ... 다운로드는 SRT 또는 원본 형식(VTT)"로 — 후자는 실제 지원 범위(VTT만
왕복 writer가 있음, `docs/TODO.md`)와도 맞춘 것이다.

`viewport.themeColor`도 같이 봤다 — 실제 배경과 무관한 제네릭 회색(`#f5f5f7`는
공교롭게도 `--bg`와 값이 같았으니 그대로 두고, `BRAND.bg`를 참조하도록만 바꿔
이후 토큰이 다시 갈라지지 않게 했다.

### 6-9. OG 마크를 새 괄호 모양으로 다시 그리고, "아무도 안 본 화면"을 훑었다 (2026-08-03)

§6-8이 스코프 밖으로 남긴 OG 마크(옛 다이아몬드)를 새 괄호 모티프로 교체했다.
Satori가 우리 `<rect>`를 안 받으므로 파비콘의 32×32 viewBox 좌표를 그대로 두고
`px()`로 스케일한 div 7개(스템 2 + 암 4 + 노란 칩)로 다시 그렸다 — 좌표를 원본
숫자로 유지해야 마크가 바뀔 때 두 파일을 눈으로 대조할 수 있다. 파비콘과 같은
밝은 칩 배경까지 재현해, 공유 카드·브라우저 탭·홈 화면 아이콘이 한 세트로 읽힌다.

**그 과정에서 Satori의 알파 미지원을 실측으로 찾았다.** §6-8에서 `BRAND`를 새
배색으로 고치자 카드가 통째로 노란 판이 됐는데, 원인은 그라디언트 중간 stop에
쓴 `rgba(255,212,0,0.08)`(`--accent-wash`, 8%)이었다. 픽셀을 찍어보니
`rgb(255,211,14)` — **Satori는 그라디언트 color stop의 알파를 버리고 불투명하게
칠한다.** 옛 팔레트에서 안 드러난 이유는 그때 `accentSoft`가 *불투명* 연녹색
(`#E8F5EE`)이었기 때문이다. 배경에 미리 합성한 불투명 hex(`WASH = #F6F0D4`)로
바꿔 해결했고, 같은 함정을 다시 밟지 않도록 `lib/brand.ts`에 경고를 달았다.
브랜드 원칙("yellow는 point color지 field color가 아니다")과도 이제 맞는다.

**이어서 "코드는 도는데 아무도 눈으로 본 적 없는" 표면을 훑었다.** OG 카드가
정확히 그런 자리였고(§6-8), 같은 종류가 더 있는지 확인한 것이다.

- **프로덕션 빌드를 처음 돌렸다** — 그동안 `tsc`만 봤지 `npm run build`는 이
  세션에서 한 번도 안 돌렸다. 통과했다. 덤으로 `/opengraph-image`가 `○ (Static)`,
  즉 **빌드 타임 프리렌더**임을 확인했다 — Pretendard CDN 페치가 요청마다가
  아니라 빌드 때 한 번만 일어나므로, 런타임에 jsdelivr이 죽어도 공유 카드는
  멀쩡하다.
- **`/legal`·`/legal/privacy` 제목이 `이용약관 | ZAMAK · ZAMAK`으로 브랜드명이
  두 번 들어가 있었다.** 페이지가 자기 제목에 `| ZAMAK`을 넣는데 루트 layout의
  `title.template`(`%s · ZAMAK`)이 또 붙였다. 페이지 쪽에서 뺐다.
- **`/mypage`는 제목이 아예 없어** 사이트 기본 제목이 떴다. `'use client'`라
  `metadata`를 못 내보내므로 `mypage/layout.tsx`를 만들어 제목 + `noindex`를 줬다
  (로그인 뒤 화면이라 색인 대상이 아니다).
- **`public/`에 create-next-app 잔여 SVG 5개**(`next.svg`·`vercel.svg`·
  `globe.svg`·`window.svg`·`file.svg`)가 배포되고 있었다. 리포 전체에서 참조 0건
  확인 후 삭제. (`grep`이 `file.svg`를 1건 잡았는데 `.dl-file svg {` CSS
  선택자 오탐이었다.)
- **확인하고 문제없던 것들**: `/dev/preview`·`/dev/prototype`은 프로덕션 빌드에서
  정상 404. 404 페이지 렌더 정상. 모바일 375px에서 가로 스크롤 넘침 0
  (`scrollWidth == clientWidth`), 레이아웃 정상. 약관 페이지의 사업자 정보는
  전부 실값으로 차 있고 시행일(8/1)도 발효 상태. `.env*`는 추적되지 않으며,
  브라우저에 나가는 `NEXT_PUBLIC_SUPABASE_ANON_KEY`는 JWT를 디코드해
  `role: anon`임을 확인했다(service_role이 아니다).
- **`og:image`가 절대 URL로 나가는지 두 시나리오로 빌드해 확인했다** — 이게
  틀리면 카톡·트위터에 미리보기 카드가 아예 안 뜬다. `NEXT_PUBLIC_SITE_URL`을
  준 빌드와, 그걸 깜빡하고 `VERCEL_ENV=production`만 있는 빌드 **둘 다**
  `https://zamak.app/opengraph-image`로 나왔다 — `layout.tsx`의 `siteUrl()`
  폴백 사다리가 실제로 안전망 역할을 한다.

**남긴 것**: 모바일 탭 타깃이 37~38px로 iOS 권장 44px 미달이다(`TODO.md`).
버튼 높이를 올리면 랜딩 리듬이 밀려 디자인 재조정이 따라오므로, 오탭이 실제로
관측되면 그때 본다. OG 카드의 워드마크는 여전히 Pretendard Bold 텍스트라 실제
로고(`zamak-logo.png`)의 자소 형태와는 다르다 — 노란 마침표만 살려 두었고,
로고 이미지를 인라인하는 건 `outputFileTracingIncludes` 배선이 따라와 배포
리스크가 있어 오늘은 안 했다.

### 6-10. 레이트 리밋·에러 모니터링·색인을 한꺼번에 닫는다 (2026-08-03)

베타 오픈 점검(§6-9)이 남긴 TODO 네 건을 처리했다. 넷이 한 커밋 묶음인 건
전부 "제품 기능이 아니라 **우리가 눈을 뜨고 있기 위한 배선**"이기 때문이다.

**① 레이트 리밋은 총량이 아니라 개인을 막는 것이다.** 처음 이 항목을 적을 때의
걱정은 "30명이 몰려 Gemini 한도에 걸린다"였는데, `gemini-limits.md` §2-1 정정
이후 §7-2 재계산이 동시 38~68명을 버틴다고 답해서 그 걱정은 사라졌다. **남은
위험은 한 사람이 스크립트로 enrich/analyze를 수백 번 도는 것**이고, 총량
숫자는 그것에 대해 아무 말도 하지 않는다. 대상은 크레딧을 안 쓰면서 실제 API
비용을 내는 넷 — `/api/analyze`·`/api/enrich`·`/api/summarize`·`/api/glossary`.
번역 경로는 크레딧이 이미 상한이라 안 붙였다.

- **카운터는 Postgres에 둔다.** 배포가 Vercel 서버리스라 프로세스 메모리
  카운터는 인스턴스마다 따로 세고, 인스턴스가 늘수록 실효 한도가 같이 는다 —
  즉 가드가 아니다. Supabase는 이미 모든 요청 경로에 있어 새 인프라가 0이다.
  고정 창(fixed window)이라 경계에서 최대 2배가 몰릴 수 있지만, 막으려는 게
  "수백 번"이지 정밀 셰이핑이 아니라 슬라이딩 윈도우의 행 누적·청소 cron을
  살 이유가 없었다.
- **한도는 일부러 느슨하다** (cheap 3종 합산 20/분, 글로사리 5/분). 한 파일의
  정상 경로는 analyze 1 + enrich 1~3 + summarize 1 + glossary 1이다. **진짜
  사용자가 429를 보면 그건 한도가 틀린 것**이고, 그 상태를 방치하면 한도는
  아무 의미 없어질 때까지 올라간다.
- **fail-open이다 — `requireUser()`와 반대 방향이고, 의도한 것이다.**
  `requireUser()`는 익명 인터넷과 우리 Gemini 청구서 사이의 벽이라 고장 나면
  "아무도 못 지나감"이 맞다. 이건 **이미 인증된** 사용자의 호출 속도 천장이고,
  최악이 "우리가 보고 있는 청구서가 좀 는다"이다. 그걸 막으려고 "Supabase가
  깜빡일 때마다 베타 전원의 업로드가 죽는다"를 사는 건 나쁜 거래다.

**② 에러 모니터링은 로그의 대체재가 아니라 집계다.** `console.error`는 전부
그대로 두고 `server_errors`에 **추가로** 쌓는다. 스택 전문은 Vercel 로그에
있고, 로그가 못 답하는 질문은 "이번 주에 /api/translate가 몇 번 터졌고 매번
같은 것이었나"다. 외부 SaaS(Sentry 등) 대신 표 하나인 이유: 베타에 새 env·
비용·개인정보 처리위탁 항목을 늘리지 않고, 조회를 이미 쓰는
`beta-review.sql` 옆(§8)에 붙일 수 있다.

가장 값이 큰 배선 지점은 **`/api/glossary`**다. 이 라우트는 실패해도 빈 시트를
200으로 돌려주므로(§2-9의 "throw가 밖으로 안 샌다"), 화면에서 "고유명사가 없는
파일"과 구분되지 않는다. 기록이 없으면 글로사리가 꺼진 채로 베타가 끝나도
아무도 모른다. 다음으로는 `/api/translation/result`의 upload 실패 — 크레딧은
이미 나갔고 행은 결과물이 있다고 말하는데 실제 바이트가 없어서, 사용자는
30일 뒤에 안다.

**한계 두 가지를 기록해 둔다.** (a) RLS 정책상 `user_id`가 필요해 **로그인
이전에 터진 예외는 안 남는다** — 그 경로는 여전히 Vercel 로그가 유일한 기록이다.
(b) `extractCastSheet` **안에서** 삼켜지는 폴백(키 없음·파싱 실패)은 라우트까지
안 올라와서 여전히 안 보인다. 둘 다 지금 고치려면 service-role 키를 새로
들이거나 서비스 계층에 요청 신원을 흘려야 해서, 이번 범위에서는 뺐다.

**③ 색인은 연다 (대표 결정).** 기존 상태가 문제였던 건 열려 있어서가 아니라
**어중간해서**였다 — `layout.tsx`가 `index: true`인데 robots.txt도 sitemap도
없어서, 크롤러가 우연히 걸어 들어간 것만 색인되는, 아무도 고르지 않은 결과가
나오고 있었다. 이제 `app/robots.ts`가 `/api/`·`/auth/`·`/mypage`·`/dev/`만
막고(비밀 유지가 아니라 크롤 예산과 "검색 결과에 API 경로가 뜨는 것"을 막는
목적), `app/sitemap.ts`가 공개 3페이지를 명시한다.

- **사이트맵을 파일시스템에서 유도하지 않고 손으로 적었다.** `app/` 아래 대부분의
  라우트는 정확히 **들어가면 안 되는** 것들이다(세션 게이트, 프로토타입, API).
  명시 목록은 나중에 누가 페이지를 추가해도 저절로 광고하지 않는다 — 사이트맵에
  넣는 건 결정이어야지 부작용이면 안 된다.
- **`lastModified`는 일부러 비웠다.** 페이지 내용이 실제로 언제 바뀌었는지에 대한
  빌드 타임 진실 소스가 없고, `new Date()`를 찍으면 "세 페이지가 배포마다 바뀐다"는
  **거짓**을 크롤러에게 말하게 된다. 구글은 이 필드를 힌트로만 쓰므로, 없는 힌트가
  틀린 힌트보다 낫다.
- **§6-9가 검증한 `siteUrl()` 폴백 사다리는 `app/lib/brand.ts`의
  `resolveSiteUrl()`로 옮겼다** (동작은 그대로). robots·sitemap·`metadataBase`
  셋이 반드시 같은 오리진을 말해야 하기 때문이다 — 프리뷰 배포가 프로덕션
  도메인으로 자기 사이트맵을 광고하는 게 전형적인 사고다. 그래서
  **`NEXT_PUBLIC_SITE_URL`은 프로덕션 환경에만 설정한다**(README Deploy 절).

**④ README 배포 env 목록**은 결제 분리(§6-2) 이후 낡아 있었다. 실제로 필요한 건
다섯 개(`GOOGLE_GENAI_API_KEY`·`TMDB_API_KEY`·Supabase 둘·`NEXT_PUBLIC_SITE_URL`)
이고, 빼는 것마다 이유를 같이 적었다 — 목록만 고치면 다음 사람이 "OPENAI는 왜
없지" 하고 도로 넣는다. 같은 §의 프로젝트 구조·아키텍처 다이어그램에도 결제
경로가 남아 있어 함께 고쳤다(TODO엔 env 목록만 적혀 있었다).

### 6-11. 운영자 테스트 계정은 DB allowlist로 차감을 면제한다 — 앱 코드 우회가 아니라 (2026-08-06)

실사용 경로(업로드→번역→다운로드→히스토리)를 반복 확인할 때마다 운영자 계정의
번역권이 소진되는 게 실질적인 개발 마찰이었다. 세 안을 놓고 골랐다.

**① 잔액을 크게 충전한다** (`supabase/comp-credit.sql`, 코드 0줄). 지금 당장은
되지만 결국 다시 떨어지고, "콤프로 넣은 잔액"과 "결제로 들어온 잔액"이 같은
컬럼에 섞여 매출 집계가 지저분해진다.

**② 라우트에 환경변수 우회를 넣는다.** 각하 — 결제 우회 분기가 프로덕션 번들에
실려 나간다. env 하나가 잘못 설정되면 전원이 무료가 되는 종류의 실수고, 사고
반경이 allowlist보다 훨씬 크다.

**③ DB allowlist (채택).** `public.unlimited_testers`(0013)에 있는 user_id는
`begin_translation_job`이 차감을 건너뛴다. 이 선택이 성립하는 이유는 **차감이
애초에 그 함수 한 곳에서만 일어나기 때문**이다(§1의 "한 번만 과금" 구조) — 면제
분기도 같은 한 곳에 들어가고, 다른 어디에도 흩어지지 않는다. 회수는 delete 한
줄이고, 대상은 표에 명시적으로 적힌 행뿐이다.

세부 결정 셋:

- **job row는 면제 계정도 똑같이 insert한다.** 크레딧만 안 빠질 뿐
  `translation_jobs`·메트릭·결과 보관은 실사용과 같은 경로를 타야 한다. 안 그러면
  "무제한 계정에서만 테스트했는데 정작 히스토리 경로는 한 번도 안 밟은" 상태가
  된다.
- **`/api/credits`는 이 계정에 `UNLIMITED_CREDIT_DISPLAY`(999)를 돌려준다.**
  실제 잔액은 0에 머무는데, UI는 잔액 0을 빨갛게 띄우도록 되어 있다
  (`TranslateSettingsStep`). 표시용 값일 뿐 한도가 아니다 — 클라이언트가 잔액으로
  번역을 막지 않기 때문에(서버가 유일한 게이트) 이 숫자는 화면에만 영향을 준다.
- **읽기 RLS만 본인 행에 열고 쓰기 정책은 만들지 않았다.** 클라이언트가 스스로를
  무제한으로 등록할 수 있으면 표 자체가 무의미해진다. 등록은 서비스 롤(SQL
  Editor)뿐이다.

**곁다리로 발견한 것: `dev-seed.sql`의 충전 블록이 죽어 있었다.** 2·3·4번이
0004에서 버려진 `balance` 컬럼을 건드리고 있어서, 실행해도 잔액이 안 늘고 번역도
안 됐다. `comp-credit.sql`은 8-02에 같은 이유로 고쳐졌는데 이 파일만 남아
있었다 — **같은 컬럼을 쓰는 스니펫이 두 파일에 흩어져 있으면 한쪽만 고쳐진다.**
둘 다 `lite_balance`/`pro_balance`로 맞췄다.

### 6-12. 진행 바 이징의 앞쏠림을 버린다 — §6-5를 뒤집지 않고 좁힌다 (2026-08-15)

**증상**: 실사용에서 바가 "시작하자마자 사십몇 프로대부터 시작해서, 마지막에
확 구십몇 프로로 점프했다가 또 잠깐 멈춘다."

**원인 셋**
1. `ENRICH_ALWAYS_DONE`(page.tsx) 때문에 enrich는 진행 화면에 **오기 전에**
   끝나 있고 글로사리는 기본 OFF다. 그런데 밴드는 context에 0-15,
   glossary에 15-25를 고정 배분했다 — 0~25가 통째로 죽은 구간이고 바는
   태어날 때 25%다.
2. `easeToward`가 `1 − e^(−3t/D)`라 t=0에서 가장 빠르다. flash 20초 런이
   2초 만에 갭의 26%를 지난다 → 25% + 65×0.26 ≈ 42%.
3. 청크 착지가 한 웨이브에 몰리면 floor가 한 번에 뛰고, `useEasedProgress`가
   그걸 즉시 반영했다.

**②와 ③은 한 손잡이의 양쪽 끝이다.** 앞쏠림은 꼬리 점프를 줄이려고 지불한
대가였다 — ②만 고치면 ③이 악화된다. 그래서 셋을 같이 고쳤다.

**§6-5를 뒤집지 않는다.** §6-5가 지킨 성질은 "이징은 천장에 도달하지
못하므로 추정이 짧아도 거짓말이 아니라 크롤로 열화된다"였다. 그건 그대로
유지된다. 버리는 건 그 성질이 아니라 지수 곡선에 **딸려온 부작용**인
앞쏠림이다.

**결정**
- 곡선: `t < D`면 `K·(t/D)` 선형, `t ≥ D`면 `1 − (1−K)·e^(−(t−D)/D)` 크롤.
  `K = 0.9`. 이음매는 연속이고, 천장에는 여전히 도달하지 않는다.
  `K`를 1이 아니라 0.9로 두는 건 남은 10%를 **청크가 실제로 착지할 자리**로
  비워두기 위해서다.
- 밴드: 고정 상수에서 **예상 소요 비례 계산**으로. weight 0인 단계는 폭도
  목록도 갖지 않는다 — §6-5가 글로사리에만 하던 처리를 전 단계로 넓힌 것이다.
  verify만 5~12%p로 클램프한다(회수 스윕이 붙을 수 있는 유일한 단계).
  밴드는 **런 시작에 한 번 계산하고 언다** — `useState` lazy initializer로.
  `useRef` lazy-init 패턴은 `react-hooks/refs` 린트가 "렌더 중 ref 읽기"로
  막는다.
- floor 점프: 즉시 반영 대신 400ms 캐치업(`catchupValue`, `easing.ts`).

**함께 고친 것**: `ProgressStep`이 `model` prop을 받는다. 밴드 폭과 남은 시간
추정을 `estimateRunMsFromBlocks(totalLines, model)`로 잡는데, 이건 설정 화면
ETA와 **같은 함수**다. 이전엔 `DEFAULT_MODEL` 폴백을 써서 Pro 런이 첫 청크
요청 전까지 flash의 "약 20초"를 보여줬다.

**주의할 점**
- verify 폭 클램프는 비례성을 **의도적으로 깬다.** Pro 장편에서 verify가 실제
  소요보다 넓은 밴드를 갖는다 → 그 구간에서 바가 실제보다 느리다. 스윕
  정체를 막는 대가다. `RECOVERY_EXPECTED_MS` 실측이 생기면 재검토한다.
- 밴드 얼림은 첫 추정에 의존한다. 첫 추정이 크게 빗나간 런은 밴드 비율이
  끝까지 틀린 채로 간다. 곡선이 초과분을 크롤로 흡수하므로 거짓말은 되지
  않지만 체감 비례성은 떨어진다.
- `K = 0.9`는 실측이 아니라 튜닝값이다. 꼬리 점프가 여전히 거슬리면 올리고,
  추정 초과 런의 크롤이 길게 느껴지면 내린다.

설계 문서: `docs/superpowers/specs/2026-08-15-progress-ui-v2-design.md`
계획 문서: `docs/superpowers/plans/2026-08-15-progress-ui-v2.md`

### 6-13. 죽어 있던 `ellipsis` 필드를 배선했다 — 한국어 `...`는 같은 날 되돌렸다 (2026-08-18)

**~~한국어 자막의 말줄임표는 `...`로 내보낸다~~ → 되돌림. 전 도착어가 `…`다.**
표기 자체는 기준 문서(`docs/standards/netflix-korean-subtitles.md` §I.4)가 요구하는
U+2026 한 글자로 돌아왔다. 이 항목을 지우지 않고 남기는 건 **배선은 그대로 살아
있기 때문**이다 — 다음 사람이 표기를 다시 만질 때 알아야 할 순서 제약이 아래에 있다.

**발견한 상태(이게 이 항목의 본체다)**: `TargetLang.ellipsis` 필드는 §6-12
커밋(07e1d8b)에 이미 들어와 있었고 한국어도 `'...'`로 선언돼 있었다. 그런데
**읽는 쪽이 없었다** — `grep`으로 확인한 참조는 정의부 하나뿐이고,
`enforceTextRules`는 도착어와 무관하게 항상 `…`로 정규화한 채 그대로 반환했다.
필드의 주석은 "마지막 단계에서 이렇게 표기한다"고 적혀 있었지만 그 마지막 단계가
존재하지 않았다. **주석이 미래형으로 쓰여 있으면 그게 구현된 건지 계획인지 구분이
안 된다** — 이번처럼 필드가 조용히 죽어 있어도 아무도 모른다. 선언이 곧 동작이라고
믿고 "한국어는 이미 `...`로 나가고 있다"고 읽은 게 애초의 오독이었다.

**배선**: `TextRuleOptions.ellipsis`를 추가하고 `useTranslation.ts`(프로덕션)와
`scripts/polish.mts`(교정 CLI) 양쪽에서 `resolveTargetLang(...).ellipsis`를 넘긴다.
두 호출부를 같이 고친 이유는 §6-11 말미의 교훈과 같다 — **같은 옵션을 쓰는 호출부가
둘로 흩어져 있으면 한쪽만 고쳐진다.** CLI만 다른 표기로 남으면 교정 리포트가
프로덕션과 다른 산출물을 채점하게 된다.

**순서가 이 배선의 전부다.** 재기록은 `enforceTextRules`의 **맨 마지막**, 다른
모든 규칙이 끝난 뒤에 한 번 돈다. 내부 표준은 계속 `…` 1글자다. 지금은 전 도착어가
`…`라 이 단계가 실질 no-op이지만, 누군가 여러 글자 표기를 다시 넣는 순간 아래가
전부 되살아난다:

- **문장부호 스트립보다 뒤**여야 한다. 앞이면 `글쎄...`의 끝 글자가 `.`이라
  줄 끝 마침표 제거에 걸려 점 하나를 잃는다(`글쎄..`). 이건 필드 주석이 원래부터
  경고하던 함정이고, 회귀 테스트로 박아뒀다(`srt.test.ts`).
- **자수 계산보다 뒤**여야 한다. `...`는 3글자라 `…`보다 2글자 부풀어서, 줄 접기
  (`linesJoined`)가 상한 앞에서 멀쩡한 접기를 거부하게 된다.
- **문장 경계 판정보다 뒤**여야 한다. `SENTENCE_END`가 `[.?!…]`로 `…` 1글자를
  기대한다.

**호출부가 `ellipsis`를 안 넘기면 `…`로 남는다** — `trailingPunctuation`·
`lineMaxChars`와 같은 하위호환 규약이다.

**표기를 바꾸려면** `languages.ts`의 그 언어 행 한 줄이면 된다. 배선은 언어
중립이라 코드는 안 건드려도 된다. 테스트도 `ellipsis: '...'`를 명시적으로 넘겨
메커니즘을 검증하므로, 어떤 언어가 무슨 값을 쓰든 그대로 유효하다.

### 6-14. 규칙 적용을 제품에 넣는다 — 무료 + 하루 5회, 독립 라우트 (2026-08-19)

`scripts/polish.mts`(개발용 하네스)로만 있던 "번역 없이 표기 규칙만 적용"을
`/polish` 페이지로 제품화했다. `docs/TODO.md`에 "제품에 넣을지, 넣는다면 크레딧을
번역과 같이 받을지"로 남아 있던 미결을 닫는다.

**무료로 낼 수 있는 이유는 보내는 양이 다르기 때문이다.** TODO의 걱정("입력 토큰이
한국어라 번역보다 오히려 크다")은 파일 전체를 보낸다는 전제 위에 있었다. 그 전제를
바꿨다 — 모델에는 **상한 초과 블록만** 간다. 실측(1,126블록)에서 3.8%이고, ZAMAK이
번역한 결과를 재적용하면 0건이라 호출 자체가 없다. 나머지 규칙은
`enforceTextRules`가 코드로 처리해 토큰을 안 쓴다. 블록당 단가는 여전히 비싸지만
곱하는 개수가 1/25이다.

**한도(하루 5회)는 편의 기능이 아니라 보안 요소다.** `/api/translate`에는 "job의
크레딧 증명이 이 엔드포인트를 로그인한 아무나의 무제한 무료 티어가 되지 않게 막는다"는
주석이 있다. `/api/polish`는 의도적으로 무료라 그 가드가 없으므로 레이트 리밋이 그
자리를 그대로 메운다. 새 테이블은 안 만들었다 — `0011`의 `api_rate_limits`가
"크레딧을 안 쓰는 AI 라우트의 유저당 호출 한도"로 이미 있고 `p_bucket`이 자유
텍스트라 **DB 변경이 0이다**. `enforceRateLimit`이 fail-open인 것은 알고 받아들였다:
같은 조건(무료 + AI)인 `/api/glossary`가 이미 같은 선택을 하고 있어 여기서만 다른
규칙을 만들 이유가 없다.

**기존 위저드에 `mode` 축을 더하는 안은 기각했다.** `useWizard`(735줄)에 축이 하나
더 생기면 작품 선택·글로사리·크레딧·동의 모달이 전부 모드별 분기가 된다. 두 흐름이
실제로 공유하는 것은 상태가 아니라 순수 함수(`enforceTextRules`, 어댑터,
`buildDownloads`)라서, 라우트를 갈라도 중복이 거의 안 생긴다. `buildDownloads`만
훅에서 `app/lib/downloads.ts`로 옮겼다.

**CPS 타이밍 조정은 뺐다.** "규칙만 적용"이라면서 노출 시간까지 바꾸면 약속의 범위가
흐려진다. 뺀 대가로 얻은 것이 더 크다 — `adjustSubtitleTiming`이 빠지자 이 경로에
타임스탬프를 건드리는 코드가 **하나도** 안 남았다. 번역 경로의 "밀릴 수 없다"가
여기서는 **"바뀔 수 없다"**가 된다. 부수 효과로 콘텐츠 유형(영화·예능·강연) 선택이
필요 없어져 업로드 화면이 파일 드롭만 남았다. 다시 넣으려면 그 선택도 함께 돌아와야
한다(프로필마다 목표 CPS가 다르다).

**병합 로직을 새로 안 짰다.** 설계 초안은 "부분집합을 보내니 `indexTranslatedBodies`를
그대로 못 쓴다"고 봤는데, 코드를 확인해 보니 틀렸다. `reassembleTranslatedChunk`는
위치가 아니라 **번호로** 대조하므로 청크가 연속일 필요가 없다. 초과 블록만 원본
번호·타임코드째 뽑아 이어 붙이면 그게 곧 유효한 청크이고, 모르는 번호 버리기·빠진
번호 폴백·`|` 분리·모델 타임스탬프 불신이 전부 딸려온다. 새로 쓴 순수 함수는
`collectOverLongBlocks`(뽑기)와 `spliceBlocks`(되돌리기) 둘뿐이다. 후자는 전체를
`map`으로 훑으며 번호가 맞을 때만 갈아끼우므로 **블록 수 보존이 구조적으로
보장된다** — 모델이 쓰레기를 뱉어도 최악은 "아무것도 안 바뀜"이다.

### 6-15. `/`를 서버 컴포넌트로 승격 — 랜딩이 색인에 아예 없었다 (2026-08-19)

§6-10에서 크롤링을 열고 robots·sitemap을 붙였는데, 정작 검색에 잡히는 게
없었다. 확인해보니 `robots.txt`(200)·`sitemap.xml`(200)·메타태그는 전부
정상이었고 **본문이 없었다.** 프로덕션 HTML에서 태그를 벗기면 남는 텍스트가
`<title>` 한 줄뿐이었다.

범인은 `app/page.tsx`의 이 세 줄이었다:

```
if (authLoading) {
  return <div className='min-h-screen' aria-busy='true' />;
}
```

`useAuth`의 `loading` 초기값이 `isSupabaseConfigured`(=true)라 **서버 렌더는
항상 이 분기**였다. `LandingPage.tsx` 740줄 — 우리가 가진 유일한 마케팅
카피 — 는 브라우저가 `getUser()`를 끝낸 뒤에만 존재했고, 크롤러는 그 렌더를
돌리지 않는다.

**`'use client'`는 범인이 아니다.** Next는 클라이언트 컴포넌트도 HTML로
찍어준다. 문제는 그 앞의 빈 early return이었다. 그래서 고친 것도 "랜딩을
서버 컴포넌트로 다시 쓰기"가 아니라 **판정을 서버로 올리기**다:

- `page.tsx` = 서버 컴포넌트. 쿠키로 세션을 읽어 `<WizardApp />` 또는
  `<LandingPage />`를 고른다. 새 인프라 없음 — `lib/supabase/server.ts`의
  `createServerClient`를 그대로 쓴다.
- 로그인 이후 트리는 `components/beta/WizardApp.tsx`로 이동(순수 이동).
  여기 도달했다는 건 세션이 있다는 뜻이므로 `useWizard`/`useFeedbackFollowup`의
  `signedIn`은 `!!user`가 아니라 리터럴 `true`다 — 클라이언트 재확인을
  기다리지 않는다.
- `LandingPage`는 props를 받지 않는다. 서버 컴포넌트는 함수를 못 넘기므로
  `onSignIn`·`auth_error` 배너를 랜딩이 직접 소유한다(어차피 `'use client'`다).

**대가**: 쿠키를 읽으므로 `/`가 동적 렌더링이 된다. 랜딩에 방문자별 콘텐츠가
없으니 캐시 손실이 아깝지만, 색인이 안 되는 것보다 낫고 — 덤으로 **깜빡임이
사라졌다**. 종전에는 로그인 유저도 blank → 앱 순서로 떴다.

측정(로컬, 같은 커밋 전후): 서빙 HTML 40.7KB / 본문 텍스트 약 5,470자,
`h1` 1개 + `h2` 7개. 종전에는 14.6KB / 본문 0자.

⚠️ `app/landing-ssr.test.tsx`가 두 가지를 못 박는다 — 랜딩이 브라우저 없이
마크업을 내는가, 그리고 `page.tsx`가 여전히 서버 컴포넌트인가. 후자가 없으면
랜딩만 검사하는 테스트는 이 회귀를 그대로 통과시킨다.

**아직 남은 것**: 색인 요청(Search Console·네이버 서치어드바이저 등록과
사이트맵 제출)은 계정 작업이라 코드 밖이다. 이 배포 이후에 해야 한다 —
빈 페이지 상태로 첫 평가를 받으면 안 된다.

### 6-16. canonical을 페이지마다 박는다 — 레이아웃 한 줄이 아니라 (2026-08-19)

§6-15를 배포한 날, Search Console이 `/`를 이렇게 거절하고 있었다:

> 페이지 색인이 생성되지 않음: **사용자가 선택한 표준이 없는 중복 페이지**
> 참조 페이지: `https://www.zamak.app/`

구글이 apex와 `www`를 같은 페이지로 보는데 어느 쪽이 정본인지 우리가 말한
적이 없었다. `metadataBase`만으로는 `<link rel="canonical">`이 나오지 않는다 —
실측하니 응답에 canonical 태그가 아예 없었다.

**루트 레이아웃에 `canonical: './'` 한 줄로 끝내지 않았다.** 레이아웃 canonical은
오타 하나로 모든 라우트가 `/`를 가리키게 되고, 그 사고는 조용하다(태그는
있으니 툴이 통과시킨다). 공개 페이지가 셋뿐이라 페이지마다 리터럴로 박는
편이 싸고 검증 가능하다 — `sitemap.ts`가 파일시스템 유도 대신 손으로
나열하는 것과 같은 논리다.

canonical의 진짜 실패 모드는 "없음"이 아니라 **"sitemap과 다른 주소를 말함"**
이다(없느니만 못한 신호다). 그래서 `app/seo.test.ts`가 두 목록을 같은 집합으로
못 박는다. 공개 페이지를 늘리면 양쪽을 다 건드려야 하고, 한쪽을 잊으면 여기서
깨진다.

곁가지 둘:
- 테스트가 서버 페이지의 `metadata`를 읽으려면 import를 해야 하는데
  `lib/supabase/server.ts`의 `import 'server-only'`가 막는다. vitest alias로
  no-op 스텁을 물렸다(`test/stubs/server-only.ts`). 그 가드는 번들을 지키는
  것이지 테스트를 막으라고 있는 게 아니다.
- **`www` 리다이렉트가 307(임시)로 나간다.** `vercel.json`은 `permanent: true`
  (=308)라고 적혀 있으니, Vercel 대시보드의 도메인 리다이렉트가 앞질러
  적용되는 것으로 보인다. 코드로 고칠 수 없어 남겨둔다 — canonical이 붙었으니
  급한 불은 껐지만, 308이 아닌 한 정본 신호는 계속 약하다.
