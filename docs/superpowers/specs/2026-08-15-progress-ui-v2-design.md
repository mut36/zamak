# 진행 바 v2 — 죽은 밴드 제거·앞쏠림 폐기·점프 캐치업

작성 2026-08-15. §6-5(2026-07-31)가 만든 진행 바가 여전히 체감상 안 맞는다.
대표 관찰: **"번역 시작하자마자 사십몇 프로대부터 시작한다. 그리고 마지막에 확
구십몇 프로로 점프했다가 또 잠깐 멈춘다."**

이 문서는 §6-5를 뒤집지 않는다. §6-5가 지킨 안전 성질(이징은 천장에 도달하지
못하므로 추정이 짧아도 거짓말이 아니라 크롤로 열화된다)은 **그대로 유지**하고,
같이 딸려온 부작용인 **앞쏠림**만 폐기한다.

---

## 1. 배경 — 관찰된 증상과 원인

| # | 증상 | 원인 |
|---|---|---|
| 1 | 바가 시작하자마자 25%에 있다 | `ENRICH_ALWAYS_DONE = true`([page.tsx:33](../../../app/page.tsx)). enrich는 진행 화면에 오기 **전에** 끝나 있고 글로사리는 기본 OFF다. `overallPercent()`가 마운트 즉시 context(0-15)·glossary(15-25)를 건너뛰고 translate 밴드 바닥 = 25를 반환한다. 두 밴드는 설계상 존재하지만 런타임에서는 **통과 지점이 아니라 죽은 구간**이다 |
| 2 | 2초 만에 42%까지 오른다 | `easeToward()`가 `from + gap·(1 − e^(−3t/D))`. 이 곡선은 t=0에서 가장 빠르다 |
| 3 | 끝에서 확 점프했다가 멈춘다 | 청크가 한두 개면 착지 이벤트가 끝에 몰려 floor가 25→90으로 한 번에 뛴다. 이어서 finalizing이 98%에 고정된 채 `MIN_VERIFY_MS`(2초)를 기다린다 |

### 1-1. ②와 ③은 한 손잡이의 양쪽 끝이다

앞쏠림을 없애고 선형으로 만들면 시작은 정직해지지만, 추정이 실제보다 길었던
런에서는 **끝의 점프가 더 커진다**. 지수 이징의 앞쏠림은 꼬리 점프를 줄이려고
지불한 대가였다. 그래서 ②만 고치면 ③이 악화된다 — 둘은 같이 고쳐야 한다.

### 1-2. ②의 실측표

translate 밴드(25→90, 갭 65) 기준. D는 이 런의 추정 소요.

| 실제 경과 | 바가 그리는 값 |
|---|---|
| 5% | 34% |
| **10%** | **42%** |
| 25% | 59% |
| 50% | 76% |
| 100% | 87% |

flash 20초 런이면 2초 지점이 곧 10%다 → 42%. 대표가 본 숫자와 일치한다.

## 2. 목표 / 비목표

**목표**
- 바가 **0%에서 시작**한다.
- 바의 위치가 실제 경과 시간에 대략 비례한다 (추정이 맞을 때 선형).
- 청크 착지가 몰려도 점프가 아니라 빠른 이동으로 보인다.
- §6-5의 천장 불가침 성질을 유지한다 — 추정이 짧으면 크롤로 열화될 뿐 앞지르지 않는다.

**비목표**
- 서버 SSE / 청크 내부 세분 진행 이벤트. A안(클라이언트 수정)으로 증상 셋이
  모두 잡히므로 미룬다. Pro 크롤이 그래도 거슬리면 그때 꺼낸다.
- `RECOVERY_EXPECTED_MS`(15초 추정치)의 실측화. 별건이며, verify 폭 클램프가
  증상은 덮는다.
- `overallPercent()`의 `enrichDone: false` 분기 제거. 진행 화면에서 enrich가
  도는 경로가 나중에 생길 수 있고 테스트도 이미 있다.
- 번역 파이프라인 자체는 건드리지 않는다 → `docs/translation-pipeline.md` 무관.

## 3. 설계

### 3-1. 밴드 — 이번 런에서 실제로 도는 단계에만, 예상 시간에 비례

`bandsFor(glossaryEnabled)`를 weight 기반으로 일반화한다. 지금 글로사리에만
특별 처리로 하던 것(안 돌면 목록에서 빼고 앞 단계가 구간을 흡수)을 전 단계로
넓히는 것이다.

각 단계의 weight(ms):

| 단계 | weight |
|---|---|
| context | 이 화면에서 enrich가 도는가 ? `CONTEXT_EXPECTED_MS`(3s) : **0** |
| glossary | (enabled && !done) ? `GLOSSARY_WAIT_MS` : 0 |
| translate | 이 런의 추정치 (`estimateRunMsFromChunks`, 없으면 폴백) |
| verify | `MIN_VERIFY_MS`(2s) |

밴드는 weight를 누적 정규화해서 만든다. **weight가 0인 단계는 밴드도 목록도
갖지 않는다.**

두 가지 안전장치:

- **verify 폭은 5~12%p로 클램프한다.** Pro 165초 런에서 비례 폭은 1.2%p인데,
  회수 스윕이 걸리면 움직일 여지가 없어 §6-5가 없애려던 정체가 그대로
  재현된다. 클램프 후 나머지 폭은 다른 단계가 비례 배분한다.
- **밴드는 런 시작에 한 번 계산하고 얼린다.** `estimatedRemainingMs`는 실측
  보정으로 계속 바뀌는데, 밴드가 그때마다 움직이면 이미 지난 구간의 경계가
  이동해 바가 뒤로 간다.

결과 — 현재 기본 런(enrich 완료·글로사리 OFF, flash 20초):

```
translate [0, 90.9]   verify [90.9, 100]
```

(verify 비례 폭 = 2s / 22s = 9.1%p — 클램프 5~12%p 안이라 그대로 쓴다.)
바가 0에서 시작한다.

### 3-2. 곡선 — 추정까지 선형, 초과분만 크롤

`easeToward()`를 교체한다. `K = 0.9`(추정 시점에 갭의 90%를 지난다):

```
t < D :  p = K · (t / D)
t ≥ D :  p = 1 − (1 − K) · e^(−(t − D) / D)
```

- t=D에서 두 식이 모두 K를 주므로 **연속**이다.
- 두 구간 모두 **단조 증가**한다.
- t→∞에서 p→1이지만 **절대 1이 되지 않는다** → 천장 불가침 유지.

**바가 실제로 그리는 절대 퍼센트** (flash 20초 런, 글로사리 OFF 기준. 지금은
translate 밴드가 25–90이고 바뀐 뒤엔 0–90.9라 갭이 다르다):

| 실제 경과 | 지금 | 바뀐 뒤 |
|---|---|---|
| 10% | 42% | **8%** |
| 50% | 76% | 41% |
| 100% | 87% | 82% |
| 300% | 90% | 90% |

추정 시점(100%)에 82%인 건 의도다 — 남은 18%p가 "청크가 실제로 착지할 자리"다.
런이 추정대로 끝나면 floor가 밴드 끝(90.9)으로 오르고 3-3의 캐치업이 400ms에
걸쳐 미끄러진다. 지금은 이 자리가 87→90으로 3%p밖에 없어서, 착지가 늦으면
그만큼 바가 죽은 채로 기다린다.

`from`/`ceiling`/`elapsedMs`/`expectedMs` 시그니처는 그대로 두고 내부 식만
바꾼다 — 호출부(`useEasedProgress`)는 무변경.

### 3-3. floor 점프 → 캐치업 슬라이드

`useEasedProgress`가 floor 상승을 즉시 스냅하지 않고 `CATCHUP_MS`(400ms) 동안
선형으로 따라붙는다. 청크가 몰려 착지해도 점프가 아니라 빠른 이동으로 읽힌다.

단조성 유지 방법: `highWater`는 슬라이드의 **목표**가 아니라 **매 프레임의 현재
값**으로 갱신한다. 목표로 갱신하면 슬라이드 도중 floor가 또 오를 때 값이 튄다.

`prefers-reduced-motion`에서는 지금처럼 계단을 그린다 — 캐치업도 건너뛴다.

## 5. 에러 처리 / 경계 조건

| 상황 | 동작 |
|---|---|
| 모든 weight가 0 | translate에 100%를 준다 (0으로 나누기 방지) |
| `totalChunks === 0` | floor는 밴드 바닥(=0). 지금과 동일하게 NaN 없음 |
| `expectedMs <= 0` | `easeToward`가 `from`을 그대로 반환 (기존 가드 유지) |
| 취소 | 지금과 동일 — 즉시 화면 전환, 캐치업 rAF는 cleanup에서 취소 |
| 회수 스윕 | verify 밴드 안에서 천장을 밴드 끝−2로 낮추고 `RECOVERY_EXPECTED_MS` 사용 (기존 로직 유지, 클램프 덕에 최소 5%p의 여지가 있다) |
| `stage === 'done'` | 지금과 동일 — `snap`으로 450ms에 100% |

## 6. 테스트

### 재보정하는 기존 테스트 (곡선을 의도적으로 바꾸므로)

- `easing.test.ts` — "추정 시간에 도달하면 갭의 약 95%" → **90%**
- `easing.test.ts` — "추정보다 오래 걸리면 기어간다"의 델타 임계를 새 곡선으로 재계산
- `progressStages.test.ts` — "`totalChunks`가 0이어도 NaN을 내지 않는다"의 기대값 `25` → **0**
- `progressStages.test.ts` — "청크가 절반 끝나면 translate 밴드의 중간쯤"의 기대값을 새 밴드로

### 그대로 통과해야 하는 기존 테스트 (깨지면 설계가 틀린 것)

- 천장에 절대 도달하지 않는다
- 시작점에서 출발한다
- 경과에 대해 단조 증가한다
- 추정보다 오래 걸리면 기어간다 (임계값은 바뀌어도 **성질**은 유지)
- 밴드가 0에서 시작해 100에서 끝나고 구멍이 없다
- 어떤 뷰도 `'skipped'` 상태를 갖지 않는다

### 새로 추가

- weight가 0인 단계는 `stageOrder`/`stageViews`에 나오지 않는다
- 밴드 폭의 합은 항상 정확히 100이다 (클램프가 걸린 경우 포함)
- verify 폭이 5~12%p 범위 안에 있다 (flash 20초 런 / Pro 165초 런 양쪽)
- 추정치가 바뀌어도 얼린 밴드는 움직이지 않는다
- 곡선이 t=D에서 연속이다 (좌극한 = 우극한 = K)
- 캐치업 중 floor가 또 올라도 값이 뒤로 가지 않는다

## 8. 남는 위험

- **verify 폭 클램프는 비례성을 깬다.** Pro 장편에서 verify가 실제 소요보다
  넓은 밴드를 갖는다 → 그 구간에서 바가 실제보다 느리게 움직인다. 스윕
  정체(§1 ③)를 막는 대가로 받아들인다. 스윕 실측이 생기면 재검토한다.
- **밴드 얼림은 첫 추정에 의존한다.** 첫 추정이 크게 빗나간 런에서는 밴드
  비율이 끝까지 틀린 채로 간다. 곡선(3-2)이 초과분을 크롤로 흡수하므로
  거짓말은 되지 않지만, 체감 비례성은 떨어진다.
- **`K = 0.9`는 튜닝값이다.** 실측이 아니라 "추정 시점에 거의 다 왔다고
  보이되 여지는 남긴다"는 판단이다. 꼬리 점프가 여전히 거슬리면 올리고,
  추정 초과 런에서 크롤이 길게 느껴지면 내린다.
