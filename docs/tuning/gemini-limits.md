# Gemini API 한도 조회표 (수기 입력)

청크 크기(B)와 동시성(K)을 계산으로 정하기 위한 입력값. **추측 금지 — 공식 문서에서 조회한 값만.**
빈칸은 비워두고, 문서에 없거나 애매하면 `?`와 함께 메모를 남길 것.

- 대상 모델(빠른번역): `gemini-3.6-flash` — `app/config/constants.ts`의 `FLASH_MODEL`
- 대상 모델(고급번역): `gemini-3.1-pro-preview` — `PRO_MODEL` (2026-07-25 추가)
- 대상 모델(보조): `gemini-3.5-flash-lite` — `AUX_MODEL` (analyze/enrich/summarize)
- 조회일: 2026-07-20 (§1~6, 대표 조회) / 2026-07-21 (§7-1 인프라, §6 thinking 실측) / 2026-07-25 (§1·§4 세 모델 갱신, 대표 조회) / 2026-07-26 (§2 rate limit — 유료 **Tier 2** 승급 후 세 모델 재조회)
- 결제 등급: **유료 Tier 2** (2026-07-26~). 이전 기록은 Tier 1 기준이었다 — §2 참조
- 출처 URL:
  - Gemini rate limits / pricing / model card: 대표가 콘솔·공식 문서에서 직접 조회
  - Vercel Functions 한도(§7-1): <https://vercel.com/docs/functions/limitations>
- **실측으로 확인된 값은 `chunk-size-model.md` §1**에 따로 있다 (이 문서는 *조회*값, 저기는 *측정*값)

## 1. 요청 단위 한도 — 3개 모델 공통 (2026-07-25 확인)

B(청크 크기)의 천장을 정하는 값들. **출력 상한이 1차 천장이다.**
`gemini-3.6-flash` / `gemini-3.1-pro-preview` / `gemini-3.5-flash-lite` **세 모델 모두 동일** —
모델별로 나눠 조회했으나 값이 같아서 공통표로 합친다.

| 항목                                   | 값        | 단위   | 메모                                      |
| -------------------------------------- | --------- | ------ | ----------------------------------------- |
| 요청당 최대 **출력** 토큰              | 65,536    | tokens | 3개 모델 공통                             |
| context window (최대 **입력** 토큰)    | 1,048,576 | tokens | 3개 모델 공통                             |
| 출력 토큰에 thinking 토큰이 포함되는가 | 예        |        | flash 실측(§6)만 확인됨. pro·flash-lite는 미확인 — 포함이면 실질 출력 여유가 그만큼 줄어든다 |

## 2. rate limit — 모델별 (2026-07-26, 유료 **Tier 2**)

K(동시성)의 천장을 정하는 값들.

⚠️ **2026-07-26에 결제 등급이 Tier 1 → Tier 2로 올라가 세 모델을 각각 다시 조회했다.**
이전 표는 flash 한 열(RPM 1,000 / TPM 2M / RPD 무제한)뿐이었고 pro·flash-lite는 미확인
상태였다. 등급이 오르면서 **RPD가 무제한에서 유한한 숫자로 바뀐 게 가장 큰 변화**다 —
이제 하루 처리 편수에 실제 천장이 생겼다.

> **현재 우리가 쓰는 건 유료 열뿐이다.** BYOK가 삭제돼 전원이 서버 키로 돈다
> (`decisions.md` §1-1). 무료 열은 참고용으로 남긴다 — 값 자체는 여전히 맞고,
> 무료 등급 키로 뭔가를 시험할 때 필요하다.

### 2-1. 유료 Tier 2 — 현재 우리가 쓰는 값

| 모델 | 용도 | RPM | TPM | RPD |
| --- | --- | --- | --- | --- |
| `gemini-3.6-flash` (FLASH_MODEL) | 빠른번역 — 번역 트래픽 대부분 | 2,000 | 3,000,000 | 100,000 |
| `gemini-3.5-flash-lite` (AUX_MODEL) | analyze / enrich / summarize | 10,000 | 10,000,000 | 350,000 |
| `gemini-3.1-pro-preview` (PRO_MODEL) | 고급번역 | 1,000 | 5,000,000 | 50,000 |

**모델마다 조이는 축이 다르다.** flash는 RPM 대비 TPM이 상대적으로 빡빡해 **토큰이 먼저**
차고(§7-2 계산), pro는 RPM이 셋 중 가장 낮은 1,000이라 **요청 수가 먼저** 찬다. flash-lite는
어느 축으로도 자릿수가 남는다 — 보조 라우트는 편당 3요청이라 사실상 무제한으로 봐도 된다.

**RPD가 하루 처리 편수의 천장이다** (자막 1편 = `⌈N/B⌉` 요청). B=100·크레딧 상한
파일(20요청/편) 기준:

| 모델 | RPD | 하루 처리 편수 (20요청/편) |
| --- | --- | --- |
| flash | 100,000 | **5,000편** |
| pro | 50,000 | **2,500편** |
| flash-lite | 350,000 | 116,000편 (편당 3요청이므로 실질 무제한) |

### 2-2. 무료 등급 (참고용 — flash 기준, 변동 없음)

| 항목                                    | 무료 등급 | 단위       | 메모                                         |
| --------------------------------------- | --------- | ---------- | -------------------------------------------- |
| RPM (분당 요청)                         | 15        | req/min    | `FREE_CONCURRENCY=6`의 유도 근거             |
| TPM (분당 토큰)                         | 1,000,000 | tokens/min | ⚠️ 아래 3번 확인 필수                        |

| TPD (일일 토큰), 있다면                 | 무제한    | tokens/day |                                              |

## 3. 반드시 확인할 애매한 지점

계산 결과가 통째로 뒤집히는 항목들이라 값보다 이 정의가 더 중요하다.

| 질문                                               | 답            | 메모                                                                                  |
| -------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------- |
| **TPM은 입력만인가, 입력+출력 합산인가**           | 입력만        | 합산이면 K 상한이 대략 절반이 된다                                                    |
| TPM에 캐시 적중된 입력 토큰도 포함되는가           | 예            |                                                                                       |
| RPM 초과 시 429인가, 큐잉/스로틀인가               | HTTP 429      | 429면 우리는 재시도 안 하므로 그 청크가 원문으로 남는다                               |
| 429에 `Retry-After` 헤더가 오는가                  | 아니오        | 제미나이는 기본 헤더 형태로 명시적인 초 단위 Retry-After를 보장하여 제공하지는 않는다 |
| 무료 등급 한도가 프로젝트 단위인가 API 키 단위인가 | 프로젝트 단위 | BYOK 시절의 질문. 지금은 서버 키 하나뿐이라 무의미                                     |

## 5. 컨텍스트 캐싱

`P_fixed`(청크마다 반복되는 고정 프롬프트) 단가를 좌우한다. 캐시가 걸리면 큰 청크의 이점이 줄어든다.

| 항목                                           | 값                      | 메모                                                              |
| ---------------------------------------------- | ----------------------- | ----------------------------------------------------------------- |
| implicit(자동) 캐싱 지원 여부                  | 지원                    | 기본 활성화                                                       |
| implicit 캐시가 걸리는 **최소 접두어 토큰 수** | 4,096                   | 우리 고정 프롬프트가 이보다 짧으면 캐시 자체가 안 걸린다          |
| 캐시 TTL (미사용 시 만료까지)                  | 기본 5분 (수정 가능)    | 청크 간 간격이 이보다 길면 무의미 (명시적 캐싱 사용 시 수정 가능) |
| 캐시 적중을 응답에서 확인하는 필드명           | cachedContentTokenCount | usage metadata의 캐시 토큰 수 필드                                |
| explicit 캐싱 최소 토큰 수                     | 4,096                   |                                                                   |

## 6. thinking / reasoning 설정

자막 번역에는 깊은 사고가 거의 불필요한데, 켜져 있으면 **비용과 출력 여유를 동시에** 잡아먹는다.
단일 최대 절감 레버일 수 있어 별도로 뗀다.

| 항목                                        | 값     | 메모                                                                     |
| ------------------------------------------- | ------ | ------------------------------------------------------------------------ |
| `gemini-3.6-flash`의 thinking 기본값        | medium | 켜짐                                                                     |
| thinking을 끄거나 예산을 0으로 둘 수 있는가 | 안됨   | `thinkingBudget: 0`은 무시된다. 먹는 건 `thinkingLevel`                  |
| 최소 thinking 예산 (0 불가라면)             | minimal | `ThinkingLevel.MINIMAL` — **flash 기준. pro-preview는 MINIMAL 자체를 거부한다, 아래 §6-2 참고** |
| 응답에서 thinking 토큰 수를 확인하는 필드명 | `usageMetadata.thoughtsTokenCount` | `[gemini]` 로그의 `thoughts=`                 |

### 6-1. flash 실측 (2026-07-21) — MINIMAL과 LOW 모두 `thoughts=0`

| THINKING_LEVEL | 실측 thoughts/요청 | 표본 |
|---|---|---|
| MINIMAL | 0 | 200블록 청크 |
| LOW | **0** | 200·200·61블록 청크 3개 (전부 0) |
| MEDIUM | 미측정 | |
| HIGH | 미측정 | |

⚠️ 3줄짜리 장난감 파일 1회에서는 LOW가 `thoughts=595`로 나왔으나, **실제 워크로드(200블록)
3회는 전부 0이었다.** 극단적으로 짧은 입력에서만 thinking이 발생하는 것으로 보인다.
결론: **실사용에서 LOW의 thinking 비용은 MINIMAL과 같다(0).** 품질이 더 나은 LOW를 쓸 이유가 있다.

이 실측이 청크 모델의 결론을 바꿨다 — `th=0`이면 "요청마다 붙는 thinking을 줄이려면 B를
키워야 한다"는 논거가 통째로 사라진다. 상세는 `chunk-size-model.md`.

**이 결론은 flash 전용이다 — pro-preview에는 가져다 쓸 수 없다.** §6-2 참고.

### 6-2. pro-preview 실측 (2026-07-26) — MINIMAL 미지원, LOW도 `thoughts=0`이 아니다

**MINIMAL을 설정할 수 없다.** `ThinkingLevel` SDK enum엔 `MINIMAL`이 존재하지만
API가 `gemini-3.1-pro-preview`에는 이 값을 거부한다(직접 시도로 확인, 2026-07-26).
**LOW가 pro에서 실제로 설정 가능한 최저값**이다 — flash처럼 MINIMAL·LOW가 동급이 아니다.

**그 LOW조차 flash처럼 항상 `thoughts=0`이 아니다.** 967블록 파일(B=100, 청크 10개,
THINKING_LEVEL=LOW) 실제 로그:

| 청크 | prompt | thoughts | output |
|---|---|---|---|
| 1 | 2,777 | 0 | 1,448 |
| 2 | 2,502 | 1,930 | 1,038 |
| 3 | 3,142 | 3,346 | 1,690 |
| 4 | 3,022 | 4,107 | 1,594 |
| 5 | 2,617 | 4,381 | 1,268 |
| 6 | 2,659 | 4,747 | 1,351 |
| 7 | 3,260 | 5,245 | 1,914 |
| 8 | 3,109 | 0 | 1,805 |
| 9 | 3,106 | 0 | 1,810 |
| 10 | 2,726 | 4,089 | 1,342 |

10개 청크 중 7개가 `thoughts>0`(평균 ~2,785/청크), 3개는 0 — flash처럼 안정적으로
0이 아니라 **청크마다 들쭉날쭉하다.** prompt 크기와의 뚜렷한 상관은 안 보인다. thoughts
합계(27,845) × 출력 단가만으로 이 파일 번역 비용의 약 58%를 차지했다. 소요시간도
정비례한다(`thoughts=0`이면 13~18초, `thoughts=5245`면 51초) — 로그 상 이상치가 아니라
실제로 사고 중이라는 뜻.

**영향**: `constants.ts`의 `MAX_BLOCKS_PER_CREDIT` 코멘트가 인용하는 pro 원가(2,000블록
$0.49)는 flash의 `th=0` 가정을 그대로 가져다 쓴 추정치라 이 실측과 안 맞는다 — 실제 pro
원가는 그보다 높을 가능성이 크다. 상세 결정 근거·크레딧 가격 재검토는 `decisions.md`
§2-4-1.

**미결**: MEDIUM(현재 pro 코드 기본값)이 LOW보다 품질·비용 면에서 나은지, LOW의
들쭉날쭉함이 프롬프트 길이 등 다른 변수 때문인지는 미측정.

### 7-1. 인프라 동시 실행 한도 — **조회 완료 (2026-07-21), 병목 아님**

출처: <https://vercel.com/docs/functions/limitations> (last_updated 2026-07-01)

| 항목 | 값 | 메모 |
|---|---|---|
| 배포 플랜의 동시 함수 실행 한도 | **Hobby·Pro 30,000까지 자동 스케일** (Ent 100,000+) | 우리가 쓰는 K=14와 3자릿수 차이 |
| 모델 응답 대기가 함수 실행시간으로 과금되는가 | **CPU는 아니오, 메모리는 예** | 아래 주의 참조 |
| 한도 초과 시 동작 | 자동 스케일 구간 내에선 해당 없음 | |
| 함수 실행시간 상한 | Hobby 300초 / Pro 기본 300초·최대 800초 | 우리 `maxDuration=300`은 Hobby에서도 안전 |

**이 절의 원래 전제가 틀렸다.** "청크 하나가 함수 하나를 300초 점유하므로 동시 접속자 수를
곱한 값이 인프라 한도에 걸린다"고 봤지만, Vercel은 30,000까지 자동 스케일한다. 동시 접속
1,000명이 각자 14청크를 돌려도 14,000으로 한도 안이다. **kmax는 유료 티어의 병목이 아니다.**

⚠️ **다만 "대기가 공짜"는 아니다.** Fluid compute의 과금은 두 축이고 성격이 다르다:
- *Active CPU time* — I/O 대기는 **불포함**. Gemini 응답을 기다리는 동안 CPU 과금 없음
- *Provisioned memory time* — 인스턴스가 **살아있는 벽시계 시간**에 비례. 대기도 여기엔 잡힘

즉 대기의 CPU 비용은 0이지만 메모리 비용은 남는다. 그래도 Gemini 토큰 비용(편당 ~$0.15)에
비하면 무시할 수준이라, **B/K 결정에서 인프라 비용은 고려 대상이 아니다.**

### 7-2. 그래서 K를 실제로 묶는 것은 무엇인가

Gemini도(§2) Vercel도(§7-1) 동시성을 막지 않으므로, K는 **제약이 아니라 우리 선택**이다.
남는 공유 자원은 모델별 **RPM·TPM**(§2-1)이고, 이건 전체 사용자가 나눠 쓴다.

```
1인이 웨이브 중 소비하는 RPM = min(K, ⌈N/B⌉) × 60 ÷ D      (D = 청크 소요초)
1인이 웨이브 중 소비하는 TPM = 위 RPM × 청크당 입력토큰
동시 번역 가능 인원 ≈ min( RPM한도 ÷ 1인RPM , TPM한도 ÷ 1인TPM )
```

flash Tier 2(RPM 2,000 / TPM 3M), 현재값 B=100·K=16 기준 — `D ≈ 9.3초`,
청크당 입력 `1,028 + 100×15 = 2,528`토큰:

| 파일 | 청크 | 웨이브 | 1인 피크 RPM | 1인 피크 TPM | 동시 인원 (RPM / **TPM**) |
| --- | --- | --- | --- | --- | --- |
| 851블록 | 9 | 1 | 58 | 147K | 34명 / **20명** |
| 1,874블록 (샘플 영화) | 19 | 2 | 104 | 262K | 19명 / **11명** |
| 2,000블록 (크레딧 상한) | 20 | 2 | 104 | 262K | 19명 / **11명** |

**먼저 조이는 건 RPM이 아니라 TPM이고, 큰 파일이 몰릴 때 11명 근처가 천장이다.**
(Tier 1 시절 이 자리엔 "16명"이 적혀 있었는데, 그건 RPM만 보고 TPM을 안 본 숫자였다 —
등급이 올라 RPM 여유가 2배가 됐어도 진짜 병목은 그대로 남아 있었던 셈이다.)

K를 키우면 이 숫자가 그만큼 줄어든다 — 그게 K의 진짜 트레이드오프다. 반대로 조여오면
**K를 줄이면 된다**(B를 건드릴 일이 아니다). 참고로 B=100에서 K 자체의 천장은
RPM 기준 309, TPM 기준 183이라, 지금의 16은 어느 쪽으로도 한참 아래다.

## 상태 (2026-07-26)

§1(요청 한도)·§4(단가)는 2026-07-25에, **§2(rate limit)는 2026-07-26 Tier 2 승급과 함께**
세 모델 모두 채웠다. §5(캐싱)는 아직 flash 기준뿐 — pro-preview·flash-lite는 번역 트래픽이
붙으면 그때 조회. **§6(thinking)은 2026-07-26에 pro-preview 실측(§6-2)이 추가됐다** — flash와
달리 pro는 MINIMAL을 설정할 수 없고 LOW도 `thoughts=0`이 아니다. `MAX_BLOCKS_PER_CREDIT`의
pro 원가 추정이 이 실측 이전 값이라 갱신이 필요하다(`decisions.md` §2-4-1).

남은 미측정: THINKING_LEVEL MEDIUM/HIGH 품질·비용(flash 및 pro), flash-lite의 캐싱·thinking
거동, pro의 thoughts 변동 원인, 그리고 **pro의 청크 소요시간 D**(진행 링의 3분 추정이 여기
걸려 있다 — `decisions.md` §2-7). B/K 결정 자체엔 영향 없음(flash의 thinking은 실사용에서
0 — pro의 thinking 변동은 비용 문제이지 B/K 재산정 사유는 아님).

B/K의 최종 결정과 근거는 **`chunk-size-model.md`**에 있다. 이 문서는 그 계산의 입력값이다.

계산 구조 (요약):

```
비용 C(B) = (N/B) × P_fixed × 입력단가          ← B로 줄일 수 있는 유일한 항
          + N × (t_in×입력단가 + t_out×출력단가)  ← B와 무관한 상수

시간 T(B,K) ≈ ceil((N/B)/K) × (TTFT + B×t_out/생성속도)

제약:  B × t_out × (p95 여유계수) ≤ 요청당 최대 출력 토큰
       TTFT + B×t_out/생성속도 ≤ 라우트 타임아웃
       K × 60 / 청크소요초 ≤ RPM
       K × 60 / 청크소요초 × 청크토큰 ≤ TPM
```

**동시성 K는 비용에 영향이 없다** — RPM 아래에서 시간만 최소화하면 되는 별개 문제다.
